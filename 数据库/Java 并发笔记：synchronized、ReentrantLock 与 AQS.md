# Java 并发笔记：synchronized、ReentrantLock 与 AQS

## 一、核心概念

Java 中，`synchronized` 和 `ReentrantLock` 都属于可重入的互斥锁，并且默认都不保证公平性。

**可重入锁**：同一个线程已经持有某把锁时，可以再次获取这把锁，不会因此阻塞自己。

**公平锁**：获取锁时原则上遵循先来先得，优先考虑已经排队的线程。

**非公平锁**：允许新到来的线程在一定条件下插队获取锁，不保证严格的 FIFO 获取顺序。

## 二、synchronized 与 ReentrantLock 区别

| 特性           | synchronized     | ReentrantLock       |
| -------------- | ---------------- | ------------------- |
| 默认公平性     | 非公平           | 非公平              |
| 支持公平锁     | 不支持配置       | 支持                |
| 可重入         | 支持             | 支持                |
| 底层机制       | JVM Monitor      | AQS                 |
| 锁释放         | 自动释放         | 手动 unlock         |
| 可中断获取锁   | 不支持           | lockInterruptibly() |
| 超时获取锁     | 不支持           | tryLock(timeout)    |
| 条件等待       | wait/notify      | Condition           |
| 获取失败时等待 | Monitor 相关机制 | AQS 队列及 park     |

### 1. synchronized

```
synchronized (object) {
    // 临界区代码
}
```

特点：

- JVM 层面实现，基于对象监视器机制。
- 不保证线程按照等待顺序获取锁。
- 进入同步块时获得锁，退出同步块时自动释放锁。
- 发生异常退出同步块，也会自动释放锁。
- 支持同一个线程重复获取相同对象的监视器锁。

注意：`synchronized` **不使用 AQS 等待队列**。

### 2. ReentrantLock

默认非公平锁：

```
ReentrantLock lock = new ReentrantLock();
```

等价于：

```
ReentrantLock lock = new ReentrantLock(false);
```

公平锁：

```
ReentrantLock lock = new ReentrantLock(true);
```

推荐使用方式：

```
lock.lock();
try {
    // 临界区代码
} finally {
    lock.unlock();
}
```

`ReentrantLock` 需要主动释放锁，因此通常使用 `try-finally`，避免出现异常时锁无法释放。

## 三、ReentrantLock 为什么可以重入？

ReentrantLock 基于 AQS 实现，核心涉及两个信息：

- `state`：记录当前锁的持有次数。
- `exclusiveOwnerThread`：记录当前持有独占锁的线程。

### state 的变化过程

假设 T1 连续获取两次锁：

```
lock.lock();   // state = 1
lock.lock();   // state = 2

lock.unlock(); // state = 1
lock.unlock(); // state = 0
```

| 操作             | state | 锁状态      |
| ---------------- | ----- | ----------- |
| 初始状态         | 0     | 未持有      |
| T1 第一次 lock   | 1     | T1 持有     |
| T1 第二次 lock   | 2     | T1 重入     |
| T1 第一次 unlock | 1     | T1 仍然持有 |
| T1 第二次 unlock | 0     | 完全释放    |

**核心结论：**

1. 同一线程重复加锁时，`state` 增加。
2. 每次解锁，`state` 减少。
3. 只有 `state = 0` 才代表锁真正释放。
4. 其他线程不能因为持有者只释放一次锁就获得锁。
5. 非持有线程不能随意调用 `unlock()` 释放别人的锁。

## 四、AQS 等待队列是什么？

AQS（AbstractQueuedSynchronizer）是 Java 实现锁和同步器的基础框架。

ReentrantLock 通过 AQS 管理锁状态和竞争失败的线程。

### 1. 等待队列

假设 T1 正在持有锁：

```
当前持有锁：T1

AQS 等待队列：

Head <-> T2 <-> T3 <-> T4
```

AQS 使用双向等待队列组织等待节点，整体采用 FIFO 思路。

其中：

- Head 是队列头节点。
- T2 是 Head 的后继节点。
- T3、T4 排在后面。

Head 通常不是当前持有锁的线程节点，不能直接把 Head 理解为 T1。

### 2. 获取锁失败后发生什么？

以 T2 为例：

```
T2 调用 lock()
      ↓
尝试获取锁
      ↓
获取失败
      ↓
加入 AQS 等待队列
      ↓
检查队列位置
      ↓
如果前驱是 Head
则尝试获取锁
      ↓
仍然获取失败
      ↓
检查/设置等待状态
      ↓
满足挂起条件
      ↓
LockSupport.park()
      ↓
线程挂起等待
```

注意：这个流程是简化版本，实际会循环检查，可能多次重试。

**进入等待队列不等于立即挂起。**

原因是：线程入队后，锁可能恰好已经释放，因此还有机会直接获取锁。

### 3. 入队后检查什么？

主要包括：

**① 队列位置**

判断自己是否为 Head 的直接后继节点。

正常队列获取流程中，Head 的后继节点优先获得尝试获取锁的机会。

**② 锁是否可以获取**

对于 ReentrantLock：

- `state = 0`：锁当前空闲，可以尝试获取。
- `state > 0`，且由其他线程持有：不能直接获得锁。
- 当前线程本来就是持有者：允许重入。

**③ 是否可以安全挂起**

AQS 需要处理等待状态、前驱节点和取消等待的节点，确保后续有适当的唤醒机制。

满足条件后调用：

```
LockSupport.park()
```

因此，不能简单理解成“第一次获取失败就立刻挂起”。

## 五、park 和 unpark 的作用

### 1. park()

```
LockSupport.park();
```

作用：挂起当前线程，使其停止继续执行当前获取锁流程，等待后续被唤醒或其他返回原因。

### 2. unpark()

```
LockSupport.unpark(thread);
```

作用：向指定线程提供一个许可，使其可以从 `park()` 返回。

### 3. 唤醒不等于获取锁

假设：

```
T1 持有锁
      ↓
T2 获取失败
      ↓
T2 进入队列
      ↓
T2 park()
      ↓
T1 完全释放锁
      ↓
AQS unpark(T2)
      ↓
T2 恢复运行
      ↓
T2 重新尝试获取锁
      ↓
成功后继续执行
```

`unpark()` 只是使线程有机会恢复执行，**并不是直接把锁交给线程**。

另外，`park()` 也可能因为中断、已有许可或虚假唤醒而返回，因此必须重新检查获取锁条件。

## 六、AQS 是按照队列顺序唤醒的吗？

正常情况下，AQS 会优先唤醒合适的后继等待线程，而不是一次唤醒所有线程。

例如：

```
Head → T2 → T3 → T4
```

一般流程：

1. 当前持有者完全释放锁，唤醒 T2。
2. T2 尝试获取锁。
3. T2 成功获取并执行任务。
4. T2 释放锁，后续由相应的队列逻辑唤醒 T3。
5. 依次推进。

实际可能跳过取消等待的节点。

**重点：唤醒顺序不一定等于锁的最终获取顺序。**

## 七、公平锁与非公平锁的区别

### 1. 公平锁

假设：

```
T1 持有锁

AQS 等待队列：
Head → T2 → T3
```

此时新线程 T4 到来。

对于公平的 ReentrantLock，正常 `lock()` 获取流程会检查是否存在排在前面的等待线程。

如果有，T4 通常不能直接插队，需要进入等待流程。

底层的关键判断是：

```
hasQueuedPredecessors()
```

即判断当前线程前面是否存在排队的线程。

### 2. 非公平锁

同样的场景：

```
T1 完全释放锁
        ↓
AQS 唤醒 T2
        ↓
新线程 T4 调用 lock()
        ↓
T4 还没有进入等待队列
        ↓
T4 直接尝试 CAS 抢锁
        ↓
如果 T4 成功，T4 获得锁
        ↓
T2 继续等待
```

非公平锁的插队主要发生在**新线程进入 AQS 等待队列之前**。

并不是把队列里所有等待线程唤醒，让它们一起抢锁。

### 3. 两种锁对比

| 场景             | 公平锁                 | 非公平锁               |
| ---------------- | ---------------------- | ---------------------- |
| 新线程调用 lock  | 检查前面是否有等待线程 | 可以直接尝试抢锁       |
| 已有线程排队     | 原则上不允许插队       | 允许新线程插队         |
| 锁释放后         | 通常唤醒合适的后继线程 | 通常唤醒合适的后继线程 |
| 是否唤醒全部线程 | 否                     | 否                     |
| 已入队线程       | 通常遵循队列顺序       | 通常遵循队列顺序       |

补充：即使是公平 ReentrantLock，无参 `tryLock()` 也允许在锁空闲时直接尝试获取锁，不严格遵守公平排队规则。

## 八、面试常见问题

### Q1：ReentrantLock 为什么可以重入？

因为其内部通过 AQS 的 `state` 记录持有次数，并记录持有锁的线程。当相同线程再次获取锁时，`state` 增加，因此允许重复获取。

### Q2：T1 连续加锁两次，释放一次后 T2 能获取吗？

不能。

T1 加锁两次后 `state = 2`，释放一次后 `state = 1`，说明锁仍由 T1 持有。必须再次释放，使 `state = 0`。

### Q3：线程进入 AQS 队列就会立即挂起吗？

不会。

线程入队后会检查队列位置，并在合适的条件下重新尝试获取锁，失败且满足挂起条件后才调用 `park()`。

### Q4：被 unpark 唤醒是否代表获得锁？

不代表。

被唤醒后仍需要重新尝试获取锁，成功才能进入临界区。

### Q5：非公平锁是不是会唤醒所有线程一起竞争？

不是。

非公平锁通常仍采用 AQS 的后继唤醒机制。非公平主要体现为新到来的线程可以绕过已有等待队列直接尝试获取锁。

### Q6：synchronized 和 ReentrantLock 默认是什么锁？

两者默认都不保证公平性。

- synchronized：无法配置为公平锁。
- ReentrantLock：默认非公平，可通过 `new ReentrantLock(true)` 创建公平锁。

## 九、核心知识总结

**ReentrantLock：**

```
lock → 尝试获取 → 失败入队 → 检查/重试 → park → unpark → 再次获取锁
```

**可重入：**

```
state: 0 → 1 → 2 → 1 → 0
```

**公平与非公平：**

- 公平锁：考虑已经排队的线程。
- 非公平锁：新线程可能在入队前插队。
- 两者都不是一次唤醒所有等待线程。

**最重要的三个区别：**

1. 入队 ≠ 挂起。
2. 唤醒 ≠ 获取锁。
3. 调用 unlock ≠ 一定完全释放锁。

以上是面试理解版。AQS 在不同 JDK 版本中的等待节点状态和具体实现存在差异，不能把简化流程理解为逐行一致的源码执行顺序。
