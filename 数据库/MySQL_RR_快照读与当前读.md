# MySQL InnoDB：RR 下快照读与当前读的区别

## 1. 核心结论

MySQL InnoDB 默认事务隔离级别是 **REPEATABLE
READ（RR，可重复读）**。理解 RR
时，不能简单地认为"同一个事务里的任何查询，永远只能看到同一份数据"。

InnoDB 中需要区分两种读取方式：

-   **快照读（Consistent Read）**：普通、不带锁的 `SELECT`。在 RR
    下，同一事务中的一致性读通常复用同一个 Read
    View，因此能读取到一致的历史快照。
-   **当前读（Current Read）**：例如
    `SELECT ... FOR UPDATE`、`SELECT ... FOR SHARE`，以及
    `UPDATE`、`DELETE`
    等需要读取并锁定记录的操作。它读取当前可用的最新版本，并按照执行计划对扫描到的记录或范围加锁。

最重要的是下面三种情况：

  -------------------------------------------------------------------------------------------------------------
  读取方式                是否通常会读到不同版本               原因
  ----------------------- ------------------------------------ ------------------------------------------------
  两次都是快照读          不会（排除事务自身修改等情况）       RR 下复用同一个 Read View

  两次都是加锁当前读      通常不会读到其他事务后来提交的修改   第一次当前读锁住相关记录，锁通常持有到事务结束

  先快照读，再当前读      **可能**                             快照读使用 Read
                                                               View；当前读读取最新可用版本，不受之前 Read View
                                                               限制
  -------------------------------------------------------------------------------------------------------------

> 记忆重点：**两次快照读看同一快照；两次加锁当前读依靠锁保护已读记录；快照读与当前读混用，可能看到不同版本。**

以上结论讨论的是 InnoDB 的
RR，且默认假设事务没有先后修改目标记录、没有主动结束事务或释放锁等特殊操作。

------------------------------------------------------------------------

## 2. 情况一：两次都是快照读

假设 `account` 表中有一条记录：

    id   balance
  ---- ---------
     1       100

事务 A：

``` sql
-- 事务 A
BEGIN;

SELECT balance
FROM account
WHERE id = 1;
-- 结果：100
```

第一次普通 `SELECT` 创建 Read View。随后事务 B 修改并提交：

``` sql
-- 事务 B
BEGIN;

UPDATE account
SET balance = 200
WHERE id = 1;

COMMIT;
```

事务 A 再执行一次普通 `SELECT`：

``` sql
-- 事务 A
SELECT balance
FROM account
WHERE id = 1;
-- 结果：100

COMMIT;
```

**为什么第二次仍然是 100？**

在 RR 下，事务 A 的普通一致性读继续使用第一次快照读建立的 Read
View。事务 B 后来提交的版本，对事务 A 当前使用的这个 Read View
不可见，因此事务 A 仍然读到旧版本 `100`。

所以，在没有事务 A
自身修改目标记录等特殊情况时，两次快照读不会因为其他事务提交了更新而出现不可重复读。

------------------------------------------------------------------------

## 3. 情况二：两次都是加锁当前读

仍然假设记录最初是 `balance = 100`。

事务 A：

``` sql
-- 事务 A
BEGIN;

SELECT balance
FROM account
WHERE id = 1
FOR UPDATE;
-- 结果：100，并对命中的记录加排他锁
```

事务 B 尝试修改同一条记录：

``` sql
-- 事务 B
BEGIN;

UPDATE account
SET balance = 200
WHERE id = 1;
-- 被事务 A 持有的锁阻塞，等待
```

事务 A 再执行当前读：

``` sql
-- 事务 A
SELECT balance
FROM account
WHERE id = 1
FOR UPDATE;
-- 结果：100

COMMIT;
```

事务 A 提交并释放锁后，事务 B 才能继续完成更新并提交。

**为什么两次当前读通常不会读到不同值？**

第一次 `SELECT ... FOR UPDATE`
对命中的记录加排他锁。其他事务不能在该锁仍被持有时成功修改这条记录，因此无法在事务
A 两次当前读之间提交对该记录的更新。

注意：

-   InnoDB
    的行锁本质上是对索引记录加锁；范围查询还可能涉及间隙锁、临键锁。
-   锁通常持有到事务提交或回滚。
-   这里讨论的是两次读取同一条已命中的记录，且事务 A
    自身没有修改它的情况。
-   当前读不是"先读完再随便加锁"，它的读取与加锁是配合完成的。

------------------------------------------------------------------------

## 4. 情况三：先快照读，再当前读

这是最容易混淆、也是最值得记住的情况。

初始数据：

    id   balance
  ---- ---------
     1       100

按下面的顺序执行。

**第一步：事务 A 先进行快照读。**

``` sql
-- 事务 A
BEGIN;

SELECT balance
FROM account
WHERE id = 1;
-- 结果：100
```

这次普通 `SELECT` 建立了 Read View。

**第二步：事务 B 修改记录并提交。**

``` sql
-- 事务 B
BEGIN;

UPDATE account
SET balance = 200
WHERE id = 1;

COMMIT;
```

**第三步：事务 A 执行当前读。**

``` sql
-- 事务 A
SELECT balance
FROM account
WHERE id = 1
FOR UPDATE;
-- 结果：200
```

这里读到 `200`，因为 `SELECT ... FOR UPDATE`
是当前读，它读取当前可用的最新版本，不受事务 A 之前快照读的 Read View
限制。

**第四步：事务 A 再执行普通快照读。**

``` sql
-- 事务 A
SELECT balance
FROM account
WHERE id = 1;
-- 结果：100

COMMIT;
```

为什么又变回了 `100`？

因为这次是普通快照读，它仍然使用事务 A 之前建立的 Read View。事务 B
提交的 `200` 版本对这个 Read View 不可见，所以仍然读到旧版本 `100`。

最终，事务 A 观察到：

``` text
第一次快照读：100
第二次当前读：200
第三次快照读：100
```

这并不矛盾。三次查询采用了不同的读取语义：当前读读取最新可用版本，快照读读取
Read View 所允许看到的版本。

## 5. 这算不算 RR 下发生了不可重复读？

需要区分"观察到不同值"和"隔离级别定义中的不可重复读"。

经典的不可重复读描述的是：同一个事务先后读取同一条记录，期间另一个事务修改并提交了该记录，导致事务再次读取时得到不同值。

但分析 MySQL InnoDB 的 RR 时，要说明读取方式：

-   两次普通快照读：在 RR 下复用同一个 Read
    View，不会因为其他事务的提交而读到不同版本。
-   两次针对同一记录的加锁当前读：第一次读取已经锁住记录，其他事务通常不能在两次读取之间修改该记录。
-   一次快照读、一次当前读：可能观察到不同版本。这是两种读取语义不同导致的可见性差异，不能不加说明地说成"两次快照读发生了不可重复读"。

因此，准确表述是：

**MySQL InnoDB 的 RR
保证一致性快照读的可重复性，并通过锁机制保护当前读访问的记录或范围；但它不保证同一个事务中所有不同类型的读取都返回完全相同的数据状态。**

## 6. 顺带区分：不可重复读与幻读

  对比       不可重复读                  幻读
  ---------- --------------------------- ----------------------------
  关注对象   同一条记录                  满足某个查询条件的记录集合
  典型变化   `balance` 从 100 变成 200   查询结果从 5 条变成 6 条
  直观理解   同一行的值变了              多出或少了符合条件的行

InnoDB 在 RR 下的处理思路：

1.  **快照读**：依靠 MVCC 和 Read View 读取一致性快照。
2.  **当前读**：依靠记录锁，以及适用场景下的间隙锁、临键锁，保护读取到的记录或索引范围，避免并发修改或插入破坏当前读所需的范围保护。

间隙锁和临键锁是否加在什么范围，取决于索引、查询条件和实际执行计划，不能简单理解为任何查询都会锁整张表或所有相关间隙。

## 7. 面试回答模板

如果面试官问："MySQL 的 RR 隔离级别下，还会不会出现不可重复读？"

可以这样回答：

> InnoDB 的 RR 下，需要区分快照读和当前读。两次普通快照读通常复用同一个
> Read
> View，因此不会因为其他事务提交更新而读到不同版本；两次针对同一记录的加锁当前读，第一次读取就会加锁，其他事务不能在锁持有期间修改该记录；但是，如果先进行普通快照读，再执行
> `SELECT ... FOR UPDATE`，当前读会读取最新可用版本，不受之前 Read View
> 的限制，因此可能出现先读到 100、当前读读到 200、再次快照读又读到 100
> 的情况。所以 RR 并不意味着事务内所有读取方式都看到完全相同的数据状态。

------------------------------------------------------------------------

## 8. 最后记忆

``` text
RR（InnoDB）
│
├── 快照读 + 快照读
│   └── 同一个 Read View → 通常读到同一版本
│
├── 当前读 + 当前读
│   └── 第一次加锁 → 保护已命中的记录
│       → 其他事务通常不能在中间修改该记录
│
└── 快照读 + 当前读
    └── Read View 与最新可用版本不同
        → 可能读到不同值
```

**一句话：RR
保证的是一致性快照读的可重复性，不是保证事务内任何读取语句都返回同一个版本。**
