# 数据库索引与外键 & JOIN 性能优化笔记（PostgreSQL）

------

## 一、核心结论（先记住这几条）

- 外键：保证**数据正确性**
- 索引：决定**查询性能**
- JOIN：利用**关联字段拼数据**

> **外键不会提升 JOIN 性能，索引才会**

------

## 二、外键、索引、JOIN 的关系

### 1. JOIN 的本质

```sql
SELECT *
FROM A
JOIN B ON A.id = B.id;
```

👉 本质是：
**通过字段相等，把两张表的数据拼起来**

------

### 2. 外键的作用

```sql
FOREIGN KEY (district_id) REFERENCES district(district_id)
```

作用：

- 保证引用存在（不能乱指）
- 防止脏数据
- 控制删除/更新（CASCADE / RESTRICT）

❗ 不负责性能

------

### 3. 索引的作用

```sql
CREATE INDEX idx_xxx ON table(field);
```

作用：

- 加速查询
- 避免全表扫描
- 优化 JOIN

------

### ✅ 三者关系总结

| 组件 | 作用         |
| ---- | ------------ |
| 外键 | 保证关系正确 |
| 索引 | 提升查询速度 |
| JOIN | 使用关系     |

------

## 三、为什么“外键字段必须加索引”

### 1. JOIN 查询

```sql
ON t.district_id = d.district_id
```

- 无索引 → 全表扫描 ❌
- 有索引 → 快速匹配 ✔

------

### 2. 删除主表数据

```sql
DELETE FROM district WHERE id = 'xxx';
```

数据库必须检查：

👉 有没有子表引用它

- 无索引 → 子表全表扫描 ❌
- 有索引 → 快速判断 ✔

------

### 3. 更新主键（CASCADE）

```sql
UPDATE station SET id = 'new' WHERE id = 'old';
```

- 无索引 → 全表找引用 ❌
- 有索引 → 快速更新 ✔

------

### ✅ 结论

> **所有外键字段，一律加索引（工程铁律）**

------

## 四、PostgreSQL 特别注意

- 主键：自动有索引 ✔
- 外键：❌ 不会自动建索引

👉 必须手动加：

```sql
CREATE INDEX idx_taz_district 
ON gzmap_taz_info(district_id);
```

------

## 五、JOIN 性能优化核心

### 1. 最关键因素

> **JOIN 字段上有没有索引**

------

### 2. 优化重点

| 表           | 是否必须索引 |
| ------------ | ------------ |
| 主表（主键） | 一般已有 ✔   |
| 子表（外键） | ❗必须补      |

------

### 3. 复杂查询 → 组合索引

```sql
WHERE type = 'xx' AND travel_time < 30
CREATE INDEX idx_xxx ON table(type, travel_time);
```

------

### 4. 组合索引原则

- 高区分度字段在前
- 常用过滤字段在前

------

## 六、为什么“有索引但 JOIN 还是慢”

### 1. 索引失效（最常见）

```sql
WHERE district_id::text = '123'
```

👉 字段被处理 → 索引失效

------

### 2. 类型不一致

```sql
varchar = int
```

👉 隐式转换 → 索引失效

------

### 3. 区分度低

```sql
WHERE is_open = true
```

👉 大部分都是 true → 索引无意义

------

### 4. 缺少组合索引

```sql
WHERE type = ? AND time = ?
```

👉 需要联合索引

------

### 5. 返回数据过多

```sql
SELECT * FROM 大表 JOIN 大表
```

👉 即使走索引也慢

------

### 6. 执行计划问题

```sql
EXPLAIN ANALYZE
```

检查：

- Seq Scan ❌
- Index Scan ✔

------

### 7. 统计信息过期

```sql
ANALYZE 表名;
```

------

## 七、索引设计规范

### 1. 索引类型

| 类型     | 使用场景     |
| -------- | ------------ |
| 主键索引 | 唯一标识     |
| 唯一索引 | 编码/证件号  |
| 普通索引 | WHERE / JOIN |
| 组合索引 | 多条件查询   |
| 全文索引 | 模糊搜索     |

------

### 2. 命名规范

| 类型     | 规则                 |
| -------- | -------------------- |
| 普通索引 | idx_表名_字段        |
| 唯一索引 | uk_表名_字段         |
| 组合索引 | idx_表名_字段1_字段2 |
| 全文索引 | fts_表名_字段        |

------

## 八、空间数据（你项目的重点坑）

你现在：

```text
geometry = text
```

👉 问题：

- 空间查询 = 全表扫描 ❌

------

### 正确做法（PostGIS）

```sql
ALTER TABLE xxx 
ALTER COLUMN geometry TYPE geometry(Point, 4326);

CREATE INDEX idx_geom 
ON xxx USING GIST (geometry);
```

------

## 九、什么时候可以不用外键

| 场景             | 是否使用外键 |
| ---------------- | ------------ |
| 高并发互联网系统 | ❌            |
| 分库分表         | ❌            |
| 数据分析系统     | ✅            |
| 你当前项目       | ✅            |

------

## 十、最终总结（面试/答辩版）

- JOIN 是基于字段匹配的数据组合操作
- 外键用于保证数据引用关系的正确性
- 索引用于提升查询效率，尤其是 JOIN 性能
- 在 PostgreSQL 中，外键不会自动创建索引，需要手动补充
- 对外键字段建立索引，是数据库性能优化的关键措施之一

------

## 十一、一句话记忆版

> **外键保证不出错，索引保证跑得快，JOIN负责把数据拼起来**
