# MySQL 索引、B+Tree、事务与锁机制

## 一、B+Tree 与索引基础

### 1. 为什么 MySQL 使用 B+Tree

MySQL InnoDB 的索引主要使用 **B+Tree**。

核心原因：

* B+Tree 是多路平衡树，树的高度较低
* 一个节点可以存放大量索引记录
* 查询时从根节点逐层向下查找
* 叶子节点通过双向链表连接，适合范围查询
* 可以减少磁盘 I/O 次数

例如：

```text
                    根节点
                 /    |    \
               /      |      \
            节点      节点      节点
           / | \     / | \     / | \
          叶 叶 叶   叶 叶 叶   叶 叶 叶
```

B+Tree 的非叶子节点主要用于**导航**，真正的数据/索引记录主要位于叶子节点。

---

## 二、Page（页）

### 1. Page 是什么

InnoDB 存储数据的基本单位之一是 **Page（页）**。

默认情况下：

```text
1 Page = 16KB
```

B+Tree 中的节点通常对应一个或多个 InnoDB Page。

因此：

```text
B+Tree 节点
    ↓
InnoDB Page
    ↓
默认约 16KB
```

### 2. 索引页是不是只有非叶子节点？

不是。

**索引页不是“非叶子节点”的同义词。**

B+Tree 中：

```text
根节点 Page        → 索引页
非叶子节点 Page    → 索引页
叶子节点 Page      → 索引页
```

“非叶子节点”是树结构概念。

“Page”是 InnoDB 的存储结构概念。

---

## 三、Page 为什么会导致页分裂

一个 Page 的空间有限。

例如：

```text
一个 Page
┌────────────────┐
│ 索引记录       │
│ 索引记录       │
│ 索引记录       │
│ ...            │
│ 接近满         │
└────────────────┘
```

如果继续插入数据放不下，就可能发生**页分裂**。

例如：

```text
原来：

[10,20,30,40,50]

插入 35：

[10,20,30]   [35,40,50]
```

然后父节点还需要增加相应的索引信息。

因此随机插入容易造成：

* 页分裂
* 数据移动
* Page 空间利用率下降
* 更多 I/O
* 性能下降

---

## 四、为什么递增主键通常更适合索引

如果主键：

```text
1
2
3
4
5
6
...
```

新数据通常直接插入 B+Tree 最右侧。

而随机主键：

```text
823
15
491
72
...
```

可能需要不断向已有 Page 的中间位置插入。

Page 满了以后更容易发生页分裂。

所以通常：

> **具有递增趋势的主键更有利于减少随机页分裂。**

---

# 五、聚簇索引与二级索引

## 1. 聚簇索引

InnoDB 的主键索引就是聚簇索引。

叶子节点保存：

```text
完整的数据行
```

可以理解为：

```text
主键索引
   ↓
B+Tree
   ↓
叶子节点
   ↓
完整数据
```

---

## 2. 二级索引

例如：

```sql
CREATE INDEX idx_name ON user(name);
```

二级索引叶子节点主要保存：

```text
索引列 + 主键值
```

例如：

```text
name      id
张三      100
李四      200
王五      300
```

如果查询：

```sql
SELECT * FROM user WHERE name = '张三';
```

先通过二级索引找到：

```text
张三 → id=100
```

然后再去聚簇索引找到完整数据。

这个过程叫：

> **回表**

---

## 3. 覆盖索引

如果查询所需要的字段全部存在于二级索引中：

```sql
SELECT name, id
FROM user
WHERE name = '张三';
```

二级索引已经包含：

```text
name
id
```

因此不需要再回聚簇索引。

这种情况叫：

> **覆盖索引**

优点：

```text
减少回表
减少 I/O
提高查询效率
```

---

# 六、联合索引

假设：

```sql
INDEX idx_abc(a,b,c)
```

索引的排序规则不是分别排序，而是按照：

```text
先 a
再 b
最后 c
```

排序。

例如：

```text
(a=1,b=10,c=1)
(a=1,b=10,c=2)
(a=1,b=20,c=1)
(a=1,b=30,c=1)

(a=2,b=10,c=1)
(a=2,b=20,c=1)
(a=2,b=30,c=1)
```

因此：

> **联合索引中的后一个字段，只有在前面的字段确定后，才能形成连续有序的范围。**

---

# 七、最左匹配原则

对于：

```text
INDEX(a,b,c)
```

以下查询可以很好利用索引：

```sql
WHERE a = 1
```

```sql
WHERE a = 1 AND b = 2
```

```sql
WHERE a = 1 AND b = 2 AND c = 3
```

但是：

```sql
WHERE b = 2
```

不能直接按照 `(a,b,c)` 的整体顺序高效定位。

因为索引首先按照 `a` 排序。

---

# 八、范围查询为什么还能使用联合索引

这是容易混淆的地方。

假设：

```text
INDEX(a,b,c)
```

查询：

```sql
WHERE a = 2
  AND b > 20
```

很多人会误认为：

> b 是范围，所以联合索引完全失效。

这是错误的。

实际上：

```text
a = 2
↓
先定位 a=2 的区域

b > 20
↓
在 a=2 的区域中定位 b>20 的起点
```

例如：

```text
(a=1,b=...)
...

(a=2,b=10)
(a=2,b=20)
(a=2,b=25) ← 从这里开始
(a=2,b=30)
(a=2,b=40)
...

(a=3,b=...)
```

MySQL 可以直接定位到：

```text
(a=2,b=25)
```

然后沿着 B+Tree 叶子节点继续向后扫描。

因此：

> **范围条件本身仍然可以利用当前列来确定索引扫描范围。**

---

## 九、为什么范围之后的列通常不能继续缩小扫描范围

例如：

```sql
WHERE a = 2
  AND b > 20
  AND c = 1
```

索引：

```text
(a,b,c)
```

当：

```text
a = 2
```

之后，`b` 是有序的。

但是一旦：

```text
b > 20
```

变成范围：

```text
b=21
b=22
b=23
...
b=100
```

在整个这个范围内，`c` 的值会分散在不同的 b 中。

因此：

```text
c=1
```

不能继续简单地缩小 B+Tree 的连续扫描范围。

所以可以理解成：

```text
a = 2
↓
利用 a

b > 20
↓
利用 b 确定扫描范围

c = 1
↓
通常不能继续缩小 B+Tree 扫描范围
```

注意：

> **“范围之后的列不能继续用于缩小索引范围” ≠ “后面的列完全没有任何作用”。**

现代 MySQL 还存在 ICP 等优化机制，但基础面试中首先掌握“范围条件通常阻断后续列的范围定位”即可。

---

# 十、索引为什么可以帮助排序

B+Tree 索引本身是有序的。

例如：

```text
1
3
4
5
7
10
```

这里虽然不是连续的：

```text
1 2 3 4 5 6 7 8 9
```

但仍然是有序的。

所以：

> **排序要求的是有序，不要求连续。**

如果：

```sql
INDEX(age)
```

那么：

```sql
SELECT *
FROM user
ORDER BY age;
```

可以按照索引叶子节点顺序读取：

```text
1 → 3 → 4 → 5 → 7 → 10
```

不需要额外排序。

---

## 十一、WHERE 筛选后还能不能利用索引排序

例如索引：

```text
1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9
```

查询：

```sql
WHERE age IN (2,4,6,8)
ORDER BY age
```

得到：

```text
2 → 4 → 6 → 8
```

虽然中间跳过了：

```text
1、3、5、7、9
```

但是剩下的记录仍然按照索引顺序读取。

所以：

> **索引不要求所有值都被命中，只要最终读取出来的记录保持索引顺序，就可以帮助 ORDER BY。**

---

# 十二、范围查询与索引排序

例如：

```sql
WHERE age > 1
  AND age < 9
ORDER BY age
```

索引：

```text
1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9
```

可以从：

```text
2
```

开始扫描：

```text
2 → 3 → 4 → 5 → 6 → 7 → 8
```

这些结果本身就是有序的。

但是：

> **能使用索引 ≠ 优化器一定选择索引。**

如果查询结果占整张表很大比例，例如：

```text
100万条数据
查询拿77万条
```

优化器可能认为：

```text
走索引 → 大量回表
```

不如：

```text
直接全表扫描
```

因此最终可能选择：

```text
type = ALL
```

这是**成本选择问题**，不是“范围查询不能使用索引”。

---

# 十三、联合索引与排序

假设：

```sql
INDEX(a,b)
```

查询：

```sql
WHERE a = 1
ORDER BY b;
```

可以很好利用索引。

因为索引中：

```text
a=1
```

这一段内部：

```text
b
```

本身就是有序的。

例如：

```text
(a=1,b=10)
(a=1,b=20)
(a=1,b=30)
```

但如果：

```sql
ORDER BY b
```

没有限制 `a`：

```text
(a=1,b=10)
(a=2,b=20)
(a=1,b=30)
```

整体并不是按照 b 排序的。

所以：

> **联合索引能否帮助 ORDER BY，要结合最左匹配和前置列是否确定来判断。**

---

# 十四、OR 与索引

例如：

```sql
WHERE name = '张三'
   OR age = 20
```

假设：

```text
name → 有索引
age  → 没索引
```

`name='张三'` 可以使用索引。

但是：

```text
age=20
```

没有索引，只能大量扫描数据。

整个查询需要满足：

```text
name='张三'
OR
age=20
```

因此不能只查 `name='张三'`，否则会漏掉：

```text
李四，20岁
王五，20岁
赵六，20岁
```

优化器可能认为：

```text
走 name 索引
+
再处理 age
```

成本太高，于是直接：

```text
全表扫描
```

所以所谓：

> “OR 后面的条件没有索引，索引失效”

更准确的说法是：

> **其中一侧无法利用索引时，整个 OR 条件可能无法通过索引高效完成，优化器可能选择全表扫描。**

---

## 十五、OR 两边都有索引

例如：

```sql
WHERE name = '张三'
   OR age = 20
```

同时：

```text
name → idx_name
age  → idx_age
```

那么可能：

```text
idx_name
   ↓
找到 name='张三'

idx_age
   ↓
找到 age=20

   ↓
合并结果
```

这就是：

> **Index Merge**

但是否真的使用 Index Merge，仍然由优化器根据成本决定。

---

# 十六、事务 ACID

## 1. Atomicity：原子性

一个事务：

```text
要么全部成功
要么全部失败
```

例如转账：

```sql
UPDATE account SET money = money - 200 WHERE id = 1;
UPDATE account SET money = money + 200 WHERE id = 2;
```

如果第二条失败：

```text
第一条也必须回滚
```

最终：

```text
ROLLBACK
```

---

## 2. Consistency：一致性

事务执行前：

```text
A = 800
B = 600

总金额 = 1400
```

转账后：

```text
A = 600
B = 800

总金额 = 1400
```

事务前后都满足业务约束。

所以：

> **一致性指事务执行前后，数据库都处于满足约束的合法状态。**

注意：

```text
原子性
↓
要么全做，要么全不做

一致性
↓
做完以后仍然合法
```

---

## 3. Isolation：隔离性

多个事务并发执行时：

> **事务之间应该尽量互不干扰。**

主要解决：

* 脏读
* 不可重复读
* 幻读

涉及：

```text
MVCC
Read View
锁
```

---

## 4. Durability：持久性

事务提交成功：

```sql
COMMIT;
```

即使数据库发生崩溃：

```text
提交的数据也不能丢失
```

主要依赖 Redo Log 等机制。

---

# 十七、幻读

幻读：

> **同一个事务中，两次相同的范围查询，第二次出现了第一次不存在的新记录。**

例如：

```text
第一次：

id
3
```

其他事务插入：

```text
2
```

第二次：

```text
id
2
3
```

新出现的 `2` 就像“幻影”。

---

# 十八、Record Lock 为什么不能解决幻读

假设：

```text
1    3    5
```

Record Lock：

```text
1    🔒3    5
```

只能锁：

```text
3
```

不能锁：

```text
2
```

因为 `2` 原本不存在。

其他事务仍可以：

```sql
INSERT INTO user(id) VALUES (2);
```

所以：

> **Record Lock 只能控制已经存在的记录，不能阻止范围内插入不存在的新记录。**

---

# 十九、Gap Lock

Gap Lock：

```text
只锁索引间隙
```

例如：

```text
1       3       5
```

锁：

```text
(1,3)
```

意味着：

```text
1 ───── 🔒🔒🔒 ───── 3
```

其他事务不能：

```sql
INSERT ... VALUES (2);
```

因为：

```text
2 ∈ (1,3)
```

但 Gap Lock 本身不锁 `1` 和 `3`。

---

# 二十、Next-Key Lock

Next-Key Lock：

```text
Record Lock + Gap Lock
```

对索引记录 `3`：

```text
1       3       5
        ↑
```

锁：

```text
(1,3]
```

其中：

```text
(1,3) → Gap Lock
3     → Record Lock
```

所以：

```text
Next-Key Lock
=
左边间隙 + 当前记录
```

不是：

```text
当前记录 + 右边间隙
```

---

# 二十一、为什么 Next-Key Lock 能防止幻读

例如：

```text
1    3    5
```

事务 A：

```sql
SELECT *
FROM user
WHERE id = 3
FOR UPDATE;
```

涉及：

```text
(1,3]
```

因此：

```text
1 ─────── 3
  Gap     Record
```

事务 B：

```sql
INSERT INTO user(id) VALUES (2);
```

因为 `2` 位于：

```text
(1,3)
```

所以受到 Gap Lock 限制。

这样就避免了其他事务在这个范围内插入新的符合条件的记录。

---

# 二十二、快照读与当前读

## 快照读

普通：

```sql
SELECT * FROM user;
```

属于：

> **Snapshot Read（快照读）**

RR 下主要通过：

```text
MVCC
+
Read View
```

读取一致的数据版本。

---

## 当前读

例如：

```sql
SELECT * FROM user FOR UPDATE;
```

或者：

```sql
SELECT * FROM user FOR SHARE;
```

属于：

> **Current Read（当前读）**

读取最新版本，并需要考虑锁。

可能涉及：

```text
Record Lock
Gap Lock
Next-Key Lock
```

---

# 二十三、RR 下幻读的完整理解

不能简单说：

> “RR 使用 Next-Key Lock 解决幻读。”

更准确：

```text
RR
│
├── 普通 SELECT
│      ↓
│    快照读
│      ↓
│    MVCC / Read View
│
└── SELECT ... FOR UPDATE
       ↓
     当前读
       ↓
     Record Lock
     Gap Lock
     Next-Key Lock
```

因此：

> **RR 下的快照读主要通过 MVCC 保证一致性视图；当前读通过锁机制限制并发修改和范围插入。**

# 二十五、面试速记

### 索引

```text
B+Tree：
多路平衡 + 低树高 + 叶子有序

Page：
InnoDB 默认 16KB

聚簇索引：
叶子节点 = 完整数据

二级索引：
叶子节点 = 索引列 + 主键

回表：
二级索引找到主键 → 再查聚簇索引

覆盖索引：
查询字段全部在索引中 → 不需要回表
```

### 联合索引

```text
INDEX(a,b,c)

a = ?
    → 用 a

a = ? AND b = ?
    → 用 a、b

a = ? AND b > ?
    → a 定位 + b 确定范围

a = ? AND b > ? AND c = ?
    → c 通常不能继续缩小 B+Tree 范围
```

### 排序

```text
索引有序
≠
索引值连续

1 3 4 5 7
也是有序的

所以索引可以帮助 ORDER BY。
```

### 事务

```text
原子性：
要么全成功，要么全失败

一致性：
事务前后都满足约束

隔离性：
事务之间尽量互不干扰

持久性：
COMMIT 后数据不能丢
```

### 锁

```text
Record Lock
= 锁已有记录

Gap Lock
= 锁索引间隙
= 防止范围内 INSERT

Next-Key Lock
= Record Lock + Gap Lock
= 左边间隙 + 当前记录
= (前一个索引值, 当前索引值]
```

### 读

```text
普通 SELECT
= 快照读
= MVCC / Read View

FOR UPDATE / FOR SHARE
= 当前读
= 读取最新版本
= 涉及锁
```

### 幻读

```text
Record Lock
    ↓
只能锁已有记录
    ↓
挡不住 INSERT
    ↓
可能幻读

Gap Lock
    ↓
锁索引间隙
    ↓
阻止 INSERT

Next-Key Lock
    ↓
左边间隙 + 当前记录
    ↓
当前读下防止范围内插入
```

**最核心的一条逻辑链：**

```text
为什么需要 Gap Lock？
        ↓
Record Lock 只能锁已有记录
        ↓
无法阻止 INSERT 新记录
        ↓
范围查询可能出现幻读
        ↓
Gap Lock 锁住索引间隙
        ↓
阻止其他事务在范围内 INSERT
        ↓
Next-Key Lock
= Gap Lock + Record Lock
        ↓
当前读下防止幻读
```
