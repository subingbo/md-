# 📚 InnoDB 锁机制核心笔记：S/X锁与 Gap/Record 兼容性

## 一、 锁的三大基本形态

在 RR（可重复读）隔离级别下，InnoDB 为了解决幻读问题，引入了基于范围的锁机制。

| 锁类型                     | 锁定对象                               | 核心作用                                                  |
| -------------------------- | -------------------------------------- | --------------------------------------------------------- |
| **Record Lock** (记录锁)   | 索引上的**单条记录**                   | 防止其他事务 UPDATE/DELETE 这条记录                       |
| **Gap Lock** (间隙锁)      | 索引记录之间的**间隙** (不含记录本身)  | 防止其他事务在间隙中 INSERT 新记录（防幻读）              |
| **Next-Key Lock** (临键锁) | **Record + Gap** 的组合 (左开右闭区间) | 既防修改，又防插入。InnoDB 在 RR 级别下默认使用的加锁算法 |

------

## 二、 ⭐️ 核心兼容矩阵 (终极考点)

> 💡 **核心口诀（用户金句）**： **“S 和 X 只在一条记录（Record）上不能共存，在间隙（Gap）上永远 OK！”**

| 锁的作用位置        | S锁 + S锁 | S锁 + X锁 | X锁 + X锁 | 结论解析                                                     |
| ------------------- | --------- | --------- | --------- | ------------------------------------------------------------ |
| **Gap (间隙上)**    | ✅ 兼容    | ✅ 兼容    | ✅ 兼容    | 间隙锁只防插入，多个事务同时声明“这里不许插”，彼此不矛盾，**永远不互斥**。 |
| **Record (记录上)** | ✅ 兼容    | ❌ 冲突    | ❌ 冲突    | 记录锁保护已有数据。读(S)+读(S)可以并发；但只要涉及写(X)，就必须独占。 |

## 三、 关键语法与触发条件

### 1. 手动触发“当前读”的两种姿势

普通的 `SELECT` 是**快照读**（走 MVCC，不加锁）。如果要加锁，必须使用**当前读**：

| SQL 语法                        | 加的锁类型          | 语义                                                         | 典型场景                      |
| ------------------------------- | ------------------- | ------------------------------------------------------------ | ----------------------------- |
| `SELECT ... LOCK IN SHARE MODE` | **S**-Next-Key Lock | “我要看最新数据，且看完前别人**不许改、不许插**，但**允许别人也来看**。” | 读取数据用于校验，不打算修改  |
| `SELECT ... FOR UPDATE`         | **X**-Next-Key Lock | “我要看最新数据，且接下来**我可能要改**，别人**既不能看也不能改**。” | 读取数据后紧接着要进行 UPDATE |

### 2. 自动加锁场景

- **Serializable 隔离级别**：所有的普通 `SELECT` 都会**自动隐式**加上 `LOCK IN SHARE MODE`（加 S-Next-Key Lock）。
- **DML 语句**：`INSERT / UPDATE / DELETE` 会自动对涉及的数据加 **X-Record / X-Next-Key Lock**。

## 四、 三大经典实战场景解析

### 🗡️ 场景 1：Serializable 下的“读读并发”

- **现象**：事务 A 执行 `SELECT * FROM t WHERE id > 5;`，事务 B 执行 `SELECT * FROM t WHERE id = 10;`。
- **结果**：**事务 B 不会阻塞，瞬间返回。**
- **原理**：Serializable 下普通 SELECT 自动加 S-Next-Key Lock。事务 A 加 S 锁，事务 B 也加 S 锁。根据矩阵，**Record 上 S+S 兼容，Gap 上 S+S 也兼容**。这正是 Serializable 允许高并发读的原因。

### 🗡️ 场景 2：S-Next-Key vs X-Next-Key 的真实区别

- **现象**：事务 A 执行 `SELECT ... LOCK IN SHARE MODE;` (加 S-Next-Key)。事务 B 执行 `SELECT ... LOCK IN SHARE MODE;` (加 S-Next-Key)。事务 C 执行 `SELECT ... FOR UPDATE;` (加 X-Next-Key)。

- **结果**：**事务 B 不阻塞，事务 C 阻塞。**

- 原理

  ：

  - A 和 B 的 Gap 部分兼容，Record 部分 (S+S) 也兼容，所以 B 畅通无阻。
  - A 和 C 的 Gap 部分兼容，但 **Record 部分 (S+X) 冲突**！C 被卡在 Record 上，必须等 A 释放锁。

### 🗡️ 场景 3：INSERT 唯一键冲突的“特例” (极易踩坑)

- **现象**：表中有 `id=10` 的记录。事务 A 执行 `INSERT INTO t VALUES (10, 'x');`（唯一键冲突报错）。事务 B 紧接着也执行 `INSERT INTO t VALUES (10, 'y');`。

- **结果**：**事务 B 立即报错，不会阻塞等待事务 A。**

- 原理

  ：

  - 正常逻辑下，INSERT 应该加 X 锁。但 InnoDB 做了一个**特殊优化**：当 INSERT 遇到唯一键冲突时，它**故意加 S-Gap Lock**，而不是 X-Gap Lock。
  - 因为加的是 S-Gap，事务 B 来插入时，也能顺利加上自己的 S-Gap（Gap上 S+S 兼容），然后检测到冲突立刻报错返回。
  - **如果加的是 X-Gap**，事务 B 就会傻等事务 A 提交/回滚，白白浪费性能。

## 五、 🧠 终极记忆卡片

```text
1. 间隙(Gap)锁之间，无论是 S 还是 X，永远相亲相爱（兼容）。
2. 记录(Record)锁之间，只有 S+S 能共存，沾 X 必打架（互斥）。
3. LOCK IN SHARE MODE = 加 S 锁（防写不防读）。
4. FOR UPDATE = 加 X 锁（防写又防读）。
5. INSERT 唯一键冲突 = 降级加 S-Gap（为了让大家都能快速报错，不互相死等）。
6. Serializable 普通读 = 自动加 S 锁（所以读读不阻塞）。
```
