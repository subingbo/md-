# Java HashMap 寻址原理与扩容机制详解



## 一、基础概念：桶数组与索引

| 概念             | 符号/值          | 含义                                                    |
| ---------------- | ---------------- | ------------------------------------------------------- |
| 数组长度（容量） | `n` / `capacity` | 桶的总个数，默认 16，必须是 2 的幂次方（16、32、64...） |
| 掩码             | `n - 1`          | 用来做 `&` 运算的二进制掩码，低位全 1                   |
| 索引范围         | `0 ~ n-1`        | 桶位的编号，共 n 个                                     |

**关键点：**

- `n - 1` **不是序号**，而是用来计算索引的**掩码**。
- 索引（序号）的范围是 `0` 到 `n-1`。

------

## 二、寻址公式：为什么用 `hash & (n-1)`

### 1. 本质等价于取模

```
hash % n  ==  hash & (n - 1)    // 当 n 是 2 的幂次方时成立
```

### 2. 为什么要减 1？

`n` 是 2 的幂次方，二进制形式为 `10000...`（只有一个 1）。 `n - 1` 的二进制形式为 `01111...`（低位全 1）。

```
n = 16  →  二进制 10000
n - 1 = 15  →  二进制 01111  ← 低4位全1，可作为掩码
```

用 `n - 1` 做 `&` 运算，效果是**保留 hash 的低位，高位清零**，结果自然落在 `0 ~ n-1` 范围内。

### 3. 如果不减 1 会怎样？

直接用 `hash & n`：

```
n = 16  →  二进制 10000
hash & 16 的结果只能是 0 或 16，无法均匀分布到 16 个桶位。
```

### 4. 为什么不用 `%`？

- `%` 是除法运算，CPU 需要 **10~30 个时钟周期**
- `&` 是位运算，CPU 只需要 **1 个时钟周期**

HashMap 每次 `put`/`get` 都要算索引，这个优化在高频调用下非常可观。

### 5. 交换律

`&` 运算可交换，所以：

```
(n - 1) & hash  ==  hash & (n - 1)
```

两者结果完全相同，源码写的是前者，理解成后者也没问题。

------

## 三、扩容机制：`n-1` 的变化

### 1. 扩容前后掩码对比

扩容时数组长度翻倍（`newCap = oldCap * 2`），公式依然是 `(n-1) & hash`，只是 `n` 变了：

```
扩容前：oldCap = 16, oldCap - 1 = 15 = 0000 1111（保留低4位）
扩容后：newCap = 32, newCap - 1 = 31 = 0001 1111（保留低5位）
```

**关键发现：新掩码比旧掩码只多了一位（第5位从 0 变成 1），其余低位完全相同。**

### 2. 元素位置的两种可能

因为只多考察了 hash 的一位，所以每个元素在新数组中的位置只有两种可能：

- **低位（lo）**：hash 的新增位是 **0** → 留在原索引 `j`
- **高位（hi）**：hash 的新增位是 **1** → 移到 `j + oldCap`

### 3. 数学证明：转移后位置与新公式一致

**情况1：`hash & oldCap == 0`（留在原索引 j）**

```
hash 的第5位是0：
hash & 31 = 0xxx xxxx = j  ✓
```

**情况2：`hash & oldCap != 0`（移到 j + oldCap）**

```
hash 的第5位是1：
hash & 31 = 1xxx xxxx = 16 + j = j + oldCap  ✓
```

**本质推导：**

```
newCap - 1 = (oldCap - 1) | oldCap

hash & (newCap - 1)
= hash & ((oldCap - 1) | oldCap)
= (hash & (oldCap - 1)) | (hash & oldCap)
= 旧索引 j | (hash & oldCap)
```

- `hash & oldCap == 0` → 结果 = `j`
- `hash & oldCap == oldCap` → 结果 = `j + oldCap`

**结论：用 `hash & oldCap` 判断去留，和直接用新公式 `hash & (newCap - 1)` 算索引，结果严格等价。**

## 四、JDK 8 扩容优化：免重算哈希

### 1. JDK 7 vs JDK 8

| 版本  | 做法                                                    | 复杂度 |
| ----- | ------------------------------------------------------- | ------ |
| JDK 7 | 遍历每个元素，重新算 `hash & (newCap - 1)`              | O(n²)  |
| JDK 8 | 用 `hash & oldCap` 判断去留，链表拆成两条直接挂到新数组 | O(n)   |

### 2. 核心判断：`hash & oldCap`

```
oldCap = 16，二进制 10000（只有第5位是1）

hash & 16 == 0   →  第5位是0  →  留在原索引
hash & 16 != 0   →  第5位是1  →  移到 原索引 + 16
```

`oldCap` 的二进制只有一个 1，`&` 运算结果要么是 0，要么是 `oldCap` 本身，恰好对应新增位的值。

### 3. 链表拆分：高低位两条链表

```java
Node<K,V> loHead = null, loTail = null; // 低位链表头尾
Node<K,V> hiHead = null, hiTail = null; // 高位链表头尾

Node<K,V> e = oldTab[j];
do {
    Node<K,V> next = e.next;
    if ((e.hash & oldCap) == 0) {
        // 低位：挂到 loTail 后面
        if (loTail == null) loHead = e;
        else loTail.next = e;
        loTail = e;
    } else {
        // 高位：挂到 hiTail 后面
        if (hiTail == null) hiHead = e;
        else hiTail.next = e;
        hiTail = e;
    }
    e = next;
} while (e != null);

// 低位链表放到新数组的原索引位置
if (loTail != null) {
    loTail.next = null;
    newTab[j] = loHead;
}
// 高位链表放到新数组的原索引 + oldCap 位置
if (hiTail != null) {
    hiTail.next = null;
    newTab[j + oldCap] = hiHead;
}
```

**注意：**

- 使用**尾插法**，保持链表原有顺序
- 避免了 JDK 7 头插法在并发扩容时可能产生的死循环问题

### 4. 红黑树的处理

如果桶里是红黑树，调用 `split()` 方法，按同样的 `hash & oldCap` 规则拆成两棵子树。如果拆分后某棵子树的节点数 ≤ 6，会退化成链表。

## 五、具体例子验证

假设 `oldCap = 16`，旧数组索引 5 的桶里有两个节点：

```
节点A：hash = 5  = 00101（第5位是0）
节点B：hash = 21 = 10101（第5位是1）
```

**扩容前：**

```
节点A: 5 & 15 = 00101 = 5  → 索引5
节点B: 21 & 15 = 00101 = 5  → 索引5（冲突，同一条链表）
```

**扩容时判断：**

```
节点A: 5 & 16 = 00101 & 10000 = 0     → 留在索引5
节点B: 21 & 16 = 10101 & 10000 = 10000 → 移到索引 5 + 16 = 21
```

**扩容后验证：**

```
节点A: 5 & 31 = 00101 & 11111 = 00101 = 5  ✓
节点B: 21 & 31 = 10101 & 11111 = 10101 = 21 ✓
```

原来挤在索引 5 的一条链表，扩容后被拆成两条，分别放到索引 5 和 21，冲突减少。

------

## 六、一句话总结

> **`n - 1` 是一个低位全 1 的掩码**，`hash & (n-1)` 等价于 `hash % n`，但用位运算更快。扩容时 `n` 翻倍，掩码只多一位，通过 `hash & oldCap` 判断该位是 0 还是 1，决定元素留在原位还是移到 `原索引 + oldCap`，不需要重新计算哈希。这是 JDK 8 扩容优化的数学基础，时间复杂度从 O(n²) 降到 O(n)。

------

## 七、延伸思考

- **为什么数组长度必须是 2 的幂次方？** 只有这样才能保证 `n - 1` 的低位全 1，`&` 运算才等价于取模。
- **如果长度不是 2 的幂会怎样？** `n - 1` 的低位不是全 1，`&` 运算无法均匀分布，会浪费一半以上的桶位。
- **ConcurrentHashMap 的扩容？** 多线程协作扩容，一个线程触发扩容，其他线程发现后主动来"帮忙"搬数据，既不会互相覆盖，还能加速扩容。
