# CPU Cache 工作原理、伪共享与缓存淘汰机制

> 学习方向：计算机组成原理 / 操作系统 / Java 并发
> 核心知识链：CPU Cache → Cache Line → 地址映射 → 缓存一致性 → 伪共享 → 缓存替换 → 写回机制

## 一、CPU 为什么需要缓存？

CPU 的运算速度远高于主内存（RAM）的访问速度。

如果 CPU 每次读取数据都直接访问主内存，就会因为内存访问延迟而频繁等待。

因此，现代 CPU 通常采用多级缓存结构：

```
CPU Core
   │
   ▼
L1 Cache（一级缓存）
   │
   ▼
L2 Cache（二级缓存）
   │
   ▼
L3 Cache（三级缓存）
   │
   ▼
RAM（主内存）
   │
   ▼
SSD / HDD（持久化存储）
```

典型特点：

| 存储层级 | 容量                 | 访问速度 | 常见设计                         |
| -------- | -------------------- | -------- | -------------------------------- |
| L1 Cache | 几十 KB              | 最快     | 每核心私有，通常分指令和数据缓存 |
| L2 Cache | 几百 KB～数 MB       | 较快     | 常见为每核心私有                 |
| L3 Cache | 数 MB～数十 MB或更大 | 较慢     | 通常由多个核心共享               |
| RAM      | 数 GB～数百 GB       | 更慢     | 多核心共享                       |
| SSD      | 数百 GB～数 TB       | 最慢     | 持久化存储                       |

具体容量、延迟与共享方式取决于 CPU 架构。

### 1.1 CPU 缓存利用什么原理？

主要利用程序的局部性：

**时间局部性（Temporal Locality）**

刚刚访问过的数据，短时间内很可能再次被访问。

例如：

```
int a = 10;
System.out.println(a);
System.out.println(a);
```

**空间局部性（Spatial Locality）**

访问某个地址后，很可能访问相邻地址。

例如：

```
int[] arr = new int[1000];

for (int i = 0; i < arr.length; i++) {
    arr[i]++;
}
```

数组中的相邻元素通常连续存储，CPU 可以利用缓存行一次加载多个元素。

## 二、什么是 Cache Line（缓存行）？

**Cache Line 是 CPU Cache 管理和传输数据的基本粒度。**

现代主流 x86 CPU 的缓存行通常为 64 字节。

例如主内存中的数据：

```
物理地址：
0x1000                         0x103F
│                                  │
▼                                  ▼
┌────────┬────────┬────────────────┐
│ a (8B) │ b (8B) │ 其他数据 (48B) │
└────────┴────────┴────────────────┘
              共 64B
```

假设：

```
long a = 10;
long b = 20;
```

并且它们在物理内存中恰好位于同一个缓存行。

CPU 访问 `a` 时，通常会把包含 `a` 的整个缓存行加载到 Cache，而不是只加载 `a` 的 8 字节。

因此，`b` 的数据也会一起进入缓存。

**注意：Java 对象的实际内存布局由 JVM 决定，不能仅凭两个字段声明相邻，就断定它们一定在同一个缓存行。**

## 三、CPU Cache 和主内存是否一一对应？

**不是。**

CPU Cache 的容量远小于主内存，不可能把主内存的数据全部存储下来。

例如：

- RAM：16 GB
- L1 Cache：32 KB
- Cache Line：64 B

L1 Cache 可以容纳：

```
32 × 1024 / 64 = 512 个缓存行
```

而 16 GB RAM 包含：

```
16 × 1024³ / 64
= 268435456 个 64B 内存块
```

所以 CPU 需要使用缓存映射机制。

### 3.1 物理内存块和 Cache Line 的关系

假设：

```
主内存：

内存块 A → 0x1000～0x103F
内存块 B → 0x1040～0x107F
内存块 C → 0x1080～0x10BF
```

CPU Cache 可以保存其中部分内存块的副本：

```
CPU Cache：

Cache Line 0 → 内存块 C
Cache Line 1 → 内存块 A
Cache Line 2 → 内存块 B
```

缓存行存放的位置由缓存映射方式决定。

因此：

- 主内存地址与 Cache 的存储槽位不是一一对应关系。
- 一个缓存行会标识自己当前缓存的是哪个内存块。
- 不同 CPU 核心可以缓存同一个物理内存块。
- 同一个 Cache 槽位在不同时刻可以保存不同内存块的数据。

## 四、CPU 怎么找到需要的数据？

CPU Cache 使用地址映射和 Tag（标记）查找数据。

常见映射方式包括：

1. 直接映射（Direct Mapped）
2. 全相联映射（Fully Associative）
3. 组相联映射（Set Associative）

现代 CPU 的许多缓存采用组相联设计。

### 4.1 组相联缓存

假设 L1 Cache 的配置为：

```
容量：32 KB
缓存行大小：64 B
相联度：8 Way
```

那么：

```
缓存行总数 = 32KB / 64B = 512

Cache Set 数量 = 512 / 8 = 64
```

也就是：

- 64 个 Cache Set（缓存组）。
- 每个 Set 有 8 个 Way（存储槽位）。
- 每个 Way 可以容纳一条 64B 的缓存行。

### 4.2 地址划分

以物理地址寻址的简化模型为例：

```
物理地址
┌────────────────┬─────────┬─────────┐
│      Tag       │  Index  │ Offset  │
└────────────────┴─────────┴─────────┘
```

各字段的作用：

| 字段   | 作用                         |
| ------ | ---------------------------- |
| Tag    | 标识当前缓存行属于哪个内存块 |
| Index  | 定位缓存组 Cache Set         |
| Offset | 定位缓存行内部的字节         |

对于上面这个 32KB、8 Way、64B 的例子：

- Offset 需要 6 bit，因为 2⁶ = 64。
- Index 需要 6 bit，因为有 64 个 Set。
- 剩余地址位用于 Tag。

这是便于理解的物理地址模型。实际处理器的 L1 Cache 还可能采用虚拟索引、物理标记等机制。

### 4.3 CPU 查询缓存的完整过程

假设 CPU 访问物理地址 `0x1008`。

```
CPU 访问 0x1008
       │
       ▼
根据 Index 定位 Cache Set
       │
       ▼
检查该 Set 中各 Way 的 Tag
       │
       ├── Tag 匹配且有效
       │        │
       │        ▼
       │     Cache Hit
       │        │
       │        ▼
       │  根据 Offset 读取数据
       │
       └── 没有匹配的有效缓存行
                │
                ▼
             Cache Miss
                │
                ▼
         获取对应的内存块
```

**重点：CPU 不是遍历整个缓存寻找某个内存地址，而是利用 Index 定位缓存组，再比较 Tag。**

## 五、为什么不同 CPU 核心会缓存相同的数据？

因为多个核心共享物理内存，但拥有各自的私有缓存。

假设：

```
                RAM
         内存块 A：0x1000～0x103F
                 │
          ┌──────┴──────┐
          │             │
          ▼             ▼
       CPU Core 1    CPU Core 2
          │             │
          ▼             ▼
       L1 Cache      L1 Cache
       内存块 A       内存块 A
```

执行过程：

1. 核心 1 需要读取 `a`，加载包含 `a` 的内存块 A。
2. 核心 2 需要读取 `b`，由于 `b` 也位于 A 中，因此同样加载 A。
3. 两个核心各自保存内存块 A 的副本。

**注意：两个核心中缓存行的实际存储位置不需要相同。**

CPU 通过缓存行对应的内存地址信息，以及缓存一致性机制，识别这些副本属于同一个物理内存块。

### 5.1 为什么不能让两个 CPU 随意修改副本？

假设：

```
初始状态：

CPU 1：a=10，b=20
CPU 2：a=10，b=20
```

然后：

```
CPU 1 修改 a=100
CPU 2 修改 b=200
```

如果完全没有缓存一致性机制：

```
CPU 1：a=100，b=20
CPU 2：a=10， b=200
```

就可能出现不同缓存副本之间的数据冲突。

因此，多核 CPU 必须通过缓存一致性协议协调这些副本。

## 六、MESI 缓存一致性协议

MESI 是经典的缓存一致性协议。

它将缓存行划分为四种状态：

| 状态           | 含义   | 说明                                               |
| -------------- | ------ | -------------------------------------------------- |
| M（Modified）  | 已修改 | 当前缓存行包含尚未写回的修改，拥有该行的独占写权限 |
| E（Exclusive） | 独占   | 只有当前核心持有该有效副本，数据未修改             |
| S（Shared）    | 共享   | 多个核心可以持有该缓存行的有效副本                 |
| I（Invalid）   | 无效   | 当前缓存行不能直接使用                             |

### 6.1 两个核心同时读取

```
CPU 1 读取 A
     │
     ▼
获取 A

CPU 2 也读取 A
     │
     ▼

CPU 1：Shared
CPU 2：Shared
```

两个核心可以同时拥有相同内存块的有效只读副本。

### 6.2 一个核心要修改数据

假设两个核心都处于 Shared 状态：

```
CPU 1：A（Shared）
CPU 2：A（Shared）
```

CPU 1 想修改 A：

```
CPU 1 请求 A 的写权限
           │
           ▼
通过一致性协议使其他副本失效
           │
           ▼
CPU 2：Invalid
           │
           ▼
CPU 1 修改 A
           │
           ▼
CPU 1：Modified
```

核心规则：

**同一个缓存行不能同时被两个核心以可独立修改的状态持有。**

### 6.3 如果 CPU 2 又要读取或修改怎么办？

CPU 2 原来的缓存行已经失效。

它需要通过缓存一致性机制获取有效数据。

数据可能来自：

- 其他 CPU 核心持有的缓存。
- 共享的下一级缓存。
- 主内存。

具体取决于硬件结构和当前一致性状态。

不代表每次缓存失效都必须访问 RAM。

### 6.4 CPU 如何发现其他核心持有同一缓存行？

常见实现涉及：

- Snooping：监听缓存一致性事务。
- Directory：通过目录记录或追踪缓存副本的持有情况。

缓存一致性机制根据缓存行对应的内存地址进行协调。

**不是把两个 CPU 的全部 Cache Line 逐个比较，也不要求缓存槽位位置一致。**

另外，MESI 负责的是硬件层面的缓存一致性，不等于 Java 内存模型中的所有可见性、原子性和有序性保证。

## 七、什么是伪共享（False Sharing）？

伪共享是指：

**多个线程修改不同变量，但这些变量位于同一个缓存行中，导致缓存行不断失效和重新获取，引发性能下降。**

### 7.1 Java 示例

```
class Counter {
    volatile long a = 0;
    volatile long b = 0;
}
```

假设 `a` 和 `b` 在同一个缓存行中：

```
Cache Line（64B）
┌────────┬────────┬────────────────┐
│ a (8B) │ b (8B) │ 其他数据 (48B) │
└────────┴────────┴────────────────┘
```

两个线程分别修改：

```
Counter counter = new Counter();

// 线程 A
new Thread(() -> {
    for (int i = 0; i < 100_000_000; i++) {
        counter.a++;
    }
}).start();

// 线程 B
new Thread(() -> {
    for (int i = 0; i < 100_000_000; i++) {
        counter.b++;
    }
}).start();
```

虽然线程 A 和 B 没有修改同一个变量，但可能发生：

```
线程 A 修改 a
      │
      ▼
CPU 1 获得缓存行写权限
      │
      ▼
CPU 2 对应缓存行失效
      │
      ▼
线程 B 修改 b
      │
      ▼
CPU 2 重新获得缓存行写权限
      │
      ▼
CPU 1 对应缓存行失效
      │
      ▼
重复发生……
```

这种现象称为：

**Cache Line Ping-Pong（缓存行乒乓）**

### 7.2 为什么叫伪共享？

因为：

- 线程 A 使用 `a`。
- 线程 B 使用 `b`。
- 两个变量逻辑上互不相关。
- 但是 CPU 的缓存一致性以缓存行为粒度工作。

因此发生了不必要的缓存一致性竞争。

### 7.3 伪共享会造成什么后果？

主要包括：

1. 缓存行频繁失效。
2. 缓存一致性通信增加。
3. 缓存行所有权频繁转移。
4. 多线程吞吐量下降。
5. CPU 核心可能因等待数据而停顿。

伪共享本身是性能问题，不代表一定存在数据竞争或线程安全错误。

### 7.4 volatile 能解决伪共享吗？

不能。

`volatile` 主要提供 Java 内存模型规定的可见性和有序性保证。

它无法改变两个变量在物理内存中的位置。

甚至在高频更新场景下，`volatile` 字段之间的伪共享可能更加明显。

另外：

```
volatile int count;
count++;
```

`count++` 依然不是原子操作。

**伪共享和原子性是两个不同的问题。**

## 八、Java 如何解决伪共享？

核心思想：

**让不同线程频繁修改的热点变量位于不同缓存行。**

### 8.1 Padding（缓存行填充）

例如：

```
class Counter {
    volatile long a;

    long p1, p2, p3, p4;
    long p5, p6, p7;

    volatile long b;
}
```

通过填充字段，尝试增加 `a` 和 `b` 的物理距离。

但 Java 对象的实际字段布局可能被 JVM 调整，因此不能保证一定消除伪共享。

### 8.2 @Contended

HotSpot JVM 提供了 `@Contended`，用于帮助隔离容易产生伪共享的字段或对象。

它属于 JDK 内部 API。

普通应用使用时可能需要额外的模块导出和 JVM 参数，例如 `-XX:-RestrictContended`，实际支持情况取决于 JDK。

### 8.3 LongAdder

`LongAdder` 是 Java 高并发计数场景的重要优化。

普通的 `AtomicLong` 通常需要多个线程竞争同一个原子变量。

`LongAdder` 则通过多个 Cell 分散更新压力，最终求和。

```
AtomicLong：

线程 1 ─┐
线程 2 ─┼──► 同一个 value
线程 3 ─┘


LongAdder：

线程 1 ───► Cell 0
线程 2 ───► Cell 1
线程 3 ───► Cell 2
                 │
                 ▼
             sum() 求和
```

其 Cell 还采用了缓存行隔离相关的优化。

需要注意：LongAdder 的主要收益还来自分散原子更新竞争，不只是解决伪共享。

## 九、CPU Cache 满了怎么办？

CPU Cache 容量有限。

新数据需要进入缓存，而目标缓存组没有可用位置时，CPU 会执行缓存替换（Cache Replacement）。

例如：

```
替换前：

Cache Set
┌───┬───┬───┬───┐
│ A │ B │ C │ D │
└───┴───┴───┴───┘

需要加载 E
       │
       ▼
选择 C 作为被替换缓存行
       │
       ▼

替换后：

┌───┬───┬───┬───┐
│ A │ B │ E │ D │
└───┴───┴───┴───┘
```

这里涉及两个问题：

**第一：淘汰哪个缓存行？**

由缓存替换策略决定。

**第二：选中的缓存行怎么淘汰？**

由缓存行状态和缓存写策略决定。

这两个概念必须区分。

### 9.1 不一定要整个 Cache 满了才会替换

对于组相联缓存：

- 某个地址只能映射到特定 Cache Set。
- 即使其他 Set 还有空间，如果目标 Set 的 Way 全部占满，仍然可能发生缓存替换。

这属于缓存映射结构带来的限制。

## 十、缓存替换算法

缓存替换策略负责决定：

**应该淘汰哪个缓存行？**

### 10.1 LRU（最近最少使用）

LRU 会优先淘汰最久没有被访问的缓存行。

例如：

```
缓存中有 A、B、C、D

最近访问顺序：

A → B → C → A → D

现在需要加载 E
```

其中 B 是最久未被使用的缓存行，因此在真正 LRU 策略下会被优先淘汰。

优点：

- 符合时间局部性原理。
- 容易理解。

缺点：

- 精确维护访问顺序存在硬件开销。
- 相联度越高，实现复杂度可能越高。

### 10.2 Pseudo-LRU（近似 LRU）

Pseudo-LRU 不精确维护完整访问顺序，而是通过较少的状态近似选择淘汰对象。

优点：

- 硬件开销较低。
- 适合部分硬件缓存设计。

缺点：

- 选中的缓存行不一定是真正最久未使用的。

### 10.3 Random（随机替换）

随机选择一个可替换缓存行。

实现简单，但不能保证每次都选中合适的数据。

### 10.4 对比

| 算法       | 原理                   | 特点                     |
| ---------- | ---------------------- | ------------------------ |
| LRU        | 淘汰最近最少使用的数据 | 访问顺序跟踪开销较高     |
| Pseudo-LRU | 近似判断最近使用情况   | 较低硬件开销             |
| Random     | 随机选择               | 简单，但可能淘汰热点数据 |

实际 CPU 可能采用更复杂的策略，不能认为现代 CPU 统一使用 LRU。

## 十一、Clean 和 Dirty 缓存行

缓存行被选中淘汰后，CPU 需要判断它是否存在尚未写回的修改。

### 11.1 Clean（干净缓存行）

假设：

```
RAM：
a = 100

CPU Cache：
a = 100
```

CPU 读取数据后，没有修改它。

那么在写回缓存的简化模型中：

```
Cache Line = Clean
```

被淘汰时可以直接丢弃缓存中的副本。

原因是下一级存储体系中已经有有效数据，不需要重复写回。

以后再次访问，可以重新加载。

**注意：Clean 不严格等于主内存 RAM 一定保存着全系统最新的数据。**

在多级缓存及一致性协议下，最新数据可能存在于其他缓存层级或其他核心中。

### 11.2 Dirty（脏缓存行）

假设：

```
原始数据：

RAM：
a = 100

CPU Cache：
a = 100
```

CPU 修改：

```
a = 200;
```

采用 Write-Back 策略时，可能变成：

```
RAM：
a = 100

CPU Cache：
a = 200（Dirty）
```

此时 CPU Cache 保存了尚未写回的修改。

如果直接丢弃，就可能丢失 `a = 200` 的更新。

因此，淘汰前必须确保这些修改得到保留。

通常需要将数据写回下一级存储，或者交给写回缓冲区等机制处理。

### 11.3 对比

| 状态    | 是否存在尚未写回的修改 | 淘汰操作                     |
| ------- | ---------------------- | ---------------------------- |
| Clean   | 否                     | 可以直接丢弃                 |
| Dirty   | 是                     | 必须先保留修改，通常需要写回 |
| Invalid | 当前副本无效           | 可以直接复用槽位             |

Clean/Dirty 是描述写回需求的概念；MESI 则是描述缓存一致性状态的协议，两者相关但不能简单视为同一套分类。

## 十二、Write-Back 和 Write-Through

它们是缓存写策略，不是缓存替换算法。

### 12.1 Write-Back（写回）

CPU 修改数据时，先更新 Cache，不要求每次都立即写入下一级存储。

例如：

```
CPU 修改 a=200
      │
      ▼
L1 Cache 更新为 200
      │
      ▼
缓存行标记 Dirty
      │
      ▼
之后在淘汰等时机写回
```

优点：

- 减少重复写入。
- 降低下一级缓存或内存的写流量。
- 适合频繁修改的数据。

缺点：

- 需要管理脏缓存行。
- 需要协调不同缓存层级之间的数据一致性。

### 12.2 Write-Through（写直达）

CPU 修改数据时，既更新当前 Cache，也将写操作传播到下一级存储。

```
CPU 修改 a=200
      │
      ├──► 更新当前 Cache
      │
      └──► 向下一级传播写入
```

优点：

- 当前缓存层不需要依赖后续淘汰来写回这些修改。
- 写入关系相对直接。

缺点：

- 下一级写流量可能更大。
- 连续多次修改同一个数据时，可能产生较多写操作。

写操作不一定同步阻塞 CPU；硬件可能使用写缓冲。

### 12.3 写策略对比

| 对比维度           | Write-Back         | Write-Through                    |
| ------------------ | ------------------ | -------------------------------- |
| 修改时             | 优先修改当前 Cache | 同时向下一级传播                 |
| 是否可能产生 Dirty | 是                 | 本层通常不因写入而产生待写回脏行 |
| 淘汰时             | 脏行需要处理写回   | 通常不需要再写回本层修改         |
| 写流量             | 通常较少           | 通常较多                         |
| 复杂度             | 相对较高           | 相对较低                         |

注意：Write-Through 也不意味着每次写操作都直接写入 RAM，它可能只是传播到下一级缓存。

## 十四、Cache Miss、Eviction、Invalidation 的区别

这是比较容易混淆的三个概念。

### 14.1 Cache Miss（缓存未命中）

CPU 访问的数据不在当前有效缓存中。

常见原因：

- 第一次访问某个内存块。
- 原有缓存行已被淘汰。
- 发生缓存映射冲突。
- 缓存一致性协议使缓存行失效。

### 14.2 Cache Eviction（缓存淘汰）

为了腾出缓存位置，将已有缓存行替换出去。

通常涉及缓存替换策略。

### 14.3 Cache Invalidation（缓存失效）

某个缓存行被标记为 Invalid，不再允许直接使用。

例如：

```
CPU 1 和 CPU 2 都缓存 A

CPU 1 修改 A
      │
      ▼
CPU 2 对应的缓存行失效
```

这种情况不意味着 CPU 2 的缓存容量已满。

### 14.4 对比总结

| 概念               | 主要含义               | 典型触发原因             |
| ------------------ | ---------------------- | ------------------------ |
| Cache Miss         | 没有命中有效数据       | 数据不存在、被替换或失效 |
| Cache Eviction     | 淘汰已有数据           | 需要复用缓存槽位         |
| Cache Invalidation | 将副本标记为无效       | 一致性协议等机制         |
| Cache Write-Back   | 将修改后的数据向下写回 | 脏行淘汰等情况           |

注意：Cache Miss 不一定导致 Eviction。

如果目标 Cache Set 还有无效或空闲槽位，可能直接使用该位置。

## 十五、伪共享与缓存容量不足的区别

| 对比             | 伪共享                             | 缓存容量或冲突问题         |
| ---------------- | ---------------------------------- | -------------------------- |
| 根本原因         | 不同线程修改同一缓存行中的不同变量 | 缓存容量有限或地址映射冲突 |
| 关键机制         | 缓存一致性                         | 缓存映射及替换             |
| 是否必须多线程   | 典型场景是多个核心并发访问         | 不需要                     |
| 是否必须修改变量 | 典型伪共享需要写入                 | 不需要                     |
| 解决方案         | 缓存行填充、隔离热点数据           | 改善局部性、优化数据布局   |
| 主要影响         | 一致性通信和等待增加               | 缓存未命中增加             |

两者都可能降低 CPU 性能，但产生原因不同。

## 十六、与 MySQL Buffer Pool 的联系

CPU Cache 与 MySQL InnoDB Buffer Pool 都使用了缓存思想。

共同点：

- 缓存热点数据。
- 利用局部性提高访问效率。
- 空间不足时需要替换。
- 对修改过的数据需要采取相应的写回策略。

例如：

| CPU Cache        | MySQL Buffer Pool      |
| ---------------- | ---------------------- |
| Cache Line       | 数据页 Page            |
| 缓存替换策略     | LRU 变体等页面管理策略 |
| Dirty Cache Line | Dirty Page             |
| 写回下一级存储   | 脏页刷盘               |
| 缓存未命中       | Buffer Pool Miss       |

不过两者存在重要区别：

**CPU Cache 的写回主要涉及硬件缓存层级和内存一致性；InnoDB Buffer Pool 还需要结合 redo log、WAL 和刷盘机制保证崩溃恢复与持久性。**

因此不能直接将 CPU 缓存一致性协议等同于数据库事务机制。

## 十七、Java 后端面试高频问题

### Q1：什么是 CPU Cache Line？

Cache Line 是 CPU 缓存管理数据的基本粒度。现代主流 x86 CPU 通常采用 64B 缓存行。

### Q2：CPU Cache 和 RAM 一一对应吗？

不对应。Cache 使用映射规则与 Tag 标识所缓存的内存块，一个 Cache 槽位在不同时刻可以存储不同内存块的数据。

### Q3：为什么两个 CPU 核心会保存相同的缓存行？

因为多核心共享物理内存，但各自拥有私有缓存。当两个核心访问同一内存块时，可以分别缓存该内存块的副本。

### Q4：不同 CPU 的缓存行位置必须相同吗？

不需要。缓存一致性依据的是它们对应的物理内存块，而不是缓存槽位的位置。

### Q5：什么是 MESI？

MESI 是缓存一致性协议，通过 Modified、Exclusive、Shared、Invalid 四种状态管理缓存副本，协调多核心读写。

### Q6：什么是伪共享？

不同线程修改不同变量，但变量位于同一缓存行，导致缓存行反复失效和所有权转移，引发性能下降。

### Q7：伪共享怎么解决？

通过缓存行填充、`@Contended`、合理的数据布局等方法，将高频修改的变量隔离到不同缓存行。高并发计数还可以考虑 LongAdder。

### Q8：CPU Cache 满了怎么办？

当目标缓存组没有可用槽位时，缓存替换策略会选择一个 Victim Cache Line，并根据其状态处理丢弃或写回，再装入新数据。

### Q9：LRU 和 Write-Back 有什么区别？

- LRU：缓存替换策略，决定淘汰谁。
- Write-Back：缓存写策略，决定修改的数据如何向下写回。

### Q10：Clean 为什么可以直接丢弃？

因为 Clean 缓存行没有需要由当前缓存层写回的修改，数据已经由下一级存储或一致性机制保证，因此可以直接释放当前副本。

### Q11：Dirty 为什么不能直接丢弃？

因为它包含尚未写回的修改。直接丢弃可能造成数据丢失，需要先确保更新得到保留。

### Q12：缓存未命中一定会淘汰数据吗？

不一定。如果目标 Cache Set 有可用位置，可以直接装入数据；只有没有可用位置时才需要替换已有缓存行。

## 十九、最终记忆要点

**1. Cache Line**

CPU 缓存以缓存行为粒度管理数据，常见大小为 64B。

**2. 缓存映射**

CPU Cache 和 RAM 不是一一对应的，通过 Index、Tag、Offset 定位数据。

**3. 缓存一致性**

不同 CPU 核心可以缓存同一个物理内存块，由 MESI 等协议协调副本。

**4. 伪共享**

不同线程写入同一缓存行的不同变量，会造成不必要的缓存一致性竞争。

**5. 缓存替换**

缓存替换策略决定淘汰哪个缓存行，例如 LRU、Pseudo-LRU。

**6. Clean / Dirty**

干净缓存行可直接淘汰；脏缓存行必须先确保尚未写回的修改得到保留。

**7. Write-Back / Write-Through**

这是缓存写策略，不是缓存替换策略。

**8. 三个容易混淆的概念**

- Cache Miss：数据未命中。
- Cache Eviction：数据被淘汰。
- Cache Invalidation：缓存副本失效。

**面试核心总结：**

CPU 通过多级缓存和缓存行提高数据访问效率，使用地址映射机制管理有限缓存空间，使用 MESI 等协议协调多核心缓存副本。当多个核心频繁修改同一缓存行中的不同变量时，可能产生伪共享。缓存需要替换时，由替换策略选择被淘汰行，再根据写策略和缓存行状态决定是否写回。
