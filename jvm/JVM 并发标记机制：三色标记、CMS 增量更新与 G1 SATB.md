# JVM 并发标记机制：三色标记、CMS 增量更新与 G1 SATB

## 一、核心概念

JVM 使用可达性分析算法（Reachability Analysis）判断对象是否存活。

从 GC Roots 出发，沿对象引用关系遍历：

- **可达对象**：被认为是存活对象，需要保留。
- **不可达对象**：可以被垃圾收集器回收。

CMS 和 G1 都支持并发标记，即 GC 线程与业务线程（Mutator）可以同时执行。

但并发标记存在一个问题：

**GC 正在遍历对象引用关系时，业务线程可能修改这些引用，导致标记结果与实际引用关系不一致。**

需要重点解决两个问题：

1. 漏标：存活对象没有被正确标记，可能被误回收。
2. 多标：已经死亡的对象仍被标记为存活，本轮不能回收，形成浮动垃圾。

垃圾收集器必须避免漏标，但可以容忍一定程度的多标。

## 二、三色标记算法

三色标记（Tri-color Marking）是理解并发标记的基础。

### 1. 三种颜色

| 颜色 | 含义                                   | 状态                     |
| ---- | -------------------------------------- | ------------------------ |
| 白色 | 尚未被 GC 扫描或发现                   | 可能是垃圾               |
| 灰色 | 已被发现，但引用的其他对象还没扫描完成 | 等待继续扫描             |
| 黑色 | 对象及其引用关系已经扫描完成           | 本轮标记处理中已完成扫描 |

注意：

**黑色表示已经完成扫描，并不代表对象永远存活。**

### 2. 标记流程

假设引用关系：

```
GC Roots
    |
    v
    A ----> B ----> C

    D（无引用）
```

标记过程：

第一步：初始状态

```
A：白色
B：白色
C：白色
D：白色
```

第二步：从 GC Roots 开始扫描

```
A：灰色
B：白色
C：白色
D：白色
```

第三步：扫描 A

```
A：黑色
B：灰色
C：白色
D：白色
```

第四步：扫描 B

```
A：黑色
B：黑色
C：灰色
D：白色
```

第五步：扫描 C

```
A：黑色
B：黑色
C：黑色
D：白色
```

最终结果：

- A、B、C 被标记为存活。
- D 没有被标记，可以回收。

注意：最终是否回收以及如何回收，还取决于收集器和回收阶段。

## 三、为什么并发标记可能发生漏标？

在并发标记期间，GC 线程和业务线程同时运行。

假设原始引用关系：

```
GC Roots
    |
    v
    A ------> B ------> C
```

GC 已扫描完 A，还未扫描 B。

此时：

- A：黑色
- B：灰色
- C：白色

业务线程执行以下操作：

```
A.ref = C;     // 新增 A → C
B.ref = null;  // 删除 B → C
```

引用关系变成：

```
GC Roots
    |
    v
    A ------> B
    |
    v
    C
```

问题在于：

1. A 已经是黑色，GC 不会按原来的遍历流程再次扫描 A。
2. B 已经删除指向 C 的引用。
3. C 仍然是白色。
4. C 实际仍可从 GC Roots 到达。
5. 如果 GC 没有额外处理引用变化，C 就可能被错误回收。

这就是**漏标问题**。

### 漏标的两个关键条件

从三色标记角度看，典型漏标需要同时满足：

1. 黑色对象新增对白色对象的引用。
2. 灰色对象删除了通向该白色对象的原有引用路径，使该对象无法再通过灰色对象被发现。

这两个条件同时出现时，就可能产生漏标。

因此，可以通过破坏其中任意一个条件来保证正确性。

- CMS 增量更新：主要破坏第一个条件。
- G1 SATB：主要破坏第二个条件。

这是两种机制最关键的区别。

## 四、写屏障（Write Barrier）

### 1. 什么是写屏障？

写屏障是 JVM 在对象引用写入操作附近插入的辅助逻辑。

例如：

```
A.ref = C;
```

业务层面只是修改引用，但 JVM 可以在引用写入前后执行额外操作，用于记录引用变化。

写屏障可以应用于：

- 并发标记
- 代际引用维护
- 卡表（Card Table）
- 记忆集（Remembered Set）

**写屏障不等于直接把对象标记成存活。**

它通常用于记录信息，供垃圾收集器后续处理。

### 2. 写前屏障和写后屏障

写前屏障（Pre-write Barrier）：

```
Object old = A.ref;

// 写前屏障：处理旧引用 old
A.ref = C;
```

写后屏障（Post-write Barrier）：

```
A.ref = C;

// 写后屏障：记录相关引用更新
```

这里是原理示意，不是 HotSpot 源码。

需要注意：

- SATB 通常使用写前屏障记录旧引用。
- 增量更新通常借助写屏障记录引用更新及受影响对象。
- 写屏障也可能用于其他用途，不应把所有写后屏障都理解成 CMS 的增量更新。

## 五、CMS：增量更新（Incremental Update）

### 1. CMS 是什么？

CMS 全称：

**Concurrent Mark Sweep**

即并发标记清除垃圾收集器。

主要特点：

- 支持 GC 线程与业务线程并发执行。
- 以标记-清除算法为主。
- 目标是缩短垃圾回收停顿时间。
- 容易产生内存碎片。
- JDK 9 被标记为废弃，JDK 14 正式移除。

CMS 主要负责老年代垃圾回收。

### 2. 增量更新原理

CMS 使用增量更新（Incremental Update）处理并发引用变化。

核心思想：

**黑色对象如果新增了引用，需要记录受影响的引用关系，避免因为已经扫描过黑色对象而漏掉新引用的对象。**

例如：

```
原始：

GC Roots
    |
    v
    A（黑色）

    C（白色）
```

业务线程执行：

```
A.ref = C;
```

修改后：

```
GC Roots
    |
    v
    A（黑色）
    |
    v
    C（白色）
```

问题：

A 已经扫描过，GC 原本不会再次扫描它。

解决：

1. 写屏障记录相关引用更新。
2. GC 后续处理这些更新记录。
3. 在重新标记阶段处理可能遗漏的引用。
4. 使 C 得到正确标记，避免误回收。

CMS 的典型实现会记录需要重新检查的对象或内存区域，并不要求每次写入都立即完整扫描目标对象。

### 3. 增量更新的优势

**优势一：不必维护完整的初始存活快照**

已经删除的旧引用，不需要仅仅为了维护初始快照而全部保存。

**优势二：可以避免漏标当前仍可达的对象**

通过处理新增引用带来的变化，确保之前扫描过的对象不会隐藏新的存活路径。

### 4. 增量更新的缺点

**缺点一：可能增加重新标记工作量**

例如：

```
A.ref = C;
A.ref = D;
A.ref = E;
```

如果 A 已经扫描完，引用频繁变化可能产生需要处理的更新记录。

重新标记阶段可能需要重新扫描相关对象。

**缺点二：重新标记停顿可能增加**

CMS 的重新标记阶段需要暂停业务线程（STW）。

如果并发标记期间记录了大量引用变化，可能增加重新标记的负担。

但具体停顿时间还取决于实现、对象图、修改频率等因素。

## 六、G1：SATB（Snapshot At The Beginning）

### 1. G1 是什么？

G1 全称：

**Garbage First Garbage Collector**

G1 是一种面向整个堆、以 Region 为基础进行垃圾回收的收集器。

主要特点：

- 将堆划分为多个 Region。
- 支持并发标记。
- 根据 Region 的回收收益选择回收集合。
- 通过对象复制转移减少内存碎片。
- 以可预测的停顿时间为重要设计目标。
- 在现代 HotSpot JVM 中广泛使用。

G1 使用 SATB 机制支持并发标记。

### 2. SATB 的核心思想

SATB 全称：

Snapshot At The Beginning

中文一般称为**原始快照**。

核心思想：

**以标记开始时的对象存活状态为基础，即使之后删除引用，也要保证原本存活的对象不会因并发修改而漏标。**

注意：

SATB 是逻辑上的快照，不会在标记开始时立即复制整个堆，也不是一开始就完成全部对象标记。

### 3. 为什么要记录旧引用？

假设：

```
GC Roots
    |
    v
    A ------> C
```

C 原本存活。

GC 正在进行并发标记，还没有扫描到 C。

此时业务线程执行：

```
A.ref = null;
```

引用变成：

```
GC Roots
    |
    v
    A

    C（已经不可达）
```

如果完全不记录原来的引用，C 就可能从标记过程的视野中消失。

SATB 的处理方式：

```
Object old = A.ref;  // old = C

// SATB 写前屏障记录旧引用 C

A.ref = null;
```

后续 GC 处理记录中的 C。

这样即使 C 当前已经死亡，本轮仍可能将其作为存活对象保留。

### 4. SATB 的优势

**优势一：减少新增引用造成的重复扫描需求**

SATB 以标记开始时的逻辑快照为依据，通常不需要因为新增引用而重新扫描所有已经处理过的黑色对象。

**优势二：有利于控制重新标记工作量**

GC 可以在并发阶段处理 SATB 队列中的引用，最终重新标记阶段处理剩余工作。

这有助于 G1 控制停顿时间。

但并不意味着 SATB 的重新标记一定比增量更新更快。

### 5. SATB 的缺点

主要缺点是：

**可能产生较多浮动垃圾。**

例如：

```
A.ref = C;

// 并发标记期间
A.ref = null;
```

虽然 C 已经没有引用，但是：

- C 在标记开始时存活。
- SATB 记录了旧引用 C。
- C 可能在本轮继续被保留。
- 后续 GC 才可能回收 C。

因此，SATB 在安全性和内存回收及时性之间进行了权衡。

## 七、浮动垃圾（Floating Garbage）

### 1. 什么是浮动垃圾？

**在并发标记过程中已经变成垃圾，但因为标记结果或快照语义，本轮 GC 仍然保留的对象。**

例如：

```
Object C = new Object();
A.ref = C;

// 标记开始后
A.ref = null;
```

如果 C 在本轮被认定需要保留，就可能形成浮动垃圾。

### 2. 浮动垃圾有什么影响？

- 本轮不能回收这部分内存。
- 增加堆内存占用。
- 可能增加后续回收压力。

但浮动垃圾并不是内存泄漏。

| 对比               | 浮动垃圾                   | 内存泄漏             |
| ------------------ | -------------------------- | -------------------- |
| 是否仍被保留       | 是                         | 是                   |
| 形成原因           | 并发标记期间的对象状态变化 | 不必要的引用长期存在 |
| 下一轮 GC 能否回收 | 如果不可达，通常可以       | 仍然可达时无法回收   |
| 是否正常           | 是                         | 通常属于程序设计问题 |

CMS 也可能产生浮动垃圾。

**浮动垃圾并不是 G1 独有的问题。**

## 八、初始标记、并发标记、重新标记的关系

以 CMS 的典型标记流程为例：

### 1. 初始标记（Initial Mark）

- 暂停业务线程（STW）。
- 标记与 GC Roots 直接关联的对象等初始对象。
- 不会立即完成整个对象图的扫描。

### 2. 并发标记（Concurrent Mark）

- GC 线程与业务线程同时运行。
- 继续遍历对象引用关系。
- 业务线程可以创建对象、修改引用、删除引用。

因此需要写屏障等机制维护标记正确性。

### 3. 重新标记（Remark）

- 暂停业务线程（STW）。
- 处理并发期间产生的引用变化及剩余标记工作。
- 保证最终标记结果不会错误遗漏仍需保留的对象。

重新标记不是简单地重新扫描整个堆。

### 4. 并发清除（Concurrent Sweep）

CMS 会清除确定可回收的对象。

CMS 的典型流程：

```
初始标记（STW）
       ↓
并发标记
       ↓
重新标记（STW）
       ↓
并发清除
       ↓
并发重置
```

G1 则不同。

G1 的并发标记主要用于获取存活对象信息和 Region 回收价值，后续可通过 Mixed GC 等回收阶段转移对象、回收选中的 Region。

所以不能把 G1 理解为「重新标记完成后，直接清除所有白色对象」。

## 九、CMS 增量更新与 G1 SATB 对比

| 比较维度       | CMS 增量更新                   | G1 SATB                        |
| -------------- | ------------------------------ | ------------------------------ |
| 英文名称       | Incremental Update             | Snapshot At The Beginning      |
| 核心思想       | 追踪引用更新                   | 维护初始逻辑快照               |
| 主要关注       | 新增引用                       | 删除或覆盖的旧引用             |
| 写屏障典型用途 | 记录修改后的扫描需求           | 记录修改前旧引用               |
| 破坏的漏标条件 | 黑色对象新增白色引用后无人处理 | 灰色对象失去旧引用路径         |
| 重新标记负担   | 可能重新扫描受影响对象         | 处理剩余 SATB 记录等           |
| 浮动垃圾       | 可能产生                       | 可能因快照语义保留更多对象     |
| 主要优势       | 不必为了快照保留所有旧引用     | 减少对已扫描对象的重复扫描需求 |
| 主要代价       | 重新扫描可能增加停顿           | 内存回收可能不够及时           |

### 两种方式的本质区别

CMS：

> 对象的引用发生新增时，需要防止已经扫描过的对象隐藏新的存活路径。

G1：

> 对象的旧引用被删除时，要防止标记开始时存活的对象从快照中消失。

两者都允许多标，但必须避免危险的漏标。

### 哪种更好？

不能单纯认为 SATB 一定比增量更新先进。

两者的主要取舍涉及：

- 写屏障开销
- 引用变化记录开销
- 并发标记工作量
- 重新标记停顿
- 浮动垃圾数量

实际回收器性能还受堆布局、对象复制、并发线程、内存碎片和回收策略等因素影响。

G1 相比 CMS 的优势，也不能全部归功于 SATB。

## 十、容易混淆的问题

### Q1：是不是 GC 最后把所有没标记的对象都清除？

对于简单的标记-清除算法，可以这样理解。

但对 G1 等采用 Region 和对象复制机制的收集器，不能直接套用「全堆统一清除所有白色对象」的说法。

### Q2：重新标记是不是再扫描所有存活对象？

不是。

重新标记主要处理并发标记尚未完成的工作和引用变化带来的标记修正，不必完整重扫整个堆。

### Q3：写屏障是否直接把新对象标记为存活？

通常不是。

写屏障主要记录引用变化或相关对象信息，再由 GC 线程后续处理。

### Q4：G1 是否只保留标记开始时存活的对象？

不是。

G1 还必须正确处理并发标记期间新分配的对象等情况。

SATB 只描述并发标记的逻辑快照机制，不能代表 G1 全部的对象生命周期管理。

### Q5：删除旧引用为什么不会马上回收？

因为 SATB 需要保证初始逻辑快照中的存活对象不因并发修改而漏标。

已经变成垃圾的对象可能保留至后续回收。

### Q6：SATB 是否保证零漏标？

SATB 必须配合相应的写屏障、队列处理、新分配对象管理等机制，才能实现安全的并发标记。

单独记录旧引用并不等于完整的垃圾收集算法。

### Q7：CMS 和 G1 都是标记-清除算法吗？

不是。

- CMS：主要采用标记-清除算法，容易产生碎片。
- G1：并发标记配合 Region 选择，通过复制、转移存活对象来回收空间，减少碎片。

## 十一、面试回答模板

### 问：为什么并发标记会发生漏标？

因为 GC 线程与业务线程并发执行，业务线程可能修改对象引用关系。

如果黑色对象新增了对白色对象的引用，同时灰色对象删除了通向该白色对象的引用路径，那么白色对象可能无法被 GC 正确发现，产生漏标。

### 问：CMS 如何解决漏标？

CMS 使用增量更新机制。

当已扫描对象的引用关系发生变化时，通过写屏障记录相关更新，后续重新扫描受影响对象，避免遗漏仍然存活的对象。

### 问：G1 如何解决漏标？

G1 使用 SATB 机制。

在引用删除或覆盖前，通过写前屏障记录旧引用，维护标记开始时的逻辑存活快照，避免对象因引用被删除而从标记过程中消失。

### 问：增量更新与 SATB 有什么优缺点？

增量更新主要处理新增引用，不必为维护初始快照而保存所有旧引用，但可能产生额外的重新扫描工作。

SATB 主要记录旧引用，有助于减少新增引用带来的重复扫描需求，但可能保留更多浮动垃圾。

两者都是为了保证并发标记的正确性，具体性能取决于实际工作负载和收集器实现。

## 十二、最终记忆总结

**1. 三色标记**

- 白色：尚未扫描或发现。
- 灰色：已发现，引用尚未扫描完成。
- 黑色：已完成扫描。

**2. 漏标产生条件**

- 黑色对象新增对白色对象的引用。
- 灰色对象删除通向该白色对象的引用路径。

**3. CMS 增量更新**

- 关注新增引用。
- 通过写屏障记录受影响对象。
- 可能需要重新扫描相关对象。

**4. G1 SATB**

- 关注被覆盖的旧引用。
- 通过写前屏障记录旧引用。
- 维护初始逻辑快照。
- 可能保留更多浮动垃圾。

**5. 正确性原则**

- 漏标：不能接受，可能误回收存活对象。
- 多标：可以接受，代价是本轮少回收部分垃圾。

**一句话概括：CMS 通过追踪新增引用防止漏标；G1 通过保留旧引用维护初始快照。两者解决的是同一个并发标记问题，但采用了不同的正确性策略。**
