# JVM 垃圾回收、STW、安全点与 G1 完整面试笔记

> 适用范围：Java 后端面试，以 HotSpot JVM、G1 垃圾回收器为主要例子。
>
> 核心知识链路：**可达性分析 → 存活对象标记 → STW → Safepoint → OopMap → 对象转移 → 引用更新 → 恢复应用线程**

## 一、先理解 GC 到底在干什么

### 1. GC 的核心目的

GC（Garbage Collection）用于自动管理 JVM 内存，回收不再使用的对象占据的内存空间。

GC 需要完成两个核心任务：

1. **判断对象是否存活**：通常通过 GC Roots 和可达性分析判断。
2. **回收垃圾对象占用的内存**：根据垃圾回收算法，可能涉及清除、复制、整理等操作。

注意：**GC 不只是删除垃圾对象，还可能移动存活对象，并更新指向这些对象的引用。**

### 2. 如何判断对象是否存活？

HotSpot 中常用可达性分析算法。

从 GC Roots 出发，沿对象引用关系进行遍历。

```
GC Roots
   │
   ▼
对象 A
   │
   ▼
对象 B ─────→ 对象 C


对象 D        对象 E
   │
   └────────→ 对象 F
```

假设 D、E、F 无法通过其他路径从 GC Roots 到达。

那么：

- A、B、C：可达对象，需要保留。
- D、E、F：不可达对象，可以作为垃圾回收候选。

常见 GC Roots 包括：

- Java 线程栈中正在使用的对象引用。
- 类的静态字段中持有的对象引用。
- JNI 等本地代码持有的特定引用。
- JVM 内部维护的其他根引用。

**注意：垃圾回收器主要通过标记存活对象，间接识别垃圾对象，而不是逐个寻找要删除的对象。**

## 二、什么是 STW？

### 1. STW 的定义

STW（Stop The World）指 JVM 暂停相关 Java 应用线程的执行，以完成某些需要全局协调的操作。

以垃圾回收为例：

```
正常运行：

线程 A：处理 HTTP 请求
线程 B：查询数据库
线程 C：计算业务数据

             │
             ▼
          发生 STW
             │
             ▼

线程 A：暂停
线程 B：暂停
线程 C：暂停

GC 线程：执行 GC 工作

             │
             ▼
          GC 完成
             │
             ▼

线程 A：继续执行
线程 B：继续执行
线程 C：继续执行
```

**STW 并不是 JVM 整个进程停止，而是相关应用线程停止执行 Java 业务代码，GC 等 JVM 内部线程仍然可以工作。**

### 2. 为什么 GC 需要 STW？

主要有两个原因。

**原因一：需要稳定、准确的对象引用信息。**

GC 需要知道：

- 对象是否可以从 GC Roots 到达。
- 哪些线程栈和寄存器持有对象引用。
- 对象移动之后，哪些引用需要更新。

如果应用线程不断改变这些信息，GC 就需要额外的并发协调机制。

**原因二：有些回收器需要安全地移动存活对象。**

例如 G1 的 Young GC 和 Mixed GC。

```
GC 之前：

线程 A 的 user 引用
       │
       ▼
地址 0x1000 → User 对象（存活）


GC 移动对象：

地址 0x1000 → 原对象位置
地址 0x4000 → User 对象（新位置）
```

如果 GC 移动对象并释放旧内存，而应用线程还在使用旧地址，就可能发生错误。

所以 G1 常规对象转移会在 STW 中完成复制及引用更新。

GC 完成后：

```
线程 A 的 user 引用
       │
       ▼
地址 0x4000 → User 对象
```

这样线程恢复后，就能够正常访问对象。

注意：不是所有垃圾回收器都必须通过 STW 移动对象。ZGC 等低延迟回收器使用了额外的并发转移和引用处理机制。

## 三、G1 垃圾回收器的完整执行流程

### 1. G1 的整体思路

G1（Garbage First）把堆划分成多个 Region。

这些 Region 可以承担 Eden、Survivor、Old 等角色。

G1 根据 Region 的存活情况、回收成本和收益等信息选择回收集合，而不是每次都清理整个老年代。

G1 的一个重要特点：

**大量老年代存活分析可以并发执行，但常规对象转移仍需要 STW。**

### 2. G1 的主要阶段

| 阶段                           | 是否 STW | 核心作用                                       |
| ------------------------------ | -------- | ---------------------------------------------- |
| 初始标记（Initial Mark）       | 是       | 建立标记起点                                   |
| 根区域扫描（Root Region Scan） | 否       | 扫描相关根区域引用                             |
| 并发标记（Concurrent Mark）    | 否       | 大量遍历并标记存活对象                         |
| 重新标记（Remark）             | 是       | 完成剩余标记任务                               |
| 清理（Cleanup）                | 部分 STW | 统计、整理回收候选 Region                      |
| Mixed GC                       | 是       | 转移存活对象，回收选中的老年代 Region 和新生代 |

这里的流程是简化后的 G1 并发标记与混合回收流程。

**不是每次 Young GC 都会触发整个标记周期，也不是 Cleanup 结束就必然立刻执行 Mixed GC。**

### 3. 初始标记（Initial Mark）

初始标记建立本轮并发标记的起点。

G1 通常把初始标记附带在一次 Young GC 的暂停中执行，这次回收可在日志中表现为 `Concurrent Start`。

注意：

初始标记不是扫描整个堆，也不是已经找出了所有存活对象。

### 4. 并发标记（Concurrent Mark）

并发标记是本轮存活分析的主要工作阶段。

例如：

```
GC Roots → A → B → C
                 │
                 └──→ D
```

GC 沿着引用关系不断遍历，标记 A、B、C、D 等存活对象。

并发标记期间：

```
GC 线程：遍历和标记存活对象
Java 线程：继续执行正常业务
```

所以它不需要全程 STW。

但是会出现一个问题：

**应用线程还在运行，可能修改对象引用关系。**

这就引出了 SATB 和 Remark。

### 5. SATB：如何处理并发期间修改的引用？

SATB 全称 Snapshot At The Beginning，意为起始快照。

可以把它理解为：

**以标记周期开始时的逻辑快照为基础，保证本轮需要保留的对象不会因为引用变化而遗漏。**

例如：

```
开始标记时：

GC Roots → A → B → C
```

并发标记过程中，应用线程执行：

```
A.next = null;
```

A 不再引用 B。

但 G1 的 SATB 写屏障会记录必要的旧引用 B，以便 GC 后续处理。

因此 GC 不需要重新扫描整个堆来寻找所有发生变化的位置。

SATB 不是完整复制一份堆快照，而是通过标记状态、写屏障及相关缓冲记录，实现起始快照语义。

### 6. 重新标记（Remark）

**Remark 的目的不是重新扫描整个堆，也不是直接删除垃圾对象。**

它主要用于：

- 处理剩余 SATB 缓冲记录。
- 完成尚未处理的标记工作。
- 完成本轮标记所需的收尾处理。

例如：

```
并发标记：

已扫描：A
还有部分标记工作未完成

应用线程：
删除 A → B

SATB：
记录旧引用 B

             ↓

Remark（STW）：

处理剩余 SATB 记录
必要时继续标记 B、C
完成本轮标记
```

为什么 Remark 需要 STW？

因为暂停相关应用线程后，可以停止本轮标记期间新的应用引用修改干扰，完成剩余标记工作。

**Remark 是并发标记的收尾，不是第二次完整的存活扫描。**

### 7. 已标记对象后来死亡怎么办？

假设：

```
标记开始：

GC Roots → A → B

并发期间：

A.next = null
```

B 现在可能已经不可达。

但按照 SATB 的起始快照语义，本轮仍可能将 B 视为存活对象。

这种已经死亡却仍被本轮 GC 保留下来的垃圾称为：

**浮动垃圾（Floating Garbage）。**

它可能留到后续 GC 再回收。

这并不会造成错误，只是垃圾回收得不够及时。

G1 允许浮动垃圾存在，避免为了得到实时准确的存活集合而反复扫描所有对象。

需要记住：

- 已标记并扫描完成的对象，通常不需要重新判断是否存活。
- 已标记但尚未扫描完成的对象，还需要继续遍历其引用。
- 标记期间死亡的对象可能暂时保留。
- 不允许错误回收仍然需要保留的存活对象。

### 8. 清理（Cleanup）和 Mixed GC

Remark 完成后，G1 已经得到本轮标记所需的存活信息。

随后会统计 Region 的存活情况、整理候选区域并评估回收价值。

Cleanup 包含需要暂停的工作，也存在相关并发整理工作。

如果老年代存在值得回收的 Region，G1 后续可以进入混合回收阶段。

Mixed GC 会回收：

- 新生代 Region。
- 部分选中的老年代 Region。

在 G1 常规 Mixed GC 暂停中，需要：

1. 确定本次回收集合。
2. 复制或转移需要保留的存活对象。
3. 更新必要的对象引用。
4. 回收相应 Region 的内存。
5. 恢复应用线程。

Mixed GC 可能执行多次，不是必须一次回收所有老年代垃圾。

## 四、什么是安全点（Safepoint）？

### 1. 安全点的定义

**安全点是 JVM 能够安全暂停 Java 线程，并准确获取 GC 所需对象引用信息的执行位置。**

安全点不是：

- Java 某一行固定的源代码。
- 某个方法必须执行完毕的位置。
- 对象已经不会被修改的位置。
- 业务执行完成的位置。

它属于 JVM 底层执行机制。

### 2. 为什么不能随便暂停线程？

假设：

```
User user = new User();
user.setAge(20);
System.out.println(user.getAge());
```

运行过程中，`user` 引用可能存放在：

- Java 线程栈。
- CPU 寄存器。
- JIT 优化后的其他表示位置。

GC 必须知道哪里保存的是对象引用。

否则，可能无法准确识别 GC Roots，或者无法正确更新对象移动后的引用。

HotSpot 通过 OopMap 等元数据帮助定位对象引用。

但 JVM 不会为每一条机器指令都保留完整的引用位置映射。

因此需要在特定位置安排安全点。

### 3. OopMap 是什么？

OopMap 可以理解为：

**在特定执行位置，告诉 JVM 哪些寄存器或栈槽保存了对象引用的元数据。**

例如：

```
某个安全点：

寄存器 R1 → 对象 A 的引用
栈槽 S1   → 对象 B 的引用
寄存器 R2 → 普通整数

GC 扫描：

R1：需要处理
S1：需要处理
R2：不是对象引用
```

注意，这只是简化示意。

OopMap 的作用是协助 JVM 准确识别对象引用，而不是直接负责判断对象是否应该被回收。

### 4. 为什么与解释器和 JIT 编译器有关？

Java 程序一般经过以下执行链路：

```
.java 源代码
      │
      ▼
javac
      │
      ▼
.class 字节码
      │
      ▼
JVM
      │
      ├── 解释执行
      │
      └── JIT 编译成机器码执行
```

安全点检查需要落实到实际执行过程。

- **解释器**：通过解释执行过程中的相应机制响应安全点请求。
- **JIT 编译代码**：在生成的机器码中安排安全点检查，例如部分方法调用位置、循环回边等。

所以安全点与解释器、JIT 有关，但程序员通常不需要手动插入安全点。

## 五、什么是安全点检测（Safepoint Poll）？

### 1. 安全点与安全点检测不是一回事

| 概念                      | 含义                         |
| ------------------------- | ---------------------------- |
| Safepoint                 | 可以安全暂停的执行位置       |
| Safepoint Poll            | 检查是否有暂停请求           |
| Safepoint Synchronization | 协调相关线程进入安全状态     |
| STW                       | 应用线程暂停执行的状态或阶段 |

可以这样理解：

**安全点解决在哪里暂停，安全点检测解决现在需不需要暂停。**

### 2. 具体过程

```
线程 C 正常运行
       │
       ▼
执行机器指令
       │
       ▼
到达安全点检查
       │
       ▼
JVM 是否请求 STW？
       │
       ├── 否 → 继续执行
       │
       └── 是
             │
             ▼
       进入安全状态
             │
             ▼
       等待 JVM 恢复
```

安全点检查不会每次都触发 STW。

正常情况下，线程经过安全点检查后继续执行。

只有 JVM 请求了相应暂停，线程才需要作出响应。

### 3. 为什么还要等待线程 C？

假设有三个 Java 线程：

```
             时间 →

线程 A：运行 → 到达安全点 → 暂停 ───────┐
                                       │
线程 B：运行 → 到达安全点 → 暂停 ───────┤
                                       │
线程 C：运行 → 继续运行 → 安全点 → 暂停─┘
                                       │
                                       ▼
                                全部线程就绪
                                       │
                                       ▼
                                  开始 STW GC
```

线程 A、B 已经到达安全点，提前暂停。

线程 C 尚未进入安全状态，所以 JVM 需要等待。

**JVM 等待的不是线程 C 完成整个业务任务，而是等待 C 进入可以安全暂停的状态。**

### 4. 线程 C 什么时候算进入安全状态？

主要有两种常见情况：

**情况一：正在运行 Java 代码。**

线程执行到安全点检查位置，发现 JVM 请求暂停，于是响应请求。

**情况二：线程已经处于 JVM 能够安全协调的状态。**

例如某些阻塞状态或 Native 执行状态。

这些线程不一定需要先执行到下一个 Java 安全点检查；HotSpot 可以根据线程状态进行协调，并在重新进入 Java 执行时处理相关安全点要求。

所以不能简单认为所有线程都必须不断执行到某条 Java 代码才能暂停。

## 六、安全点同步时间与 STW 时间

### 1. 一次暂停过程

假设发生以下事件：

```
0ms              20ms                 50ms
 │                 │                    │
 ▼                 ▼                    ▼
请求 STW       全部线程就绪          GC 完成
 │                 │                    │
 └──── 20ms ──────┘                    │
                   └──── 30ms ────────┘
```

那么：

| 时间     | 含义                             |
| -------- | -------------------------------- |
| 0～20ms  | 安全点同步耗时                   |
| 20～50ms | 全局安全点内执行 GC 等工作的耗时 |
| 0～50ms  | 从发出请求到恢复的总过程约 50ms  |

注意严格区分：

**安全点同步期间，已经暂停的线程会等待，但其他线程可能还在执行 Java 代码。**

所以如果把 STW 严格定义为“所有相关应用线程已经停止的阶段”，它主要对应全部线程就绪之后的时间。

但从业务停顿角度看，安全点同步耗时也可能造成明显延迟。

另外，安全点中的工作不一定全部是纯粹的 GC 计算，还可能包含相关管理和收尾开销。

### 2. STW 时间是 JVM 事先决定的吗？

不是。

一般来说，STW 持续到当前必须暂停应用线程的相关工作完成。

影响暂停时间的因素包括：

- 需要处理的对象和引用数量。
- 存活对象复制量。
- GC 线程数量与处理速度。
- CPU、内存带宽和系统负载。
- JVM 内部协调和收尾开销。

### 3. `MaxGCPauseMillis` 是什么？

例如：

```
-XX:MaxGCPauseMillis=200
```

表示 G1 尽力把 GC 暂停时间控制在约 200ms 的目标附近。

但它不是硬性上限。

JVM 不会因为到达 200ms，就强行中断尚未安全完成的 GC 工作。

G1 会通过预测回收成本、调整回收集合等方式尽量达到暂停目标。

## 七、怎么通过 GC 日志观察？

### 1. 开启 G1 和 GC 日志

JDK 17/21 可以使用：

```
java -XX:+UseG1GC \
     -Xlog:gc*,safepoint*=debug:file=gc.log:time,uptime,level,tags \
     -jar app.jar
```

Windows PowerShell 可以写成一行：

```
java -XX:+UseG1GC '-Xlog:gc*,safepoint*=debug:file=gc.log:time,uptime,level,tags' -jar app.jar
```

### 2. 常见 GC 日志

例如：

```
Pause Young (Concurrent Start)
Concurrent Mark Cycle
Concurrent Mark From Roots
Pause Remark
Pause Cleanup
Pause Young (Prepare Mixed)
Pause Young (Mixed)
```

日志含义：

| 记录                       | 含义                             |
| -------------------------- | -------------------------------- |
| Concurrent Start           | 本次 Young GC 启动了并发标记周期 |
| Concurrent Mark From Roots | 并发标记主要工作                 |
| Pause Remark               | 重新标记 STW                     |
| Pause Cleanup              | 清理暂停 STW                     |
| Prepare Mixed              | 准备混合回收                     |
| Mixed                      | 混合回收 STW                     |

实际日志名称和顺序细节可能随 JDK 版本、GC 状态有所差异，中间还会出现其他阶段。

### 3. 怎么知道并发标记完成？

**不是根据时间判断，而是根据内部标记任务是否满足完成条件。**

GC 工作线程需要完成主要对象遍历，处理相应的标记工作队列，并协调判断是否可以终止当前并发阶段。

并发标记主体完成后，G1 才推进到 Remark 收尾。

可以通过对应阶段的结束日志观察。

### 4. 怎么知道安全点等待是否太久？

查看 Safepoint 日志中的信息，例如：

```
Reaching safepoint: 5000000 ns
At safepoint: 12000000 ns
Total: 17000000 ns
```

含义：

- `Reaching safepoint`：进入全局安全点所需的同步时间。
- `At safepoint`：处于全局安全点的时间。
- `Total`：相关安全点过程总耗时。

上述是示例值，具体日志格式取决于 JDK 版本。

如果 `Reaching safepoint` 很大，应排查为什么线程进入安全状态较慢。

如果 `At safepoint` 很大，则应进一步判断是不是 GC 工作耗时较长。

## 八、不同垃圾回收器与 STW 的关系

| 回收器      | 特点                           | STW 情况                       |
| ----------- | ------------------------------ | ------------------------------ |
| Serial GC   | 单线程执行主要回收工作         | 主要回收过程 STW               |
| Parallel GC | 多线程并行回收                 | 主要回收过程 STW               |
| G1 GC       | Region、并发标记、分批混合回收 | 并发工作与 STW 交替            |
| ZGC         | 并发标记、并发对象转移等       | 主要耗时工作并发，仍有短暂停顿 |
| CMS（历史） | 并发标记清除，易出现碎片等问题 | 初始标记、重新标记等需要 STW   |

需要区分：

**并行（Parallel）**：多个 GC 工作线程可以同时执行垃圾回收。

**并发（Concurrent）**：GC 工作与 Java 应用线程能够在同一时间段推进。

所以：

- 多线程 GC 不代表没有 STW。
- 并发 GC 不代表完全没有 STW。
- 不同 GC 回收器的暂停位置和对象转移机制可能完全不同。

## 九、Java 代码能不能优化 STW？

可以改善 GC 性能和部分暂停问题，但通常无法通过 Java 源代码直接指定安全点位置。

### 1. 减少不必要的对象分配

例如避免在高频路径中无意义地大量创建临时对象。

减少对象分配压力，可以降低部分 GC 的触发频率。

### 2. 控制存活对象数量

避免不必要的大对象长期被集合、静态字段、缓存等持有。

对象存活数量较多时，某些 GC 阶段的标记、复制和引用处理成本可能增加。

### 3. 排查安全点同步延迟

如果 Safepoint 日志显示线程响应缓慢，需要进一步分析：

- JIT 生成代码的安全点检查情况。
- 长时间执行的特殊 Native/JNI 路径。
- 线程状态和 JVM 版本相关问题。

不推荐通过随意插入 `Thread.sleep()`、`Thread.yield()` 等方法来人为优化安全点，这些方法没有可靠的安全点优化保证，还可能增加业务延迟。

### 4. 使用合适的垃圾回收器

需要关注吞吐量的应用，可以评估 Parallel GC。

需要兼顾吞吐量和暂停表现的常见服务端应用，可以考虑 G1。

对尾延迟特别敏感的服务，可以评估 ZGC。

具体选择应结合业务负载、JDK 版本和实测结果。

## 十、面试高频追问

### Q1：为什么需要 STW？

**答：**

因为部分 GC 操作要求稳定的对象引用信息或安全的对象转移过程。例如 G1 在对象转移时需要复制存活对象并更新引用，因此暂停应用线程，避免应用线程同时访问正在被移动的对象。

### Q2：为什么需要安全点？

**答：**

因为 JVM 不能保证在任意机器指令位置都具有准确的对象引用位置映射。安全点提供了可以安全暂停线程、准确识别相关对象引用的位置，方便执行 GC Roots 扫描及其他需要全局协调的操作。

### Q3：安全点检测检测的是什么？

**答：**

主要检测 JVM 当前是否请求了相关暂停。没有暂停请求就继续执行；存在请求时，线程响应并进入安全状态。

### Q4：为什么要等待所有线程进入安全状态？

**答：**

因为需要全局 STW 的操作要求相关应用线程停止执行 Java 代码。只有所有线程处于安全状态，JVM 才能安全执行该类全局操作。

### Q5：G1 为什么需要 Remark？

**答：**

因为并发标记期间应用线程还在修改引用关系。G1 通过 SATB 写屏障记录必要的旧引用，在 Remark 阶段暂停应用线程，处理剩余标记记录并完成本轮标记。

### Q6：Remark 会重新检查所有已标记对象吗？

**答：**

不会。Remark 主要完成剩余的标记工作，不是重新对整个堆进行一次完整扫描。

### Q7：已经标记存活的对象后来死亡怎么办？

**答：**

G1 采用 SATB，允许本轮产生浮动垃圾。对象虽然已经死亡，但仍可能被本轮视为存活，后续 GC 再回收。

### Q8：为什么 G1 并发标记可以不 STW，而 Mixed GC 需要 STW？

**答：**

G1 的并发标记使用 SATB 等机制，可以在应用线程继续运行时完成大量存活对象分析。而 Mixed GC 需要转移存活对象并更新引用，G1 常规采用 STW 完成这些操作。

### Q9：STW 耗时是不是等于 GC 耗时？

**答：**

不能直接画等号。

GC 可能包含并发工作；而业务实际停顿除了 STW GC 工作之外，也可能受到安全点同步时间的影响。

排查时应分别观察 GC 暂停耗时和 Safepoint 同步耗时。

### Q10：设置了 200ms 暂停目标，GC 就不会超过 200ms 吗？

**答：**

不是。`MaxGCPauseMillis` 是 G1 的软目标。G1 尽量通过预测回收成本、调整回收集合等方式达到目标，但不能保证每次暂停都不超过该值。

## 十一、完整面试回答模板（约 1～2 分钟）

如果面试官问：**介绍一下 JVM 的 STW 和安全点，以及 G1 为什么需要它们。**

可以这样回答：

> STW 是 Stop The World，指 JVM 暂停相关 Java 应用线程，以执行某些需要全局协调的操作，例如 G1 的对象转移。
>
> JVM 不能在任意机器指令位置直接暂停线程并进行精确 GC，因为线程的对象引用可能位于栈或寄存器中，而 JVM 需要准确的引用位置信息。
>
> 因此 HotSpot 提供安全点机制，在合适的执行位置通过 OopMap 等元数据记录对象引用的位置，并通过安全点检查协调线程暂停。
>
> 当需要全局 STW 时，JVM 发出安全点请求，相关线程进入安全状态，全部就绪后执行需要暂停的 GC 工作，完成后再恢复应用线程。
>
> 以 G1 为例，它的并发标记阶段可以与应用线程同时运行，使用 SATB 处理引用变化；重新标记阶段需要 STW 来完成剩余标记；而 Young GC 和 Mixed GC 的常规对象转移也需要 STW，以安全复制存活对象并更新引用。
>
> 最后，STW 没有固定持续时间，`MaxGCPauseMillis` 只是暂停目标。实际排查时应该同时观察 GC 日志和 Safepoint 日志，区分 GC 工作耗时与安全点同步耗时。

## 十二、最终速记

| 知识点         | 一句话记忆                         |
| -------------- | ---------------------------------- |
| GC             | 识别存活对象，回收无用内存         |
| GC Roots       | 可达性分析的起点                   |
| 初始标记       | 建立并发标记起点                   |
| 并发标记       | 大量查找存活对象                   |
| SATB           | 记录必要的旧引用，维持起始快照语义 |
| Remark         | 处理剩余标记任务，不是再次扫描全堆 |
| 浮动垃圾       | 已经死亡但本轮仍保留的对象         |
| Cleanup        | 统计、整理回收候选区域             |
| Mixed GC       | 回收新生代及部分老年代 Region      |
| STW            | 暂停应用线程                       |
| Safepoint      | 能安全暂停并获得必要引用信息的位置 |
| Safepoint Poll | 检查是否需要响应暂停请求           |
| OopMap         | 记录特定执行位置的对象引用位置     |
| 安全点同步     | 等相关线程进入安全状态             |
| G1 暂停目标    | 尽量控制停顿，而不是硬性上限       |

### 最后需要真正理解的五句话

1. **GC 标记的主要是存活对象，而不是需要删除的对象。**
2. **Remark 不是第二次全堆标记，而是完成并发阶段剩余的标记工作。**
3. **安全点的目的不是等待业务执行完，而是让 JVM 能准确识别引用并安全暂停线程。**
4. **STW 不只是为了标记，也可能是为了安全地复制存活对象和更新引用。**
5. **不同回收器的实现不同，但可达性分析、引用处理、并发协调和暂停成本是共同的核心问题。**

记住整条链路：

```
GC 需要判断对象是否存活
            ↓
通过 GC Roots 进行可达性分析
            ↓
需要准确知道对象引用的位置
            ↓
安全点 + OopMap 提供所需信息
            ↓
需要全局暂停时发出 STW 请求
            ↓
相关线程进入安全状态
            ↓
GC 执行必须暂停的工作
            ↓
复制或清理对象、更新必要引用
            ↓
恢复 Java 应用线程
```

补充：这是一条用于理解 STW GC 的简化链路，并不意味着每次可达性分析都必须 STW，也不意味着所有回收器都在 STW 中移动对象。
