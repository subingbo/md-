# JVM 内存与垃圾回收（GC）核心笔记

> 一份从「内存参数」到「GC 触发与晋升」再到「线上故障」的完整知识链梳理，适合面试复习与线上排查速查。

---

## 一、先厘清内存参数：堆 vs 栈

最容易混淆的起步问题：`-Xms` 是栈的最大内存吗？——**不是**。它管的是**堆的初始大小**，与栈无关。

| 参数 | 控制区域 | 含义 | 默认值 |
| :--- | :--- | :--- | :--- |
| `-Xms` | 堆 (Heap) | 堆的**初始**大小 (**s**tart) | 物理内存的 1/64 |
| `-Xmx` | 堆 (Heap) | 堆的**最大**大小 (ma**x**) | 物理内存的 1/4 |
| `-Xss` | 栈 (Stack) | **每个线程**的栈大小 | 512KB ~ 1MB（平台相关） |
| `-XX:MetaspaceSize` | 元空间 | 元空间的初始阈值 | 约 21MB |

**核心区分：**
- **堆 (Heap)**：存**对象实例**（`new` 出来的东西），所有线程共享，GC 管理的就是这块区域。
- **栈 (Stack)**：存**方法调用、局部变量、操作数**，每个线程私有，自动分配释放，**不归 GC 管**。

**记忆技巧：** `Xms` = 堆起点；`Xmx` = 堆上限；`Xss` = 栈大小（每个线程，不是总量）。

```bash
java -Xms4g -Xmx8g -Xss512k -jar app.jar   # 堆初始4G / 最大8G / 每线程栈512K
```

> 把 `-Xms` 当成栈来调的后果：栈大小没变（该 StackOverflowError 还报），堆被意外改动导致 GC 行为异常甚至 OOM。

## 二、新生代用什么 GC 算法？

一句话：**新生代基于「复制」思想，但在不同收集器里有不同的实现形态**，并非「唯一一套算法」。

| 时代 | 代表收集器 | 新生代算法 | 特点 |
| :--- | :--- | :--- | :--- |
| 经典 | Serial, Parallel Scavenge, ParNew | 复制算法 (Copying) | Eden + 2 个 Survivor，对象在 S0/S1 间来回复制 |
| 现代 | G1 | 分区复制 (Region Copying) | 不严格区分 Eden/Survivor，按 Region 动态分配，复制粒度更小 |
| 前沿 | ZGC, Shenandoah | 并发转移 + 读屏障 | 新生代/老年代统一处理，复制过程几乎全程并发 |

**为什么新生代偏爱「复制」而非「标记-清除/整理」？** 由对象存活特征决定：
1. **朝生夕死**：98% 以上对象活不过第一次 GC，存活对象极少。
2. **复制成本极低**：只复制那 2% 的存活对象，远快于遍历整块区域做标记。
3. **天然无碎片**：复制后内存连续，无需额外整理。
4. **空间换时间**：浪费一个 Survivor 换极低暂停，划算。

## 三、既然是复制算法，为什么要分 Eden 和 Survivor？

**关键认知：三区设计不是「复制算法」本身的要求，而是为解决「纯复制算法太浪费空间」打的工程补丁。**

**如果没有 Survivor（纯双区复制）：** 你必须永远预留 50% 空间作为「复制目标」，可用内存上限永远只有一半。

**HotSpot 的洞察：** 绝大多数对象活不过第一次 GC。于是把「复制目标」拆成两部分：
- **Eden (80%)**：高速分配新对象，不参与复制目标职责。
- **Survivor × 2 (各 10%)**：只存少数存活对象，互为复制源/目标。

| 方案 | 可用分配空间 | 复制目标大小 | 空间利用率 |
| :--- | :--- | :--- | :--- |
| 纯双区复制 | 50% | 50% | 50% |
| Eden + 2×Survivor | **80%** | **10%** | **80%** |

- **默认比例 8:1:1 的依据**：98% 对象朝生夕死（Eden 占大头）、存活对象通常 <10%（一个 Survivor 装得下）、年龄晋升机制让对象有机会「证明自己值得长期存活」。
- **Survivor 太小的后果**：存活对象放不下 → 提前晋升老年代 → 老年代压力剧增 → Full GC 频繁。这正是 `-XX:SurvivorRatio` 调优的意义。

> 算法 = 复制思想（只移动存活对象）；布局 = Eden + Survivor（让复制思想的空间开销可接受）。

## 四、Eden 到底是不是「复制」？—— 方向性是关键

Eden 里的存活对象**确实是被复制走的**，但要纠正一个心理模型：

> **Eden 是复制算法的「数据源」，不是「受益者」。Eden 从不接收复制过来的对象，只产出不回收复用。**

Minor GC 时数据流向是**单向**的：

```
Eden (源)         ──复制存活对象──→ Survivor To (目标)
Survivor From(源) ──复制存活对象──→ Survivor To (目标)
```

注意：**没有任何箭头指向 Eden**。

| 区域 | 是否参与复制 | 角色 | 如何复用 |
| :--- | :--- | :--- | :--- |
| Eden | 作为源 | 只出不进，GC 后整体清零 | 靠指针重置，不通过复制 |
| Survivor | 作为源+目标 | 双向流转，互为备份 | 通过复制实现内存复用 |

Eden 的清理方式是 **指针碰撞 + 整体清零**，比复制快几个数量级——这正是新生代分配极快的原因。真正的「双区复制循环」只发生在两个 Survivor 之间。

## 五、各区域什么时候触发 GC？

GC 不靠定时器，而是靠 **空间不足** 或 **显式指令** 驱动。

**新生代 (Young Gen) → Minor GC：**
- **Eden 区满**（最常见，扳机永远在 Eden）。
- 大对象直入老年代失败时可能先触发 Minor GC 腾空间。
- 担保失败 → 直接退化为 Full GC。

> 注意：**Survivor 满不会单独触发 GC**，只会导致对象提前晋升老年代。

**老年代 (Old Gen) → Major / Full GC：**
- 老年代空间不足（晋升放不下）。
- 元空间/永久代满（类加载过多、动态代理泛滥）。
- `System.gc()`（仅 hint，加了 `-XX:+DisableExplicitGC` 即被忽略）。
- CMS/G1 并发模式失败 → 退化为 Serial Old Full GC。
- G1：老年代占用达 `-XX:InitiatingHeapOccupancyPercent`（默认 45%）触发并发标记 + Mixed GC。
- ZGC/Shenandoah：基于时间/负载**主动预测**触发，不等空间满，目标暂停 < 1ms。

**收集器触发逻辑对比：**
```
Serial / Parallel  -> 纯被动：Eden满->Minor；Old满->Full
CMS                -> Minor看Eden；Major看Old占用/并发失败
G1                 -> Young看Eden Region；Mixed看IHOP(45%)；来不及则退化Full
ZGC/Shenandoah     -> 主动预测：分配速率 vs 回收速率动态决定，"快满就开始"
```

**三个常见误区：**
1. Survivor 满会触发 GC（错，只会提前晋升）
2. 老年代满才触发 Full GC（错，G1 在 45% 就启动，ZGC 更早）
3. `System.gc()` 一定执行 Full GC（错，只是 hint）

## 六、Survivor 满了怎么办？要等 15 次 GC 吗？

**Survivor 满绝不单独触发 GC，也无需等满 15 次；一旦放不下存活对象，JVM 立即强制其提前晋升老年代。**

「熬过 15 次 GC 才晋升」(`-XX:MaxTenuringThreshold=15`) 只是**理想情况下的默认规则**。实际有两道「提前放行」机制：
- **动态年龄判定**：Minor GC 后，若 Survivor 中相同年龄对象总大小超过其容量 50%，则年龄 ≥ 该年龄的对象直接晋升。
- **空间担保失败 / Survivor 溢出**：存活对象总量超过 To Survivor 容量，多出的对象无论年龄，直接晋升老年代。

**晋升条件（满足任意一条即晋升）：**

| 晋升条件 | 触发时机 |
| :--- | :--- |
| 年龄达标 | 熬够 15 次 Minor GC（理想情况） |
| 动态年龄 | 同龄对象抱团超过 Survivor 50% 容量 |
| Survivor 溢出 | 存活对象太多装不下（最常见） |
| 大对象直入 | 创建时体积过大，跳过新生代进老年代 |

> 15 次是「正常退休」年龄上限；Survivor 一满就是「强制提前退休」。

## 七、空间担保失败 -> 线上频繁 Full GC 的经典诱因

**本质：** JVM 在每次 Minor GC 前做一次「风险评估」，评估不通过就直接退化为代价极高的 Full GC。

**担保逻辑：**
1. **理想情况**：老年代最大可用连续空间 > 新生代所有对象总大小 → 安全执行 Minor GC。
2. **风险评估**：若上一条不满足，检查老年代最大可用连续空间是否 > **历次晋升到老年代的平均大小**。
   - 大于平均值 → 「冒险」执行 Minor GC。
   - 小于平均值 → 判定风险过大，**直接触发 Full GC**。

（`-XX:HandlePromotionFailure` 在 JDK 6u24 后默认开启，后续版本移除该开关、默认执行担保逻辑。）

**为什么演变成线上故障（死亡螺旋）：**
- **流量突增**：平时「平均晋升大小」很小，大促时新生代产生大量长存对象。老年代剩余虽 > 平时平均值，却 < 本次实际晋升量。JVM 冒险执行 Minor GC → 对象挤爆老年代 → **Promotion Failed** → Full GC。
- **恶性循环**：Full GC 长时间 STW → 请求堆积 → Full GC 结束新生代又满 → 再次评估失败 → 频繁 Full GC → 服务雪崩 / OOM。

**排查与解决：**
1. **确认原因**：看 GC 日志关键字 `concurrent mode failure`（CMS）/ `promotion failed`。
2. **观察水位**：`jstat -gcutil <pid> 1000`；若 O 区持续 80%~90% 且 Full GC 后回落不明显，老年代已极度紧张。
3. **调优方案**：
   - 增大老年代：调 `-Xmx` 或 `-XX:NewRatio`。
   - 增大 Survivor：调 `-XX:SurvivorRatio`，让对象多留存几轮。
   - 降低晋升阈值：调小 `-XX:MaxTenuringThreshold`，让晋升更早更分散。
   - 切换收集器：CMS -> G1（Mixed GC 提前清老年代）或 ZGC。

> 空间担保失败是 JVM 的一次「赌注」：赌本次晋升不超过历史平均。赌输就用一次昂贵的 Full GC 买单。

## 八、GC 日志快速判断流程（速查）

```
GC 发生了
|- Young GC？ -> Eden 分配速率太快 / Eden 太小
|- Mixed GC？ -> 正常，G1 在设计预期内工作
|- Full GC？
|   |- 伴随 "Promotion Failed"        -> 老年代碎片化或太小
|   |- 伴随 "Concurrent Mode Failure" -> CMS 并发跟不上
|   |- 伴随 "Metadata GC Threshold"   -> 类加载泄漏
|   |- 无明确原因                      -> 检查 System.gc() 或 JNI 调用
|- ZGC 频繁触发？ -> 分配速率持续超过回收能力，需扩容或优化代码
```

## 九、一句话总纲

- **内存参数**：`Xms` 堆起点、`Xmx` 堆上限、`Xss` 每线程栈大小。
- **新生代算法**：基于复制思想，Serial/Parallel 经典三区、G1 分区复制、ZGC 并发转移。
- **Eden/Survivor**：复制思想的工程落地——用 80/10/10 布局把空间利用率从 50% 提到 80%。
- **方向性**：复制发生在 Survivor 之间；Eden 只出不进，靠指针清零。
- **触发时机**：新生代看 Eden，老年代看收集器策略，元空间看类加载；现代收集器已「被动救火」转「主动预防」。
- **晋升**：15 次是理想上限，动态年龄、Survivor 溢出、大对象直入都会触发提前晋升。
- **故障**：空间担保失败 -> Promotion Failed -> Full GC 死亡螺旋，是线上频繁 Full GC 的头号诱因。
