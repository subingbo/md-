# 评估接口排查原理（2026-10-19）

这份笔记讲排查时每次在问什么、为什么上一个数字不能用、内存和耗时各自改了哪一段。**重点是 SSE 序列化的临时大字符串：为什么它会推高 JVM 堆峰值、为什么发送完成后内存未必马上下降、以及为什么优化后的 SSE 峰值仍接近一次性返回。** 原始测量表在同目录的基线、复测、内存记录和链路记录里。环境是公司 Docker 测试机 `192.168.1.240`，分析服务堆 `-Xmx2048m`，容器上限 3 GB。耗时经网关 `:48080/gzmap`，内存直连分析服务 `:8108`。

> **先记结论**：`writeValueAsString()` 会把一个图层的完整 JSON 先做成 Java `String`，在序列化和发送时与图层对象、缓冲区共同占堆。`send()` 结束后，这份字符串**可以**变成垃圾，但**不会自动立即从 `Heap Used` 里消失**；GC 回收后，JVM 的 `Heap Committed` 和容器占用也**不一定马上下降**。679 MB → 255 MB 的 **424 MB 是实测峰值之差，不是单条字符串大小**。

## 1. 四个数不要混

同一次请求可以同时报出四个差很远的数。后面几次误判，都是把其中一个当成了「内存峰值」。

| 名字 | 它量的是什么 | 这次大框上的数量级 |
| --- | --- | --- |
| 响应字节 | 网上发出去的 UTF-8 文本 | 整包 74.4 MB，最大一条 26.7 MB |
| 堆用量 | JVM 堆里对象占用的字节，新生代 `used` 加老年代 `used` | SSE 峰值 255 MB，一次性返回 302 MB |
| 堆已提交 | G1 向操作系统要过、现在仍划给堆的地址空间 | SSE 285 MB，一次性返回 382 MB |
| 容器驻留 | cgroup 的 `memory.current`，和 `docker stats` 同一类 | SSE 630 MB，一次性返回 708 MB |

这四个数字是**不同统计口径**，不能直接等同：

- **响应字节**：HTTP/SSE 最终写出的文本大小，不能推算服务器上一个 `BoxLayerResultVO`、`Map`、集合、JSON 缓冲区的总占用。
- **Heap Used（堆已用）**：JVM 各代/区域的 `used` 之和，表示当下被占用的堆空间，**既可能有仍被引用的对象，也可能有已经不可达但尚未被 GC 回收的对象**。它**不等于严格意义上的“存活对象大小”**；要估计活对象，需要结合 GC 后采样、堆转储等。
- **Heap Committed（堆已提交）**：JVM 已为堆提交的内存容量，通常 `Committed ≥ Used`。垃圾被回收，可以先让 `Used` 下降；`Committed` 未必随之下降。
- **容器 `memory.current` 与进程 `VmRSS`**：不是同一个计数器。前者统计该 cgroup 计费的内存（可能含页缓存等），后者反映进程驻留页；两者还都可能涉及非堆、线程栈、元空间、直接缓冲区等。原始记录里两者曾分别采样，不应当混成“纯 JVM 堆”。

所以，「空闲驻留 550 MB → 请求时 630 MB」只说明该指标增长约 80 MB，**不能说请求只需要 80 MB Java 堆**。旧配置 `-Xmx512m` 限制的是最大 Java 堆，而不是进程或容器所有内存；空闲驻留超过 512 MB 并不矛盾。

**G1 的关键行为**：一次请求触发大量分配，堆已提交可能被推至 706 MB。即使随后有对象不可达、甚至部分已经 GC 回收，堆也可能继续保持较高 `Committed`，容器使用量也不会立刻回到请求前。**“高驻留”不等于“对象仍被持有”或“内存泄漏”。** G1 具备在一定条件下归还空闲堆内存的能力，但是否/何时归还受 JDK、GC 周期和配置影响，不能默认请求结束立即缩堆。

本轮对比的实验方法：**SSE 与一次性返回各重启一次 `analysis-service`、使用同一大框、不传 `limit`、直连 `8108`，从相近的空闲状态分别采样**，避免上一轮 G1 的高水位干扰。堆用量由容器 `/tmp/hsperfdata_root/<pid>` 中的 JVM 性能计数器计算（新生代 `used` + 老年代 `used`）；容器 JRE 没有 `jstat`，重启后 PID 会变化，采样前需要重新确认。

**最容易误读的一句**：请求结束时采到 `Heap Used = 454 MB`，不代表仍有 454 MB 的对象“被引用活着”；它可能包含尚未被 GC 回收的临时数据。详见第 4 节。

## 2. 两条返回路径实际留住了什么

总规的一次性返回和 SSE 都进 `AssessReportServiceImpl.stream()`。差别只在回调把结果放哪。

```text
stream()
  预取驾车 OD、公交/轨道覆盖、多个等时圈覆盖
  对每个指标：
      算指标值
      从库里取出这一条的点、线、面（GeoJSON 文本）
      sink.onLayer(这一条)
      releaseFeatureCache()  清掉请求上下文里的几何缓存
  最后推总评
```

数据库返回的几何来自 `ST_AsGeoJSON` 文本；MyBatis 将结果组织进 `Map`，随后又放入 `BoxLayerResultVO` 等 Java 结构。**网络上最大 SSE 事件 26.7 MB，不等于它在 Java 堆里只占 26.7 MB**：除了字段文本本身，可能还有重复字段/列表/对象头/序列化缓冲区，以及在序列化前后短时并存的对象。Java `String` 在语言层面表示 Unicode 文本，但现代 JDK 的 Compact Strings 可根据内容使用单字节或双字节存储；因此**不能固定说“UTF-8 上网 26.7 MB → Java `char[]` 必为 53.4 MB”**。

### 2.1 共同的计算入口

两条路径都是 `AssessReportServiceImpl.stream()` 逐条计算；区别在 `sink.onLayer()` 后面的结果归属：

- **SSE 路径（优化后）**：`onLayer(layer)` 把**当前** `BoxLayerResultVO` 交给 SSE + Jackson 输出。输出调用结束、后续缓存清理完成、且没有其他强引用时，**前一条**的结果可被 GC 回收；这不意味着下一行代码执行时对象一定已经被回收，也不意味着输出一定已经到达浏览器。
- **一次性路径**：`CollectingSink` 把每个 `BoxLayerResultVO` 放进同一个列表；即使 `releaseFeatureCache()` 清掉请求上下文里的几何缓存，**该列表仍持有已收集的结果对象**，必须等 `stream()` 结束、整体响应序列化完成，才有机会释放它们。

```text
共同入口：AssessReportServiceImpl.stream()
  ├─ 计算图层 1 → sink.onLayer(layer1) → releaseFeatureCache()
  ├─ 计算图层 2 → sink.onLayer(layer2) → releaseFeatureCache()
  ├─ ...
  └─ 计算图层 20 → sink.onLayer(layer20) → releaseFeatureCache()

SSE sink（优化后）                CollectingSink（一次性返回）
  当前 layer → JSON 输出流           layer1、layer2、... → List
  后续不再保留旧 layer 的引用         stream() 结束后统一写 JSON
  是否真正回收，仍取决于 GC          写完后引用消失，也仍取决于 GC
```

### 2.2 `releaseFeatureCache()` 到底清除什么

它清理请求上下文中缓存的点、线、面以及相关要素缓存，避免之后的指标通过这些缓存继续持有上一条几何。**它不是 `System.gc()`，不能强制销毁 `BoxLayerResultVO` 或字符串**；也无法清理 `CollectingSink.list` 对结果对象的引用。`scored` 中主要保留得分而不是几何；`odFutures` 中的 OD 路径可能持续到对应使用结束/请求上下文不可达。这些是另外的引用关系，不能与 SSE 生成的完整 JSON String 混为一谈。

一次性返回优化后在请求结束附近采到 `Heap Used = 261 MB`，SSE 为 159 MB。**这符合一次性路径在请求处理期间保留更多结果对象的预期，但不能仅凭“结束时 `used`”证明那个瞬间列表还持有全部对象**；写完响应后同样存在“对象已不可达、但尚未 GC”的可能。

## 3. 排查是怎么一步步改问题的

### 3.1 先确认慢在哪

16:50 的旧包上，同一块 20 km 框、`limit=20`：

- 总规驾车约 10.9 秒
- 详规约 13.6 秒
- 可达性约 57.8 秒
- 加路对比约 46 秒，时间在 Python 等时圈，Java 只转发
- 建规约 0.63 秒，矩阵和出行需求汇总在 100 毫秒内

只改前三个。慢的原因是重复计算：最大内切圆每个枢纽算一遍，五条驾车 OD 串行等，公交和轨道各做一次交通小区相交，多个步行覆盖也各做一次，线裁剪把同一次相交算两遍。评分公式没有改。

改完之后，详规 13.6 秒到 10.2 秒，可达性 57.8 秒到 55.8 秒。总规驾车仍是 10.9 秒，墙钟在 OD 服务里，Java 并行发请求并没有把这 11 秒拿掉。

第一次部署没起来：合并 SQL 写在 MyBatis `<script>` 里，`&&` 被 XML 当成实体。改成 `&amp;&amp;` 之后服务才注册上。

### 3.2 把响应大小当成了内存

`limit=20` 时总规整包 11.8 MB，最大一条 11.3 MB。这是文本长度。它回答不了「进程会不会 OOM」。

### 3.3 把驻留涨幅当成了峰值

空闲驻留约 748 MB，`limit=20` 期间最高 768.6 MB，只涨了大约 20 MB。当时的结论是内存增加很少。这个结论错在口径：进程早就占着 750 MB，小结果放得进已经划好的堆，涨幅自然小。8 月的 OOM 不是这 20 MB。

### 3.4 回到 8 月的堆溢出

8 月 21 日的异常是 `Java heap space`，线程 `box-sse-12`，接口是总规 SSE。框是一块外接约 16.4 km × 19.7 km 的三角。建成区的重叠条数和重叠率已经返回，随后堆满，整次请求 5.8 秒。重叠率只是一个数。满的是把建成区多边形装进堆再序列化。

当时 compose 写了 `-Xmx2048m`，进程实际是 `-Xmx512m`，变量没有进 Java 命令。堆改成 2 GB 之后，同一次请求不再抛这个异常，驻留涨到 2.04 GB，然后客户端断开。

现在的几何查询已经按框裁剪，并且可以带 `limit`。用来对比的 20 km 框大约 400 km²，比 8 月那块三角更大。`limit=20` 看起来只有几十 MB，是因为只取了 20 条裁剪后的几何，不是框比 8 月小。

### 3.5 去掉条数限制，SSE 反而更高

不传 `limit`，直连 `8108`，两种返回各重启一次。约 29.6 km 的大框：

- SSE 驻留峰值 1121 MB，响应 74.4 MB，最大一条 26.7 MB
- 一次性返回驻留峰值 630 MB，整包同样 74.4 MB

整包 74.4 MB、单条最大 26.7 MB，说明 SSE 每次业务事件的数据量小于整包；**不能直接把 74.4 − 26.7 ≈ 47.7 MB 当成“应节省的 Java 堆内存”**。当时 SSE 的进程占用峰值反而高约 490 MB，说明问题在服务端中间对象/分配与 GC，而不是网络字节数之差。

当时的实现有两层叠加。第一层是先把十几个指标的要素放进一张表，再按顺序推，上一条的几何还活着。第二层是推送时 `writeValueAsString`，每条再造一段和整条事件一样长的字符串。一次性返回在 `stream()` 之后由 Jackson 直接写流，没有这第二层。

### 3.6 先拆掉「全部算完再推」

`stream()` 改回按目录算一条、推一条，推完调用 `releaseFeatureCache`。驾车 OD 仍提前并行，覆盖 SQL 仍合并。

同一块大框：SSE 驻留 1121 MB 降到 1035 MB，只少 86 MB。一次性返回大约 717 MB。SSE 仍然更高。说明前面几条几何已经不是峰值的主体，推送当前这一条时还有别的分配。

### 3.7 改看堆用量，才定位到完整 JSON 字符串

驻留停在高位，不足以判断对象是否还可达。于是改从 JVM 性能计数器读取 `Heap Used`：

| 返回 | 堆用量峰值 | 请求结束时采样的 `used` | 堆已提交 | 容器占用/驻留记录 |
| --- | ---: | ---: | ---: | ---: |
| SSE（仍先转字符串） | **679 MB** | **454 MB** | **706 MB** | **1097 MB** |
| 一次性返回 | 291 MB | 247 MB | 363 MB | 714 MB |

该轮的对象直方图记录了请求结束后 `char[]` 约 56 MB、`byte[]` 约 11 MB。这些结果和 `BoxStreamSseSupport.send` 使用 `writeValueAsString()` 的代码一起，支持**“完整字符串及其临时缓冲带来显著额外分配”**的定位；但不能据此说「20 个字符串一直存活」或「679 MB 都是活对象」。**直方图是采样时刻，堆峰值是请求期间另一时刻，两者不是同一瞬间。**

### 3.8 去掉完整中间字符串并复测

`BoxStreamSseSupport.send` 改为 `emitter.send(event().name(name).data(事件对象, application/json))`：传入事件对象，让 Spring 选中的 Jackson HTTP 消息转换器向响应输出流序列化，不再显式调用 `writeValueAsString()` 制造一条完整 JSON String。仍可能有分块缓冲，并非“零缓冲”。原来的事件名、JSON 对象内容和返回口径保持不变；短的异常事件按记录仍可能走单独的字符串处理。

| 返回 | 堆用量峰值 | 请求结束时采样的 `used` | 堆已提交 | 容器占用/驻留记录 |
| --- | ---: | ---: | ---: | ---: |
| SSE（直接写对象） | **255 MB** | **159 MB** | **285 MB** | **630 MB** |
| 一次性返回 | 302 MB | 261 MB | 382 MB | 708 MB |

对同一大框（约 29.6 km × 29.6 km）、不传 `limit`、SSE 20 个事件、总输出仍 74.4 MB，SSE 记录到：

- `Heap Used` 峰值 **679 → 255 MB，降低 424 MB（约 62%）**；
- `Heap Committed` **706 → 285 MB**；
- 容器占用/驻留记录 **1097 → 630 MB**。

**424 MB 是“两个实现的堆采样峰值差”**，包括省下的完整字符串及其临时缓冲、减少的分配/GC 压力、采样时的未回收垃圾等综合影响；**并不是一条 424 MB 的 String，也不证明 20 条 String 互相引用、全部滞留**。一次性返回的 291 → 302 MB 处于不同轮次实测的波动范围，不能说 SSE 的修改也使一次性返回降低了内存。

## 4. 重点：字符串为什么“发送完了还占内存”？为什么省 424 MB 后仍有 255 MB？

**先回答最核心的问题：字符串不是一定一直保留。它经历了“创建 → 被引用/使用 → 失去引用 → 等 GC → JVM 可能仍保持已提交内存”五个阶段。** 原始排查里容易把这五件事混成一件。

### 4.1 优化前：当前图层和完整 JSON String 会短暂并存

下面是与原来 `BoxStreamSseSupport.send` 相同的**示意逻辑**（不是从仓库复制的完整源码）：

```java
void send(BoxLayerResultVO layer) throws Exception {
    // layer 仍被当前方法、stream() 调用链和可能存在的缓存引用
    String json = objectMapper.writeValueAsString(layer);
    // 先分配并构造整条 JSON 字符串，序列化过程还可能产生临时数组/缓冲

    emitter.send(SseEmitter.event().data(json));
    // 传给 SSE 的是整个 String
}
```

- **序列化前**：已有 `layer`、内部 `Map`、GeoJSON 字段及集合。
- **序列化期间**：Jackson 把整个对象转成 JSON，`writeValueAsString()` 需要返回**一个完整 `String`**；其内部缓冲、字符转换和最终字符串在部分时段可能**一起占堆**。
- **发送期间**：`json` 仍被局部变量或发送调用持有，属于**可达对象，GC 不能回收它**；这时底层可能还有输出缓冲。
- **发送返回后**：如果别处（异步队列、回调、缓存等）没有继续引用，该 `json` **通常已可以回收**；但“可以回收”不是“已经回收”。

> `writeValueAsString()` 产生的 JSON 是 Java `String`；在 JDK 9+，String 的底层一般是 `byte[]`（Compact Strings），Jackson 中间缓冲可能用 `char[]`。**不要把“整条 JSON String”机械理解为“永远存在一块长度×2 的 `char[]`”**。网络上的 26.7 MB 也不能乘一个固定系数得到堆峰值。

### 4.2 发送 20 条，不代表堆里始终留着 20 条 String

按条发送时，可能发生以下时间线：

```text
时间 →

第 1 条：算 layer1 ── JSON String1 ── send ── 不再引用 String1
                                                │
                                                └─ [可回收 ≠ 已回收]
第 2 条：                         算 layer2 ── String2 ── send ── 可回收
第 3 条：                                              算 layer3 ── ...

某个 GC 时刻：清理已经不可达的 String1 / String2 / 临时缓冲等
              （何时执行由 JVM 决定，可能在两次 send 之间，也可能更晚）
```

一个大对象的生命周期可以分为四种状态：

| 状态 | 引用关系 | 这时是否计入 `Heap Used`？ | 是否已经归还给操作系统？ |
| --- | --- | --- | --- |
| 正在发送 | 被局部变量/框架调用链引用 | 通常计入 | 否 |
| 已发送且没有强引用，但 GC 未执行 | **不可达，等待回收** | **可能仍计入** | 否 |
| GC 已回收该对象 | 已释放对应堆内占用 | 通常不再计入对象占用 | **不一定** |
| G1 之后缩小已提交堆 | 不再被引用且内存空闲并满足归还条件 | 已回收 | **这时才可能减少 `Committed`/部分驻留** |

因此，原始记录的“请求结束后 `Heap Used = 454 MB`”**不等于**“SSE 还引用了 454 MB 的对象”；更不等于“20 条 String 一直保留”。它只能说明**该采样时刻的堆区域仍记录了这些占用**。如果要证明长期引用，需要看 GC 后的活对象、引用链/支配树，而不是只看请求刚结束的一次 `used`。

### 4.3 为什么临时字符串依然能推高峰值？

**峰值是请求过程中某个瞬间测到的最大占用，不要求那些对象持续存活。**

```text
本来就存在的请求对象（当前大图层 + 相关几何/Map）
                +
本条的完整 JSON String
                +
Jackson 写 String 用的临时缓冲 / 下游输出缓冲
                +
前面已经不可达、但 GC 还没清掉的临时对象（如果有）
                ↓
          瞬时 Heap Used 峰值
                ↓
     G1 为继续分配，可能提高 Heap Committed
                ↓
        峰值过后 RSS / memory.current 仍可能偏高
```

只要某一条特别大，在它序列化的当下，就可能出现**“原始图层数据 + 第二份完整 JSON + 中间缓冲”**的重叠分配。连续 20 次生成完整字符串又提高了分配速率。**即使旧字符串最终都可被 GC 回收，峰值仍然已经出现；一旦 G1 把堆提交到高水位，也不会因为 `send()` 返回就立刻缩回去。**

这里的数字需要分开理解：

| 现象 | 实测 | 能得出的结论 | 不能直接得出的结论 |
| --- | --- | --- | --- |
| SSE 修改前最大堆用量 | 679 MB | 某个采样时刻 JVM 堆占用很高 | “679 MB 全是存活对象” |
| SSE 修改后最大堆用量 | 255 MB | 去掉完整中间字符串的写法后，峰值显著降低 | “一个 String 恰好占 424 MB” |
| 差额 | **424 MB** | 两次实现的峰值差 | “20 条 JSON 都常驻内存” |
| 堆已提交 | 706 → 285 MB | 高分配压力下降，JVM 不必提交到旧高位 | “已提交堆里每一个字节都被活对象使用” |
| 容器占用/驻留记录 | 1097 → 630 MB | JVM/进程整体高水位随之下降 | “所有下降都来自 String 自身的字节数” |

### 4.4 优化后：直接把事件对象交给 Jackson 输出

优化后的**示意代码**：

```java
void send(String name, Object layer) throws IOException {
    emitter.send(
        SseEmitter.event()
            .name(name)
            .data(layer, MediaType.APPLICATION_JSON)
    );
}
```

调用链从：

```text
旧：VO → Jackson 创建完整 String → SSE 再处理 String → 输出
新：VO → SSE/Jackson 将 JSON 写入输出流（可分块缓冲） → 输出
```

直接序列化**不是不需要字符串**：VO 内 `ST_AsGeoJSON` 原本就是文本字段，仍在；也不是网络无缓冲。它只避免**再专门构造“整条 SSE JSON 的完整中间 String”**，减少大对象与临时缓冲的重叠分配。正是这个改动，让 SSE 堆采样峰值从 679 MB 降至 255 MB。

### 4.5 SSE 和一次性返回的差异，是“前面图层的引用是否还在”

**要区分两种完全不同的“保留”：**

1. **业务代码主动保留**：一次性返回通过 `CollectingSink` 的 `List<BoxLayerResultVO>` 保存前面各图层；`List` 还在时，元素仍可达，GC **不能**回收它们。SSE 优化后通常不把每个输出结果长期放入该列表。
2. **GC 还没来得及清理**：SSE 某条发完、引用已经断开，但对象和字符串还可能暂时占据 `Heap Used`。GC **可以**回收它们，只是时间尚未到。这不是主动缓存，更不能直接称作内存泄漏。

`releaseFeatureCache()` 解决的是请求上下文缓存保留几何的问题；Jackson 直接写流解决的是每条事件的完整 JSON 字符串问题。**一个缩短对象可达时间，一个减少额外对象的创建。作用机制不同。**

### 4.6 为什么直接写入后，SSE 峰值 255 MB 仍接近一次性返回 302 MB？

因为这里的 SSE 粒度是**“一整个图层”**，而不是“一个个 Feature”。**输出第 N 条之前，当前这一条的 `BoxLayerResultVO`、GeoJSON 字段、`Map` 等仍需构造出来。** 如果某条大面占主要内存，SSE 不能通过“释放前面 19 条”消除**当前最大图层**的峰值。

```text
SSE（逐图层）：
  layer1 → 发出 → 旧结果可回收
  layer2 → 发出 → 旧结果可回收
  ...
  [最大 layerK 完整在堆中] → 直接写出 → 旧结果可回收

一次性返回：
  layer1 → List
  layer2 → List
  ...
  [最大 layerK] → List
  ... → 所有 layer 一起写出
```

本轮数据：

- HTTP/SSE 合计 **74.4 MB**，最大一个 SSE 事件 **26.7 MB**，事件 **20 条**。这三个数说的是**网络文本**，不是图层 Java 对象占多少堆。
- 优化后 SSE 峰值 **255 MB**，一次性返回 **302 MB**，只相差 **47 MB**。两者都需要处理完整的**当前最大图层**；一次性返回还需累计其他图层。结合相近的实测，这可以解释为什么峰值比较接近；**不能仅根据这两个数精确反推出“其余图层恰占 47 MB”**，因为 GC 时机、基线及采样点也会影响结果。
- SSE 请求结束附近 `used` **159 MB**，一次性返回 **261 MB**，相差 **102 MB**。这与一次性路径累计更多对象、清理/GC 时机不同相符；**但结束时的堆已用不是严格的存活堆对照，更不能用差额证明某个列表此时仍在引用 102 MB**。
- 当轮空闲堆 SSE 约 130 MB、一次性约 141 MB，可做粗略“增量”参考：255 − 130 ≈ 125 MB，302 − 141 ≈ 161 MB。**这些是不同请求和时间点的采样差，不是对象大小的精确测量。**

所以不能认为“用了 SSE，峰值就应当接近网络单条的 26.7 MB”。**SSE 只控制按什么粒度产出与保留数据；如果最小产出单位本身仍是巨大的整层对象，最大单层就很可能主导峰值。**

### 4.7 要继续降低 255 MB，该查哪里？

当前结论是：**减少完整 JSON String 的优化已有效，下一步瓶颈更可能在“生成当前最大图层对象”**，但需要新的分配剖析来验证，不能仅凭一份 `used` 峰值定位到单个类。

- 进一步把大图层按页/批次（如分批 Feature）获取和发出，避免先构造完整的 `BoxLayerResultVO.features`；这需要同步调整 SSE 事件协议及前端拼接/顺序处理，属于**尚未实施的方案**。
- 在可行时考察数据库游标/流式读取，并核实 JDBC 驱动、MyBatis 映射、事务和网络写出是否真的按批处理，避免在中间层又一次性缓冲所有 GeoJSON。
- 为了区分“分配高峰”与“长期引用”，在测试环境开启适当的 GC 日志（例如受 JDK 支持时 `-Xlog:gc*`），必要时做 JFR/Allocation Profiling、GC 后堆转储/引用链分析。**不能用 `System.gc()` 作为生产业务上的常规优化**；诊断时也须说明 GC 对测试数据的干扰。

### 4.8 本节记忆版

> **三个时间点**：`send()` 正在执行时，`json` 仍被使用；`send()` 返回且无其他引用后，`json` 才是可回收垃圾；GC 回收后，JVM 的 `Committed`/容器内存仍可能保留高水位。  
> **两种优化**：算一条、推一条 + 释放缓存，减少“旧图层持续被引用”；Jackson 直接写输出流，减少“当前图层的完整 JSON 临时副本”。  
> **两个峰值**：424 MB 是前后实现的**堆峰值差**；255 MB 和 302 MB 接近，是因为二者仍要处理**当前最大的完整图层**，并不意味着 SSE 没有释放之前的图层。

## 5. 耗时和内存是两条线

耗时改动碰的是算什么、算几次：内切圆一次、OD 并行、覆盖 SQL 合并、线相交一次。它们不负责把峰值从 679 MB 降到 255 MB。

内存改动碰的是算完的对象活多久、写出时有没有第二份文本。它们不负责详规那 3.4 秒。

结果文本这次没有改计算口径。`limit=20` 的三份响应和优化前比，总字节数仍是 86,420、172,379、962,010，保存下来的前 400 字逐字相同。没有做全文哈希。不限条数的大框几次都是 74.4 MB，没有优化前的全文可以逐字段比。

## 6. 这次没有动、以后仍会占内存的部分

- 一次性 `/query` 仍通过 `CollectingSink` 列表收集全部图层，直到整包准备好并序列化完成。**响应完全结束后若已无引用，这些对象同样可被 GC 回收；并非永久驻留。**
- SSE 仍完整构造当前单个大图层的 `BoxLayerResultVO` 和 GeoJSON 字段，**SSE 粒度是按图层，不是逐 Feature**。最大的面可能支配峰值。
- `odFutures` 可能在对应指标使用之前继续持有驾车路径；何时可回收取决于其引用链。
- G1 不保证请求结束立即归还已提交堆。优化前 `Committed` 曾高达 706 MB、优化后 285 MB；容器记录分别是约 1.1 GB 和 630 MB。**即使看到“请求后还占用内存”，也必须先看 GC/引用链，不能直接判定泄漏。**
- 加路对比大约 46 秒、等时圈和 OD 服务自己的数 GB 内存属于其他服务/进程，不在本轮 SSE 修改范围。
