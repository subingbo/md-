# 框选查询 - 开发文档

> 面向后续接手 `analysis-service` 框选查询功能的开发者。本文档说明功能的整体架构、关键实现决策、踩坑记录与扩展方法；接口协议细节见《框选查询接口文档.md》，前端消费见《框选查询-前端对接指南.md》。

## 1. 功能概述

用户在地图上绘制一个矩形范围（广州2000 投影米制坐标），后端按《对应关系.xlsx》定义的「图层 → 表」映射，返回框内每个图层的要素（geometry 转为 GeoJSON 字符串 + 关键属性）与合规指标。

- **老接口** `POST /api/analysis/box-selection/query`：全部图层串行算完后一次性返回 `R<BoxSelectionResponseVO>`（大框实测约 40s）。
- **流式接口** `POST /api/analysis/box-selection/query/stream`：SSE 长连接，每算完一个图层立即推送 `layer` 事件，全部完成推 `done` 事件（`completed:true` + 总耗时 + 失败清单）。单个图层失败推 `error` 事件不中断。

关键需求来源：用户体验上老接口等待过久且无进度反馈，需要"边算边推"。

## 3. 核心架构

### 3.1 图层注册表（核心模式）

`BoxSelectionServiceImpl` 用 `@PostConstruct init()` 注册 21 个图层，每个 `LayerDef` 记录：

```java
private record LayerDef(String layerName, String tableName,
                        Integer module1No, Integer module2No, LayerQuery query) {}
```

- `query` 是函数式接口（`LayerQuery`），每个图层绑定自己的 Mapper 查询方法（含过滤条件闭包，如 `boundary_type='生态保护红线'`）。
- **新增图层 = 注册表加一行 + 写一个 Mapper 方法**，其余逻辑（查询、流式、指标）自动复用。
- 老 `/query` 与 `/query/stream` 共用 `computeOneLayer(def, ...)`，保证两接口逐图层结果完全一致。

### 3.2 双接口一致性保证

`queryByBox` 与 `queryByBoxStream` 都调用同一 `computeOneLayer`（查要素 + 算指标），集成测试用同 bbox 断言逐层 count 完全一致（`streamMatchesBatchQuery`）。流式 layer 事件载荷 = 老接口 `data.layers[]` 单元素全部字段（通过 `BeanUtils.copyProperties` 拷贝）+ 3 个元字段（`layerIndex`/`totalLayers`/`completed`），老 VO 新增字段时流式自动跟随。

### 3.3 指标与目录序号

- 指标计算独立为 `BoxIndicatorService`，输入 `(layerName, bbox)`，不依赖要素查询结果 → 两接口共用。
- `module1No`/`module2No`（一级/二级目录序号）是**图层级**字段（与 `count` 平级），依据《总规符合性评估报告-指标与模块对应关系.md》行序取图层首次出现的归属；无指标图层（PTAL/等时圈）为 `null`。
- **注意**：目录序号曾经实现为指标级（每个指标打标），导致一个图层横跨多个目录（如道路线网同时命中 2-2/2-3/3-1）。必须保持"一个图层一个目录"的图层级设计，改回指标级属于回归。

### 3.4 流式架构（分层解耦）

```
Controller (BoxSelectionController)
  │  validateQuery 预校验（失败 → 422 JSON 非流式）
  │  创建 SseEmitter(300s) + buildSink(emitter) 翻译层
  │  sseExecutor.execute(runStream)  —— worker 线程串行跑
  ▼
Service (BoxSelectionServiceImpl.queryByBoxStream)
  │  逐图层: try { computeOneLayer } catch { sink.onError; 继续 }
  │  sink.onLayer(vo, i, total)  ← 在 try 外：客户端断开直接冲出循环停止计算
  ▼
Sink (BoxSelectionStreamSink 接口，Web 层匿名实现)
  │  onLayer → BeanUtils.copyProperties + layerIndex/totalLayers/completed → SSE 帧
  │  onDone  → completed:true + totalFeatures + elapsedMs + failedLayers
  ▼
SseEmitter.send(event 帧)
```

**为什么 Service 依赖 Sink 接口而非 SseEmitter**：Service 层只面向回调接口，可以用内存收集器做单元测试，完全不依赖 HTTP 容器；Sink 的 Web 翻译实现放 Controller 里，职责单一。

## 4. 关键实现决策

### 4.1 线程池（SseExecutorConfiguration）

```java
new ThreadPoolExecutor(4, 8, 60s, LinkedBlockingQueue(1000),
        ThreadFactoryBuilder().setNamePrefix("box-sse-").build(),
        new ThreadPoolExecutor.CallerRunsPolicy())
```

- 每个流式请求占 1 个 worker 线程串行推图层；核心 4 线程 ≈ 4 个并发流。
- `CallerRunsPolicy`：队列满时降级到请求线程（Tomcat 线程）同步执行——**不拒绝请求**，只是占用 Tomcat 线程，功能不失败。
- `destroyMethod = "shutdown"`：停机优雅关闭。

### 4.2 SseEmitter 超时语义（重要）

| 取值 | 后果 |
| --- | --- |
| `0L` | 永不超时，连接泄漏（线程/连接不回收） |
| 默认 `30_000L` | 30s 超时，大框全量计算会断流 |
| 本项目 `300_000L` | 5 分钟，覆盖大框余量；实测全量约 40s |

**超时是绝对计时，不因 send 重置**。`onTimeout` 回调里 `emitter.complete()` 兜底。

### 4.3 手动序列化规避 converter 歧义

`emitter.send(SseEmitter.event().name(name).data(json, MediaType.APPLICATION_JSON))` —— 先 `objectMapper.writeValueAsString` 再按 `APPLICATION_JSON` 发送。直接传对象会让 Spring 在 String 与 Jackson 两个 HttpMessageConverter 之间竞争，行为不稳定。

### 4.4 错误处理矩阵

| 错误场景 | 处理 | 客户端看到 |
| --- | --- | --- |
| bbox 非法 / 未知图层 | `validateQuery` 抛 `IllegalArgumentException`，类内 `@ExceptionHandler` | 422 JSON（HTTP 200，yudao 风格 `code:422`） |
| 单个图层 SQL 失败 | service 捕获 → `sink.onError` → 继续 | `error` 事件，`done.failedLayers` 含该图层 |
| 客户端断开 | `send` 抛 `IOException` → `SseClientDisconnectedException` → 停止剩余计算 | 无（连接已断） |
| 未预期异常 | `runStream` 顶层 catch → 推 `error` 事件（`message` 以 `服务端异常:` 开头） | `error` 事件 |
| 连接超时 | `onTimeout` → `complete()` | 正常关闭 |

**为什么要在 Controller 内声明 `@ExceptionHandler`**：流提交后 `GlobalExceptionHandler` 已失效，流内错误必须推为事件。类内 handler 优先级高于全局，且校验放在建 emitter **之前**，保证校验失败走 JSON 而非流式。

### 4.5 客户端断开检测（sink.onLayer 在 try 外）

`queryByBoxStream` 里图层计算包 try，但 `sink.onLayer` 在 try **外**——客户端断开时 send 抛异常直接冲出循环，剩余图层不再计算。若放 try 内会被当成"图层失败"继续算完所有图层（浪费计算 + 一直尝试往断开的连接写）。

### 4.6 框架级 Bug 修复（ApiAccessLogInterceptor）

**症状**：所有 SseEmitter 接口在非 prod 环境 async 分发的第二次 dispatch 时 500 崩溃。

**根因**：DispatcherServlet 在 ASYNC dispatch 时会重新执行 `preHandle`；`ApiAccessLogInterceptor.preHandle` 读取请求体（`getInputStream`），但 body 已被 `@RequestBody` 消费 → `IllegalStateException`。

**修复**（`yudao-framework/.../apilog/core/interceptor/ApiAccessLogInterceptor.java`）：

```java
if (request.getDispatcherType() == DispatcherType.ASYNC) {
    return true;  // 异步分发直接放行，访问日志只在首次分发记录
}
```

同类拦截器（读 body 的）都可能踩这个坑，排查 500 时先看是不是 ASYNC dispatch。

**测试基础设施两个关键点**：

1. **`@DynamicPropertySource` 覆盖 Nacos 远端配置**：gjy-common.yaml 把数据源写成内网主机名 `kingbase`/`redis`，本机无法解析；动态属性优先级最高，强制覆盖为 `192.168.1.240` IP。这是测试能连库的关键。
2. **`-Dsurefire.failIfNoSpecifiedTests=false`**：`-Dtest=...` 指定测试时框架模块没有匹配测试会报错，需加此参数。

# 集成（需本地 Nacos/Redis/Kingbase 可用）

## 6. 数据库要点

- 空间查询：`ST_Intersects(geometry, ST_MakeEnvelope(minX, minY, maxX, maxY, 0))`，几何 SRID 为 0，接口不做坐标系转换，bbox 需与数据同坐标系（广州2000 投影米制）。
- 多表合并图层（轨道/公交站点线网）：站点 + 线两表分别查询，`limit` 均分（`Math.max(1, lim/2)`），每个要素补 `sourceTable` 标记来源表。
- 错配指数：功能区（边界）+ 低 PTAL TAZ 两表联合计算。
- 单图层查询 SQL 细节见《框选查询接口文档.md》§5.1。

## 7. 部署

单服务部署（见 deploy-docker skill 模式 B，analysis-service 参数）：

```powershell
# 1. 本地打包（框架改动必须 -am 连带编译）
mvn -pl gzmap-parent/analysis-service/analysis-service-biz -am -DskipTests package
# 2. 复制 jar 到部署目录
Copy-Item -Force ".\gzmap-parent\analysis-service\analysis-service-biz\target\analysis-service-biz-1.0.0.jar" ".\deploy\apps\analysis-service-biz.jar"
# 3. 上传 + 重建（需要用户交互输密码，在会话里用 ! 前缀执行）
scp .\deploy\apps\analysis-service-biz.jar root@192.168.1.240:/opt/gzMap/deploy/apps/
ssh root@192.168.1.240 "cd /opt/gzMap/deploy && docker compose rm -sf analysis-service && docker compose up -d --force-recreate analysis-service && docker compose ps analysis-service"
```

**坑**：只 scp 上传不重建容器不生效；必须 `rm -sf` + `up -d --force-recreate`。

## 8. 已知问题与 TODO

- 开发强度图层字段当前数据为空（指标 `indicators` 存在，要素列值为空），联调注意。
- 单图层不做分片：超大框某图层要素过多时，该图层内仍是一次性返回（跨图层已流式）。
- 未做并行化：21 层串行推流已满足首屏需求，若需加速可考虑并发算多层（注意 Count 顺序与客户端对账）。
- 目录序号映射是手工填写的（`init()` 中每行注释），《总规符合性评估报告》更新时需人工同步。
- 单元测试文件在 `src/test/.../service/`（`BoxSelectionServiceImplStreamTest`），集成测试在 `src/test/.../service/` 下的 `BoxSelectionStreamIntegrationTest`——若后续重命名包注意路径。

## 9. 扩展指南（新增图层的标准流程）

1. **写 Mapper 方法**：`BoxSelectionMapper` 加 `selectXxx(minX, minY, maxX, maxY, limit)`，返回 `List<Map<String, Object>>`，SELECT 列即要素字段（snake_case 键名直接进 features）。
2. **注册 LayerDef**：`init()` 加一行 `new LayerDef("图层名", "表名", m1, m2, (x1,y1,x2,y2,lim) -> ...)`；目录序号按《总规符合性评估报告》行序取首次归属，无对应行给 `null`。
3. **指标（可选）**：`BoxIndicatorService.computeIndicators` 按 layerName 分发。
4. **同步文档**：接口文档 §2.3 图层名列表、§3.3 要素示例、前端指南 §5 图层顺序表、集成测试 `REGISTRY_ORDER`。
