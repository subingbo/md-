# Linux 内核缓冲区：分配、管理与回收机制

> **学习范围**：以 Linux 常见文件 I/O、TCP 网络 I/O
> 和网卡驱动路径为主，解释 Page Cache、Socket
> 发送/接收缓冲区、`sk_buff`、网卡 DMA 描述符环和 DMA
> 数据缓冲区如何分配、使用、复用与回收。
>
> **重要说明**：Linux 内核版本、文件系统、网络协议、网卡驱动、DMA/IOMMU
> 能力和具体 I/O API
> 都会影响实现细节。本文描述的是通用机制和典型路径，不把某一种驱动或某个内核版本的实现当作所有
> Linux 系统的固定行为。

------------------------------------------------------------------------

## 1. 先理解：Linux 中不存在一个统一的"内核缓冲区"

"内核缓冲区"是一个统称。Linux
不会只分配一块叫作"内核缓冲区"的大内存，然后让文件、网络、磁盘和网卡全部共用。不同子系统会根据用途分配和管理不同资源。

  ----------------------------------------------------------------------------------------------------
  名称               用途                             主要管理者        常见内存来源
  ------------------ -------------------------------- ----------------- ------------------------------
  Page Cache         缓存文件内容                     文件系统 /        主机 RAM 中的页或 folio
                                                      内存管理子系统    

  Socket 发送数据    暂存待发送、未确认的网络数据     TCP / Socket      skb 数据区、页面片段等
                                                      网络协议栈        

  Socket 接收数据    暂存已收到、等待应用读取的数据   TCP / Socket      skb 数据区、页面片段等
                                                      网络协议栈        

  `sk_buff`（skb）   描述和组织网络数据包             Linux 网络协议栈  内核对象分配器及其数据存储区

  网卡 RX/TX         告诉网卡从哪里收发数据           网卡驱动          通常是主机 RAM 中的 DMA
  描述符环                                                              一致性内存

  网卡 RX/TX         实际承载收发 payload             网卡驱动          通常是主机 RAM
  数据缓冲区                                                            中映射给设备的页面或缓冲区

  网卡内部 SRAM /    网卡内部临时缓存和硬件处理       网卡硬件          网卡设备自身资源
  FIFO                                                                  
  ----------------------------------------------------------------------------------------------------

要特别区分三类东西：

1.  **内核管理的数据缓冲区**：例如 Page Cache 页面、网络 payload 页面。
2.  **描述和管理数据的元数据**：例如 `sk_buff`、DMA 描述符、队列节点。
3.  **设备内部硬件缓冲**：例如网卡 SRAM、FIFO。

它们都可能被口语化地称为"缓冲区"，但不是同一块内存，也不是同一种分配方式。

## 2. Linux 内核通过什么机制分配内存？

理解具体缓冲区前，先认识几个基础分配机制。

### 2.1 页分配器（Page Allocator / Buddy Allocator）

主机 RAM 被内核按页管理。常见体系结构中基础页大小通常为 4
KiB，但也存在其他页大小和大页机制。

页分配器负责向内核子系统提供一个或多个物理页。Linux 的伙伴系统（Buddy
System）是页分配的重要机制之一。

概念示意：

``` text
内核需要一批物理页
       |
       v
页分配器（伙伴系统等）
       |
       +---- 分配 1 个基础页
       |
       +---- 分配多个连续页
       |
       v
返回页 / folio 等内存资源
```

页分配器通常不理解"这是文件缓存"或"这是 TCP
数据"。它主要负责提供页级内存，具体用途由调用它的内核子系统决定。

### 2.2 SLAB / SLUB 等小对象分配器

内核经常需要分配小型对象，例如：

-   `struct sk_buff` 这样的网络元数据对象；
-   文件系统和内存管理中的各种结构体；
-   内核对象、队列节点和管理信息。

如果每个小对象都直接申请整页，会产生明显浪费。因此内核提供 slab
系列分配器。现代 Linux 常见配置使用 SLUB。

概念示意：

``` text
页分配器提供若干页
       |
       v
SLUB 等对象分配器
       |
       +---- 切分为多个同类小对象槽位
       |
       +---- 分配一个 skb 元数据对象
       |
       +---- 对象释放后放回缓存，等待复用
```

注意：SLAB/SLUB 管理的是小对象缓存，不代表所有网络 payload 都放在 skb
结构体内部，也不代表所有内核缓冲区都来自 SLUB。

### 2.3 `kmalloc`、`vmalloc` 与 DMA API

-   `kmalloc`：常用于申请较小的内核内存块，通常要求物理地址连续（具体行为受分配大小和实现影响）。
-   `vmalloc`：提供虚拟地址连续的内核内存，但底层物理页不一定连续。
-   页分配器接口：用于申请页级内存。
-   DMA API：用于让设备能够安全访问主机内存，处理 DMA
    地址映射、缓存一致性和 IOMMU 等平台差异。

**DMA 地址不应简单等同于 CPU 看到的虚拟地址，也不保证等同于物理地址。**
在有 IOMMU 的系统中，设备使用的 DMA 地址可能由 IOMMU
映射到真实物理页面。

### 2.4 内核分配内存的一般流程

``` text
文件系统 / 网络协议栈 / 网卡驱动
                 |
                 | 根据业务需求申请内存
                 v
          内核内存分配接口
                 |
        +--------+---------+
        |                  |
        v                  v
   小对象分配           页级分配
   SLUB/kmalloc         Page Allocator
        |                  |
        +--------+---------+
                 |
                 v
          获得内核内存资源
                 |
                 v
       子系统初始化并使用该资源
                 |
                 v
       释放、回收或放回缓存复用
```

## 3. Page Cache：文件数据是怎么进入内核缓存的？

### 3.1 Page Cache 是按需建立的，不会提前缓存整个磁盘

假设程序第一次读取一个文件：

``` java
ByteBuffer buffer = ByteBuffer.allocateDirect(4096);
fileChannel.read(buffer);
```

典型的 buffered I/O 路径大致如下：

``` text
Java 调用 read()
    |
    v
进入内核，文件系统处理读取请求
    |
    v
查询文件对应的 Page Cache
    |
    +---- 命中：复用已有缓存页 / folio
    |
    +---- 未命中：
            |
            v
       申请页 / folio
            |
            v
       建立文件页缓存映射
            |
            v
       发起块设备 I/O
            |
            v
       存储设备通过 DMA 等机制
       将数据写入主机 RAM 中的页面
            |
            v
       I/O 完成，页面可供读取
    |
    v
内核将数据复制到用户缓冲区
    |
    v
read() 返回
```

重点是：**Page Cache 中的页面通常不会在一次 `read()` 返回时立即释放。**
它们会继续作为文件缓存保留，以便后续读取复用。

### 3.2 Page Cache 的页面由谁分配？

从概念上看，文件系统 /
内存管理子系统发现缓存缺页后，会通过内核页分配机制取得物理页或
folio，再将其关联到文件的地址空间映射（常见概念是 `address_space`）。

现代 Linux 内核逐步使用 folio
抽象来管理一个或多个基础页。较早资料可能更多使用 `page` / `struct page`
的表述。理解原理时可以把它们看作文件缓存中的页级内存单元，但不要把 folio
永远等同于一个 4 KiB 页。

简化过程：

``` text
文件偏移 / 文件页索引
       |
       v
查询文件 address_space 中的缓存
       |
       +---- 已存在：取得引用并使用
       |
       +---- 不存在：
                |
                v
          页分配器分配页面
                |
                v
          建立 Page Cache 条目
                |
                v
          读取文件内容到页面
```

### 3.3 Page Cache 什么时候释放？

Page Cache 是缓存，不是"读完立即释放"的临时缓冲区。

常见情况：

-   **干净页面（clean
    page）**：内容与磁盘一致，内存压力下通常可以直接回收，之后需要时再从存储设备读入。
-   **脏页面（dirty
    page）**：内容已修改但尚未写回存储设备，通常需要先安排写回，之后才能安全回收。
-   **正在被引用、映射或固定的页面**：可能暂时不能回收，必须等相关引用或使用关系结束。
-   **内存压力**：内核回收机制会扫描可回收页面，Page Cache
    是重要回收对象之一。
-   **显式丢弃缓存**：某些系统调用和文件系统操作可以影响缓存，但不应把它理解为普通程序每次读取后都手动释放缓存。

### 3.4 Page Cache 的分配与回收小结

  时机                                 典型行为
  ------------------------------------ -------------------------------------------------
  第一次读取某个文件区域，缓存未命中   按需分配页面 / folio 并发起 I/O
  再次读取相同区域                     命中时复用已有缓存
  顺序读取                             内核可能进行预读（readahead），提前加载后续页面
  读取系统调用返回                     缓存通常保留，不立即释放
  内存压力                             回收可回收的干净缓存页；脏页通常需要先写回
  文件数据被修改                       对应缓存页可能变脏，之后由写回机制处理

### 3.5 Page Cache 与 Direct I/O

普通 buffered I/O 通常使用 Page Cache。某些文件系统和设备路径支持 Direct
I/O（例如使用 `O_DIRECT`），其目标是绕过普通 Page Cache
数据缓存路径，但仍然需要内核管理
I/O、地址对齐、页面和设备传输资源。Direct I/O
不等于"应用直接控制磁盘"，也不意味着完全没有内核缓冲或复制。

## 4. Socket 发送缓冲区：什么时候分配，什么时候释放？

### 4.1 `SO_SNDBUF` 不是启动时一次性分配好的整块内存

应用可以通过 `SO_SNDBUF` 设置 Socket 发送缓冲区相关限制。

但需要纠正一个常见误解：

**设置发送缓冲区大小，通常是在设置内核发送内存记账和排队容量的限制，不代表内核立刻为这个
Socket 预先分配一整块同样大小的连续物理内存。**

实际发送数据时，内核按需分配 skb、数据区或页面片段，并将其纳入 Socket
的内存记账和发送队列管理。

Linux 还会受到系统级参数、协议栈策略和自动调优机制影响。`SO_SNDBUF`
的具体语义和返回值处理也有 Linux
特有细节，不应简单将应用设置值等同于实际一次性分配量。

### 4.2 普通 TCP 发送过程

应用执行：

``` java
socketChannel.write(buffer);
```

概念路径：

``` text
Java 用户态
    |
    | write() 系统调用
    v
Linux 内核态
    |
    v
TCP / Socket 发送路径
    |
    v
检查 Socket 发送内存记账与限制
    |
    v
按需组织 skb 和 payload 存储
    |
    +---- 可能使用 skb 线性数据区
    |
    +---- 也可能使用页面片段等形式
    |
    v
进入 TCP 发送队列 / 重传相关队列
    |
    v
拥塞控制、流量控制、分段、排队
    |
    v
驱动映射 DMA 并提交 TX 描述符
    |
    v
网卡读取并发送
```

`write()`
返回通常只说明本次调用处理了多少数据（可能是部分写入），不代表远端应用已经收到，也不代表网络发送和
TCP ACK 已经完成。

### 4.3 发送数据什么时候释放？

TCP
需要可靠传输，因此不能简单地认为"网卡一发送完，发送缓冲区就立刻释放"。

发送数据可能需要保留，以便在丢包时重传。典型情况下：

1.  应用写入数据，内核把数据放入 TCP 发送路径。
2.  网卡发送数据。
3.  TCP 等待对端 ACK。
4.  未确认数据仍可能需要保留，以支持重传。
5.  收到有效 ACK 后，对应已确认数据可以从 TCP
    未确认发送队列中移除，其相关 skb / payload 内存可以释放或回收。
6.  若发生丢包或超时，内核可能重传相应数据。

注意：实际释放时机还受 skb
结构、分段、GSO/TSO、重传队列、引用计数、零拷贝页面引用等影响。不要把"ACK
到达"理解成每一种底层内存对象都在同一条指令里立即释放；准确说法是，ACK
推进确认状态后，相应数据不再需要用于 TCP
重传，随后相关资源可被释放或复用。

### 4.4 TCP 发送缓冲区流程图

``` text
应用 write()
    |
    v
内核按需分配 / 使用 skb 和 payload 存储
    |
    v
TCP 发送队列（等待发送 / 发送中）
    |
    v
网卡 DMA 读取并发送
    |
    +---- 收到 ACK
    |        |
    |        v
    |    已确认数据从未确认队列移除
    |        |
    |        v
    |    相关内存释放或复用
    |
    +---- 未收到 ACK / 丢包
             |
             v
         保留数据以支持重传
             |
             v
           重新发送
```

## 5. Socket 接收缓冲区：什么时候分配，什么时候释放？

### 5.1 接收缓冲区也不是每个 Socket 一创建就分配满额

TCP Socket 有接收缓冲区相关限制，例如
`SO_RCVBUF`。它主要参与接收内存记账和容量控制，不应简单理解为创建 Socket
时立即分配一整块同等大小的连续内存。

实际接收数据时，内核网络协议栈和网卡驱动会按需使用接收缓冲区、skb
和页面等资源。

### 5.2 网卡接收数据之前，驱动通常要准备 RX 缓冲区

网卡不能凭空把数据写进任意内存。驱动通常会先准备可供网卡 DMA
写入的主机内存缓冲区，并将其 DMA 映射后放入 RX 描述符环。

简化过程：

``` text
驱动初始化 / 补充 RX 队列
    |
    v
分配或取得主机 RAM 中的接收缓冲区
    |
    v
通过 DMA API 映射给设备
    |
    v
填写 RX Descriptor（DMA 地址、长度等）
    |
    v
通知网卡：这些缓冲区可用于接收
    |
    v
网卡收到数据
    |
    v
网卡 DMA 将数据写入对应主机 RAM 缓冲区
    |
    v
驱动通过中断 / NAPI 轮询发现接收完成
    |
    v
内核协议栈处理数据
    |
    v
数据进入 TCP 接收队列，等待应用读取
```

### 5.3 应用调用 `read()` / `recv()` 后发生什么？

典型 TCP 接收路径：

``` text
网卡接收数据
    |
    v
DMA 写入主机 RAM 的 RX 缓冲区
    |
    v
驱动 / NAPI 处理数据
    |
    v
构造或组织 skb，交给网络协议栈
    |
    v
IP / TCP 处理
    |
    v
TCP 接收队列
    |
    v
应用调用 read() / recv()
    |
    v
内核将数据复制到用户缓冲区（普通接收路径）
    |
    v
相关接收数据被消费
    |
    v
skb / 页面等资源可释放或复用
```

普通 `recv()`
路径通常会把数据复制到用户缓冲区。复制完成后，已经被应用消费的接收数据可以从
Socket 接收队列移除，相关 skb 或页面资源可以释放或回收到内存池。

如果应用还没有读取数据，数据会继续留在接收队列中，占用接收内存，并受到接收缓冲区限制、TCP
流量控制等机制影响。

### 5.4 接收缓冲区什么时候释放？

-   数据尚未被应用读取：通常仍在接收队列中等待消费。
-   应用读取并消费数据：对应队列数据被移除，相关资源可释放或复用。
-   接收队列被丢弃或连接关闭：未消费的数据和相关资源会在清理过程中释放。
-   驱动 RX
    缓冲区：接收完成后，驱动可能把缓冲区交给协议栈，也可能在适用情况下复用或补充新的缓冲区；具体取决于驱动和页面池机制。

## 6. `sk_buff`：它是什么，如何分配？

### 6.1 skb 不是"整个 Socket 缓冲区"

`struct sk_buff` 是 Linux 网络协议栈的重要数据结构，通常简称
skb。它主要描述一个网络数据包及其相关元数据，例如：

-   数据长度；
-   网络协议头位置；
-   MAC / IP / TCP 等头部相关偏移；
-   校验和状态；
-   分段与卸载信息；
-   线性数据区；
-   页面片段引用等。

**skb 元数据对象和 payload 数据不一定是同一块内存。**

一个 skb 可能有： - 自己的线性数据区； - 一个或多个页面片段； -
对其他页面数据的引用； - 克隆或共享的数据存储关系。

所以"分配一个 skb"不等于"分配一块完整、连续、固定大小的网络数据缓冲区"。

### 6.2 skb 如何分配？

具体分配函数取决于路径。常见概念包括：

-   `alloc_skb()`：通用 skb 分配路径之一；
-   `napi_alloc_skb()`：常见于 NAPI 接收处理路径；
-   其他驱动或协议路径的专用分配 / 构造方式；
-   数据存储区可能由 `kmalloc`、页分配器、页面片段或页面池等机制提供。

简化示意：

``` text
网络协议栈 / 驱动需要一个数据包对象
                 |
                 v
           分配 skb 元数据
                 |
                 v
        分配或关联 payload 数据存储
                 |
       +---------+----------+
       |                    |
       v                    v
   线性数据区            页面片段 / 引用页面
       |                    |
       +---------+----------+
                 |
                 v
         skb 描述网络数据包
```

### 6.3 skb 什么时候释放？

skb 的生命周期由网络协议栈、驱动和引用关系共同决定。

-   发送路径：数据完成发送、确认、丢弃或不再需要后，相关 skb 可释放。
-   接收路径：数据被协议栈消费、应用读取、丢弃或连接清理后，相关 skb
    可释放。
-   共享 /
    克隆：可能有多个引用者，最后一个引用结束后底层数据存储才能释放。
-   页面片段：页面可能通过引用计数或页面池等机制复用，不一定在 skb
    释放时立刻归还给页分配器。

## 7. 网卡 RX/TX 描述符环和 DMA 缓冲区如何分配？

这是与 Page Cache、Socket Buffer 不同的一层：它属于网卡驱动和设备 DMA
交互机制。

### 7.1 描述符环（Descriptor Ring）是什么？

网卡需要知道： - 接收数据应该写到主机内存的哪个 DMA 地址； -
发送数据应该从主机内存的哪个 DMA 地址读取； - 每个缓冲区有多长； -
当前描述符的状态是什么。

驱动和网卡通过 RX/TX 描述符环交换这些信息。

描述符通常只保存地址、长度、状态和控制位等元数据，**它本身通常不保存完整的网络
payload。**

### 7.2 描述符环通常如何分配？

很多驱动会在设备初始化或队列建立时，为描述符环分配一段设备可 DMA
访问的内存。常见方式是使用 DMA 一致性分配 API（例如
`dma_alloc_coherent()`），然后把 DMA 地址提供给设备。

简化过程：

``` text
网卡驱动初始化
    |
    v
分配 RX / TX 描述符环内存
    |
    v
建立 CPU 可访问地址和 DMA 地址映射
    |
    v
初始化每个描述符
    |
    v
把环的 DMA 地址和大小配置给网卡
    |
    v
设备开始使用描述符环
```

具体驱动也可能采用不同的队列布局、内存分配方式和 DMA API。

### 7.3 RX 数据缓冲区如何准备？

驱动通常需要为 RX 描述符准备真正承载数据的主机内存缓冲区：

1.  申请或从池中取得一个页面 / 缓冲区。
2.  使用 DMA API 将其映射为设备可访问的 DMA 地址。
3.  把 DMA 地址和缓冲区长度写入 RX 描述符。
4.  通知网卡 RX 描述符可用。
5.  网卡收到数据后，通过 DMA 将数据写入主机 RAM。
6.  驱动处理完成的描述符，并把数据交给协议栈。
7.  驱动或页面池补充新的 RX 缓冲区，保持接收队列有可用资源。

### 7.4 TX 数据缓冲区如何使用？

发送方向通常相反：

1.  协议栈准备 skb 和 payload。
2.  驱动获取 skb 中的线性数据区和页面片段。
3.  驱动通过 DMA API 映射这些数据。
4.  将 DMA 地址、长度和控制信息写入 TX 描述符。
5.  通知网卡开始发送。
6.  网卡通过 DMA 从主机 RAM 读取数据。
7.  发送完成后，驱动处理完成描述符，解除 DMA 映射，并释放或复用 skb /
    页面资源。

### 7.5 RX 与 TX 对照

  ----------------------------------------------------------------------------
  项目                    RX 接收方向             TX 发送方向
  ----------------------- ----------------------- ----------------------------
  数据方向                网卡 → 主机 RAM         主机 RAM → 网卡

  谁准备描述符            驱动 / CPU              驱动 / CPU

  谁执行数据搬运          网卡 DMA 写入主机 RAM   网卡 DMA 从主机 RAM 读取

  描述符内容              目标 DMA                源 DMA
                          地址、长度、状态等      地址、长度、控制信息等

  完成后                  驱动处理数据并补充 RX   驱动回收完成资源、解除映射
                          缓冲区                  
  ----------------------------------------------------------------------------

### 7.6 DMA API 的两个常见概念

**一致性 DMA 内存（Coherent DMA）**

例如描述符环常使用一致性 DMA 分配机制。CPU
和设备可以共享访问这块内存，具体一致性语义由平台和 DMA API
保证。它适合设备和 CPU 需要频繁共享描述符状态的场景。

**流式 DMA 映射（Streaming DMA Mapping）**

例如发送 payload 或接收数据缓冲区，驱动可以使用
`dma_map_single()`、`dma_map_page()` 等 DMA API
将一段内存映射给设备使用。映射方向（DMA_TO_DEVICE、DMA_FROM_DEVICE、DMA_BIDIRECTIONAL）要与实际用途匹配，并按平台要求处理同步和解除映射。

不要把 DMA 地址当作普通 CPU 虚拟地址使用，也不要绕过 DMA API
假设所有平台都能直接把物理地址交给设备。

## 8. 网卡接收：从设备到应用程序的完整生命周期

以 TCP 接收为例，把驱动缓冲区、skb、Socket 接收队列和用户缓冲区连起来：

``` text
A. 队列准备阶段
CPU / 驱动
    |
    +--> 分配或取得 RX 数据缓冲区（主机 RAM）
    |
    +--> DMA API 映射
    |
    +--> 填写 RX 描述符环
    |
    v
网卡获得可用接收缓冲区

B. 数据到达阶段
网络数据到达网卡
    |
    v
网卡 DMA 将数据写入主机 RAM 的 RX 缓冲区
    |
    v
驱动通过中断 / NAPI 轮询发现完成
    |
    v
驱动组织 skb / 页面引用
    |
    v
IP / TCP 协议栈处理
    |
    v
TCP Socket 接收队列

C. 应用消费阶段
Java 调用 read() / recv()
    |
    v
内核把接收数据复制到用户缓冲区（普通路径）
    |
    v
接收队列中已消费的数据被移除
    |
    v
skb / 页面资源释放或复用
```

关键点： - RX DMA 缓冲区可能直接被协议栈使用，也可能需要构造或组织
skb。 - 驱动通常会补充新的 RX 缓冲区，避免接收队列耗尽。 - 普通 `recv()`
复制到用户空间后，相关数据才算被应用消费。 -
具体页面是否立刻回到分配器，取决于引用计数、页面池和驱动复用策略。

## 9. 文件发送：Page Cache 与 sendfile 页面引用的生命周期

在适用的 Linux `sendfile()` 零拷贝路径中，内核可能让网络发送结构引用
Page Cache 中原来的文件页面，而不是复制一份完整 payload。

概念流程：

``` text
文件数据位于 Page Cache 页面 P
           |
           v
sendfile() 请求发送文件范围
           |
           v
内核取得页面 P 的引用 / 组织发送结构
           |
           v
skb 的页面片段引用页面 P
           |
           v
驱动将页面数据映射为 DMA 地址
           |
           v
网卡 DMA 读取页面 P 的数据
           |
           v
发送完成 / 相关网络引用结束
           |
           v
释放相应引用
           |
           v
页面 P 是否回收由 Page Cache 和内存回收机制决定
```

需要注意：

1.  网卡发送期间，相关页面必须保持有效，不能在设备仍可能读取时被错误释放或修改。
2.  网络发送结构对页面的引用需要正确管理。
3.  发送完成后，网络路径释放自己的引用；Page Cache
    仍可能保留页面作为文件缓存。
4.  页面不一定在发送结束后立即从 Page Cache 删除。
5.  具体内核路径可能使用页面引用、拷贝或其他优化，不能把"sendfile"理解为任何系统、任何设备上都绝对没有复制。

## 12. 面试回答模板

### 12.1 Linux 内核缓冲区是怎么分配的？

Linux 没有一个统一的内核缓冲区。不同子系统根据用途申请资源：Page Cache
在文件缓存缺页时通过页分配机制按需建立；Socket
发送和接收路径在数据收发时动态组织 skb 和 payload，并受 Socket
内存记账及缓冲区限制约束；网卡驱动在队列初始化和运行过程中准备 RX/TX
描述符环及 DMA 缓冲区。小型内核对象常通过 SLAB/SLUB
等分配器管理，页级数据通常通过页分配器或页面池管理，设备访问主机内存则通过
DMA API 建立映射。

### 12.2 Page Cache 什么时候释放？

Page Cache 是文件缓存，不是一次 `read()`
调用的临时数组。缓存缺页时按需建立页面，读取完成后通常保留以便复用。内存压力下，内核可以回收干净缓存页；脏页通常需要先写回存储设备。正在被引用、映射或固定的页面可能暂时不能回收。

### 12.3 TCP 发送缓冲区什么时候释放？

应用调用 `write()` 后，内核会把数据组织到 TCP
发送路径中。网卡发送完成不代表 TCP
数据可以立即释放，因为未确认数据可能需要重传。收到有效 ACK
后，已确认数据不再需要用于重传，相关 skb 和 payload
资源可以从发送队列移除并释放或复用。具体底层对象的回收还受引用计数、分段和驱动完成状态影响。

### 12.4 网卡 DMA 缓冲区如何分配？

驱动通常在队列初始化或运行补充时，准备主机 RAM 中的 RX/TX 缓冲区，并通过
DMA API 映射给设备使用。描述符环保存 DMA
地址、长度和状态等信息。接收时网卡 DMA 把数据写入 RX 缓冲区；发送时网卡
DMA 从 TX 数据缓冲区读取数据。CPU /
驱动负责准备描述符、映射、通知设备和处理完成状态，DMA 引擎负责实际搬运。

### 12.5 零拷贝时 Page Cache 会被释放吗？

不会因为一次 sendfile 发送就必然释放。适用的零拷贝路径可以让 skb
等网络结构引用 Page Cache 页面，网卡 DMA
读取页面数据。发送路径需要在发送完成前保持页面有效；网络引用结束后释放相应引用，但
Page Cache
仍可能保留该页面作为文件缓存，之后由内存回收机制决定是否回收。

## 13. 最后记住这 10 句话

1.  Linux 没有一个统一的"内核缓冲区"，而是多个子系统管理多种内存资源。
2.  页分配器负责提供页级内存，SLAB/SLUB 常用于管理内核小对象。
3.  Page Cache 在文件缓存缺页时按需建立，读取完成后通常不会立即释放。
4.  Page Cache 的干净页可以回收，脏页通常需要先写回。
5.  `SO_SNDBUF` / `SO_RCVBUF` 主要涉及 Socket
    内存记账和容量限制，不代表一次性分配同等大小的连续物理内存。
6.  skb 是网络数据包描述和组织结构，payload 不一定与 skb
    元数据处于同一块连续内存。
7.  TCP 发送数据可能要保留到收到 ACK，以支持可靠传输和重传。
8.  TCP 接收数据在应用消费后，相关 skb / 页面可以释放或复用。
9.  网卡描述符环和 DMA 数据缓冲区通常由驱动准备，设备通过 DMA 访问主机
    RAM；网卡也可能有自己的 SRAM/FIFO。
10. **分配、记账、引用、DMA
    映射和物理内存回收是不同概念，不能把它们统称为"分配一块缓冲区、用完立即释放"。**
