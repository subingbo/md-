# Java I/O、直接内存、零拷贝与 DMA 完整笔记

> 学习目标：理解 CPU 用户态/内核态、用户空间/内核空间、JVM
> 堆内存/直接内存、Page Cache、Socket 发送路径、网卡缓冲区、CPU
> 数据复制、DMA，以及 Linux `sendfile()` 零拷贝之间的关系。
>
> 本文以 **Linux + OpenJDK 常见实现 + 普通文件缓冲 I/O + TCP Socket**
> 为主要讨论场景。不同 JDK
> 版本、操作系统、内核版本、网卡驱动、硬件卸载能力和 I/O
> 模式可能导致具体路径不同。流程图是帮助理解的典型模型，不代表所有平台都逐步完全相同。

------------------------------------------------------------------------

## 1. 先建立整体认识

讨论 I/O 时，经常会把几个不同维度混在一起：

  -------------------------------------------------------------------------------------------------------
  概念                    它回答的问题                                         例子
  ----------------------- ---------------------------------------------------- --------------------------
  用户态 / 内核态         CPU 当前以什么特权级别执行指令？                     Ring 3 / Ring 0

  用户空间 / 内核空间     当前进程的虚拟地址空间如何划分、哪些地址允许访问？   JVM Heap、Page Cache

  内存归属与用途          某块内存由谁管理、用来做什么？                       DirectByteBuffer、Socket
                                                                               发送数据页

  CPU 复制                是否由 CPU 执行内存复制指令？                        `memcpy`、`copy_to_user`

  DMA                     是否由 DMA 引擎完成数据搬运？                        网卡从主机 RAM
                                                                               读取待发送数据

  零拷贝                  是否避免了不必要的数据复制，尤其是用户空间中转？     Linux `sendfile()`
  -------------------------------------------------------------------------------------------------------

**最重要的结论：这些概念不是同一个维度。**

-   用户态 / 内核态是 CPU 执行指令时的特权级别。
-   用户空间 / 内核空间是虚拟地址空间和访问权限的划分。
-   Heap、DirectByteBuffer、Page Cache、Socket 数据页是不同用途的内存。
-   CPU 和 DMA 是不同的数据搬运执行方式。
-   零拷贝是减少数据复制的一类优化思路，不是取消所有内存、缓冲区或 CPU
    工作。

## 2. 用户态和内核态到底是什么？

### 2.1 它们属于 CPU 的执行特权级别

以常见 x86 架构为例，操作系统内核通常运行在 Ring
0，普通应用程序通常运行在 Ring 3。

-   **用户态（User
    Mode）**：权限受限，普通应用程序不能直接执行某些特权指令，也不能随意访问内核受保护的地址。
-   **内核态（Kernel
    Mode）**：拥有更高特权，操作系统内核可以执行特权操作、管理硬件和系统资源。

它们不是某段代码永久拥有的属性，也不是某个线程固定不变的身份。CPU
执行普通应用代码时通常处于用户态；通过系统调用进入内核执行内核代码时，CPU
切换到内核态；系统调用返回后再回到用户态。

### 2.2 一个 Java 线程会在两种状态间切换

``` text
CPU 执行 Java 业务代码
状态：用户态
        |
        | 调用 read() / write() 等系统调用
        v
CPU 执行操作系统内核代码
状态：内核态
        |
        | 系统调用处理完成并返回
        v
CPU 继续执行 Java 业务代码
状态：用户态
```

**线程由内核调度，不代表线程一直处于内核态。** 普通 Java
线程绝大多数业务代码都在用户态执行，只有进入内核服务路径时才会执行内核态代码。

### 2.3 用户空间和内核空间不是两条完全独立的物理内存

它们是虚拟地址空间及访问权限上的划分。用户进程使用用户空间地址；内核使用内核空间地址。它们最终都可能映射到机器的物理
RAM，但访问权限和映射方式不同。

可以粗略理解为：

``` text
主机物理内存 RAM
    ^
    | 通过页表映射到虚拟地址空间
    |
+---------------------------------------+
| 用户进程可访问的用户空间               |
|   JVM Heap                            |
|   DirectByteBuffer 的本地内存           |
+---------------------------------------+
| 操作系统内核使用的内核空间             |
|   Page Cache                          |
|   Socket / 网络协议栈数据结构           |
|   内核管理的其他内存                   |
+---------------------------------------+
```

注意：图中是概念示意，不表示物理 RAM
被永久切成两块，也不表示所有机器的虚拟地址布局都相同。

## 3. 各种内存分别是什么？

### 3.1 JVM Heap（堆内存）

通过以下代码分配：

``` java
ByteBuffer buffer = ByteBuffer.allocate(1024);
```

缓冲区的数据存储在 JVM 堆内。它受 JVM
垃圾回收机制管理。对于普通堆对象，GC 可能在整理内存时移动对象。

### 3.2 DirectByteBuffer（直接内存）

通过以下代码分配：

``` java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024);
```

DirectByteBuffer 的数据存储在 JVM 堆外的本地内存（Native
Memory）中。Java 层仍然有一个 DirectByteBuffer
对象包装和管理这块内存，但实际数据不在普通 JVM Heap 中。

**直接内存仍然属于用户进程可以访问的内存，不是内核内存。**

它常用于 I/O 缓冲，因为底层本地 I/O
可以使用其本地内存地址，避免普通堆缓冲区在某些 JDK I/O
实现中需要的临时直接内存中转。

### 3.3 Page Cache（页缓存）

Page Cache 是 Linux 使用主机 RAM 缓存文件内容的机制。

读取普通文件时：

-   如果数据已经在 Page Cache 中，内核可以直接从缓存提供数据。
-   如果数据不在缓存中，内核需要从存储设备读取数据，通常由存储设备 DMA
    将数据传输到主机内存中的页缓存页面。

Page Cache 由操作系统内核管理，通常使用主机 RAM。

### 3.4 Socket 发送路径、Socket Buffer 和 `sk_buff`

网络发送时，内核需要管理待发送数据、协议头、网络设备队列、发送状态等。

在 Linux 中，`sk_buff`（常简称
skb）是网络数据包的重要内核数据结构。它包含数据包元数据，并可管理线性数据区和页面片段（page
fragments）等。

因此，不能把 Socket Buffer 简单理解成一块永远独立、连续、完整保存所有
payload 的固定内存。具体数据可能位于 skb
的线性区，也可能通过页面片段引用其他内存页面。

日常说"Socket 发送缓冲区"，通常是对内核发送缓存、排队和记账机制的概括。

### 3.5 网卡缓冲区有两种常见含义

**第一种：主机 RAM 中由网卡驱动管理的缓冲区。**

例如 RX/TX
描述符环、接收缓冲区、发送数据页等。它们位于主机内存中，驱动通过 DMA API
将相应内存映射给设备使用。

**第二种：网卡硬件内部的缓冲资源。**

例如网卡内部 SRAM、FIFO
等，由网卡硬件管理，用于临时缓存和发送/接收处理。

所以，"网卡缓冲区"这个词需要结合上下文判断。它不一定指网卡板卡上独立的一块内存；很多网卡数据收发直接使用主机
RAM 中的 DMA 缓冲区。

### 3.6 内存归属速查表

  -----------------------------------------------------------------------
  名称                    典型位置                管理者 / 使用者
  ----------------------- ----------------------- -----------------------
  JVM Heap                主机 RAM，用户空间映射  JVM

  DirectByteBuffer 数据区 主机                    JVM / 本地内存分配机制
                          RAM，用户进程本地内存   

  Page Cache              主机 RAM，内核管理      Linux 内核

  Socket / skb 数据区     通常是主机              Linux 网络协议栈
                          RAM，内核管理           

  网卡 RX/TX              通常是主机 RAM          网卡驱动与网卡设备
  描述符环、DMA                                   
  数据缓冲区                                      

  网卡内部 SRAM / FIFO    网卡设备内部            网卡硬件
  -----------------------------------------------------------------------

## 4. CPU 复制与 DMA 搬运有什么区别？

### 4.1 CPU 复制

当 CPU 执行内存复制指令时，例如 `memcpy` 或内核中的 `copy_to_user` /
`copy_from_user`，就是 CPU 亲自执行复制工作。

例如：

``` text
主机 RAM 中的 A 区域
        |
        | CPU 执行复制指令
        v
主机 RAM 中的 B 区域
```

CPU 可能使用优化过的指令、SIMD、缓存等，不是简单地每次只复制一个字节。

### 4.2 DMA

DMA（Direct Memory Access，直接内存访问）允许 DMA 引擎在 CPU
不逐字节执行复制指令的情况下完成数据传输。

以网卡发送为例：

1.  CPU / 驱动准备主机内存缓冲区。
2.  CPU / 驱动通过 DMA API 做必要的映射和同步。
3.  CPU 填写 DMA 描述符，提供设备可使用的 DMA 地址和长度等信息。
4.  驱动通知网卡有发送任务。
5.  网卡 DMA 引擎从主机 RAM 读取数据。
6.  网卡完成发送后，通过中断、轮询等机制让驱动获知完成情况。

CPU 仍然负责配置和管理，但不需要亲自复制每个字节。

### 4.3 DMA 不是"完全不需要 CPU"

CPU 通常仍需要： - 准备源地址和目标缓冲区； - 进行 DMA 地址映射； -
填写描述符； - 启动或通知设备； - 处理完成状态、中断或轮询； -
管理缓冲区生命周期和同步。

DMA 引擎负责实际的数据搬运。DMA 执行期间，CPU 可以做其他工作。

**DMA 阶段没有一个固定的"CPU 用户态/内核态"。** 用户态/内核态描述 CPU
执行指令时的状态；DMA 是硬件引擎独立执行传输。CPU 可能在 DMA
运行期间执行其他用户态或内核态代码，也可能处于空闲状态。

### 4.4 "内存到内存就一定要 CPU"吗？

不是绝对规则。

-   普通 Linux `read()` / `write()` 路径中的很多内存复制通常由 CPU
    执行。
-   某些平台和硬件支持 DMA 内存到内存复制。
-   但使用 DMA 有描述符配置、映射、同步、完成通知等开销。
-   对较小的数据块，CPU 使用缓存和优化复制指令往往更合算。
-   设备 DMA
    引擎通常也有自身用途和能力限制，不能假设任意设备都能复制任意两块内存。

因此，**设备与主机内存之间通常会使用 DMA；主机内存之间的普通复制通常由
CPU 执行，但两者都不是绝对规则。**

### 4.5 常见传输方式对照

  --------------------------------------------------------------------------------------------
  数据传输                常见方式                                  CPU 是否参与
  ----------------------- ----------------------------------------- --------------------------
  磁盘 → Page Cache       存储设备 DMA                              CPU 配置和管理 I/O

  Page Cache →            内核复制到用户缓冲区                      CPU 在内核态执行复制
  DirectByteBuffer                                                  

  DirectByteBuffer →      普通网络发送路径通常由内核复制/组织数据   CPU 在内核态执行相关操作
  Socket 发送路径                                                   

  主机 RAM → 网卡发送路径 网卡 DMA 读取                             CPU 配置描述符和管理

  网卡接收路径 → 主机 RAM 网卡 DMA 写入                             CPU
                                                                    预备缓冲区并处理接收结果

  主机 RAM → 主机 RAM     通常 CPU 复制，也可能有 DMA               取决于实现
  --------------------------------------------------------------------------------------------

## 5. Java NIO：普通堆内存和直接内存

本节以 OpenJDK 常见实现为例。具体实现会因 JDK 版本、操作系统和 I/O
路径不同而变化。

### 5.1 普通堆内存读取文件

代码：

``` java
ByteBuffer buffer = ByteBuffer.allocate(1024);
fileChannel.read(buffer);
```

在 OpenJDK 的常见实现中，底层本地 I/O 需要可用的本地内存地址。普通堆内
ByteBuffer 的数据区在 JVM Heap 中，可能受 GC 移动影响。因此，JDK 的相关
I/O
实现通常会准备一个临时直接缓冲区（可能来自缓存池），先把文件数据读到临时直接缓冲区，再复制到
Java 堆缓冲区。

**读取时的中转方向要特别注意：不是先把空的 Heap Buffer 复制到临时
DirectBuffer，而是先把文件数据读入临时 DirectBuffer，再复制到 Heap
Buffer。**

典型流程：

``` text
阶段 1：Java 发起读取
CPU 状态：用户态
    Java 调用 FileChannel.read(heapBuffer)
                 |
                 v
    JDK 准备 / 获取临时 DirectBuffer
                 |
                 v
阶段 2：执行本地 read 系统调用
CPU 状态：内核态
    检查 Page Cache
       |
       +-- 缓存命中：直接使用缓存页面
       |
       +-- 缓存未命中：
       |      存储设备 DMA
       |          |
       |          v
       |      Page Cache（主机 RAM）
       |
       v
    CPU 将 Page Cache 数据复制到临时 DirectBuffer
                 |
                 v
阶段 3：系统调用返回
CPU 状态：用户态
    JDK 将临时 DirectBuffer 的数据复制到 HeapByteBuffer
                 |
                 v
    Java 程序使用 HeapByteBuffer 中的数据
```

复制动作： 1. Page Cache → 临时
DirectBuffer：内核执行用户缓冲区复制，通常由 CPU 完成。 2. 临时
DirectBuffer → HeapByteBuffer：JDK 在用户态完成复制，通常由 CPU 完成。
3. 如果 Page Cache 未命中，磁盘 → Page Cache 通常由存储设备 DMA 搬运。

**重要纠正：读取时没有"Heap Buffer → 临时 DirectBuffer"的数据复制。**
那是堆内缓冲区写入时的典型中转方向。

### 5.2 直接内存读取文件

代码：

``` java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024);
fileChannel.read(buffer);
```

直接缓冲区的数据区已经位于用户进程可访问的本地内存中，JDK
常见实现可以把它作为本地 I/O 的目标缓冲区使用，不需要再经过
HeapByteBuffer 的临时中转。

``` text
阶段 1：Java 发起读取
CPU 状态：用户态
    Java 调用 FileChannel.read(directBuffer)
                 |
                 v
阶段 2：进入 read 系统调用
CPU 状态：内核态
    检查 Page Cache
       |
       +-- 缓存命中：直接使用缓存页面
       |
       +-- 缓存未命中：
       |      磁盘 DMA → Page Cache
       |
       v
    CPU 将 Page Cache 数据复制到 DirectByteBuffer
                 |
                 v
阶段 3：系统调用返回
CPU 状态：用户态
    Java 直接使用 DirectByteBuffer 中的数据
```

因此，直接内存读取文件时，典型情况下仍然有： - Page Cache →
DirectByteBuffer 的内核到用户空间复制； - 但省去了临时 DirectBuffer →
HeapByteBuffer 的额外复制。

**直接内存不是内核内存，也不会因为使用了 DirectByteBuffer 就让普通
`read()` 自动变成零拷贝。**

### 5.3 普通堆内存写入网络

代码：

``` java
ByteBuffer buffer = ByteBuffer.allocate(1024);
socketChannel.write(buffer);
```

在 OpenJDK 常见实现中，堆内 ByteBuffer 写入本地 Socket 时，通常先把
HeapByteBuffer 的数据复制到临时 DirectBuffer，再执行本地写操作。

``` text
阶段 1：Java 准备写入
CPU 状态：用户态
    HeapByteBuffer
         |
         | CPU 复制
         v
    临时 DirectBuffer
         |
         | write() 系统调用
         v
阶段 2：内核网络发送路径
CPU 状态：内核态
    内核将用户数据复制 / 组织到网络发送数据结构
    （例如 skb 的线性数据区或页面片段）
         |
         v
    驱动准备发送描述符、DMA 映射
         |
         v
    网卡 DMA 从主机 RAM 读取待发送数据
         |
         v
    网卡发送
         |
         v
阶段 3：系统调用返回
CPU 状态：用户态
    Java 继续执行
```

典型的额外复制： 1. HeapByteBuffer → 临时 DirectBuffer：JDK 用户态复制。
2. 用户缓冲区 → 内核网络发送路径：普通发送路径中通常由内核 CPU
复制或组织数据。 3. 网卡 DMA 从主机 RAM 读取数据：设备 DMA，不是 CPU
逐字节复制。

注意：`write()` / `SocketChannel.write()`
返回，通常表示数据已被内核接受或部分接受，不代表远端已经收到，更不代表网卡一定已经把全部数据发完。

### 5.4 直接内存写入网络

代码：

``` java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024);
socketChannel.write(buffer);
```

典型流程：

``` text
阶段 1：Java 调用 write()
CPU 状态：用户态
    DirectByteBuffer（用户空间堆外内存）
                 |
                 | write() 系统调用
                 v
阶段 2：内核网络发送路径
CPU 状态：内核态
    内核通常将用户数据复制 / 组织到 skb 等发送数据结构
                 |
                 v
    网卡驱动配置 DMA 描述符
                 |
                 v
    网卡 DMA 读取主机 RAM 中的数据
                 |
                 v
    网卡发送
                 |
                 v
阶段 3：系统调用返回
CPU 状态：用户态
    Java 继续执行
```

直接内存省掉了堆内 ByteBuffer → 临时 DirectBuffer 的 JDK
中转复制，但普通 Socket
写入仍然通常需要内核处理用户数据并组织网络发送结构。

### 5.5 普通堆内存与直接内存对照

  ----------------------------------------------------------------------------
  对比                    HeapByteBuffer          DirectByteBuffer
  ----------------------- ----------------------- ----------------------------
  数据区位置              JVM Heap                用户进程 Native Memory

  受 JVM 堆 GC 移动影响   是                      数据区不属于普通 JVM Heap

  FileChannel 读取        常见实现使用临时        可直接作为本地 I/O 目标
                          DirectBuffer 中转       

  Socket 写入             常见实现先复制到临时    可直接作为本地 I/O 源
                          DirectBuffer            

  是否仍有系统调用        有                      有

  是否自动零拷贝          否                      否

  主要优势                使用方便，受 JVM 堆管理 减少某些 I/O
                                                  场景中的堆与本地缓冲区中转
  ----------------------------------------------------------------------------

临时直接缓冲区可能被 JDK 缓存和复用，不代表每次 I/O
都重新分配一块本地内存。

## 6. Linux 零拷贝：sendfile

### 6.1 为什么需要零拷贝？

假设 Java
文件服务器要把磁盘上的一个文件原样发送给客户端。应用程序并不需要解析或修改文件内容。

普通方式大致是：

``` text
磁盘文件
   |
   | DMA（缓存未命中时）
   v
Page Cache（主机 RAM）
   |
   | CPU 复制
   v
用户空间缓冲区（JVM Heap 或 DirectBuffer）
   |
   | CPU 复制 / 内核组织
   v
Socket 发送路径
   |
   | 网卡 DMA
   v
网卡
```

这里存在用户空间中转：内核把数据交给用户程序，用户程序又把同一批数据交回内核发送。

如果应用不需要处理文件内容，这个中转通常没有必要。

### 6.2 sendfile 的基本思路

Linux 提供 `sendfile()`，可以在内核中完成文件到 Socket 的传输。Java 的
`FileChannel.transferTo()` 在 Linux / OpenJDK 的适用路径中可能使用
`sendfile()` 等内核优化机制；但具体是否使用、是否回退到其他路径，取决于
JDK、操作系统、通道类型和运行条件。

Java 示例：

``` java
long transferred = fileChannel.transferTo(
    position,
    count,
    socketChannel
);
```

### 6.3 sendfile 典型路径

以下是 Linux 常见的基于 Page Cache 的文件到 Socket 发送路径的概念模型：

``` text
阶段 1：应用发起请求
CPU 状态：用户态
    Java 调用 FileChannel.transferTo(...)
                 |
                 v
    适用路径进入 sendfile() 系统调用
                 |
                 v
阶段 2：内核处理文件数据
CPU 状态：内核态
    查找 / 获取文件数据页
       |
       +-- Page Cache 命中：直接使用已有页面
       |
       +-- Page Cache 未命中：
       |      存储设备 DMA 将数据读入 Page Cache
       |
       v
    内核组织网络发送数据结构
    skb 可以引用原来的文件数据页
    不必把完整 payload 复制到 JVM 用户缓冲区
                 |
                 v
    网卡驱动将数据页映射为 DMA 可访问的地址
    并准备 TX 描述符
                 |
                 v
    网卡 DMA 从主机 RAM 读取数据页
                 |
                 v
    网卡发送数据
                 |
                 v
阶段 3：系统调用返回
CPU 状态：用户态
    Java 程序继续执行
```

### 6.4 "传递页面引用"是什么意思？

假设 Page Cache 中已经有文件数据：

``` text
主机 RAM
+-------------------------------------+
| Page Cache 页面 P                   |
| 文件的实际 payload 数据             |
+-------------------------------------+
```

普通复制方式可能是：

``` text
Page Cache 页面 P
       |
       | CPU 复制完整 payload
       v
另一个 Socket 数据缓冲区
```

而典型的零拷贝路径可以让 skb 的页面片段引用原来的页面：

``` text
Page Cache 页面 P
       ^
       | 页面引用 / 偏移 / 长度
       |
Socket 发送队列中的 skb
```

skb 保存的是描述和引用关系，不必再保存一份完整的 payload
副本。内核还需要管理页面引用计数和生命周期，确保网卡发送完成前数据页不会被错误回收或修改。

随后驱动为页面数据建立 DMA 映射，网卡可以通过 DMA 读取主机 RAM
中的原始数据页。

### 6.5 零拷贝仍然需要哪些缓冲区？

零拷贝不等于没有缓冲区。

  ----------------------------------------------------------------------------
  组件                     是否仍需要               说明
  ------------------------ ------------------------ --------------------------
  Page Cache               常见文件路径需要         保存文件数据页

  Socket / skb 发送队列    需要网络发送结构         skb 可以引用原数据页

  网卡驱动 DMA 描述符      需要                     告诉设备从哪里读取数据

  主机 RAM 中的网卡 DMA    可能直接使用 Page Cache  具体由驱动和内核路径决定
  数据页                   页                       

  网卡内部 SRAM / FIFO     取决于硬件设计           网卡内部可能有硬件缓冲

  JVM                      不需要作为文件内容中转   这是 sendfile
  用户空间文件数据缓冲区                            避免的关键部分
  ----------------------------------------------------------------------------

**零拷贝不是把 Page Cache 的数据先复制到网卡内部一块独立内存，再发送。**
在适用路径中，网卡可以通过 DMA 直接从主机 RAM
的数据页读取数据。网卡内部是否使用
FIFO、内部缓存或其他硬件缓冲，属于网卡实现细节。

### 6.6 零拷贝究竟减少了什么？

普通 `read()` + `write()` 的简化数据路径：

``` text
Page Cache
   |
   | CPU 复制
   v
用户空间缓冲区
   |
   | CPU 复制 / 内核组织
   v
Socket 发送路径
   |
   | DMA
   v
网卡
```

典型 `sendfile()` 优化路径：

``` text
Page Cache
   |
   | skb 引用原数据页
   v
Socket 发送队列
   |
   | 网卡 DMA 读取原数据页
   v
网卡
```

主要减少： - 文件内容从内核复制到用户空间缓冲区； -
再从用户空间缓冲区复制回内核网络发送路径。

因此，零拷贝减少了用户空间中转和 CPU 参与的数据复制。

**零拷贝不代表完全没有复制、没有 DMA、没有内核工作或没有缓冲区。**
内核仍然需要组织网络协议数据、管理
skb、处理校验和/分段等工作；具体实现也可能因为硬件能力、协议、内核版本或回退路径而发生额外复制。

## 7. DMA：CPU 到底参与什么？

以网卡发送为例：

``` text
阶段 1：CPU / 驱动准备任务
CPU 状态：通常在内核态
    选择待发送数据
    做 DMA 映射和必要同步
    填写 TX Descriptor（DMA 地址、长度等）
    通知网卡有新的发送任务
                 |
                 v
阶段 2：网卡 DMA 引擎执行
执行者：网卡硬件
    通过 PCIe 等总线读取主机 RAM 中的数据
    不需要 CPU 逐字节复制 payload
                 |
                 v
阶段 3：网卡发送
执行者：网卡硬件
    处理并发送网络数据
                 |
                 v
阶段 4：完成通知和资源回收
CPU / 驱动
    通过中断、轮询（例如 NAPI）等方式处理完成状态
    回收或复用发送资源
```

接收方向则大致相反：

``` text
CPU / 驱动预先准备 RX 缓冲区和描述符
                 |
                 v
网卡收到网络数据
                 |
                 v
网卡 DMA 将数据写入主机 RAM 中的接收缓冲区
                 |
                 v
网卡通知 CPU，或由驱动轮询发现完成
                 |
                 v
CPU / 内核网络协议栈处理数据
                 |
                 v
应用通过 recv/read 等接口获得数据
```

所以： - CPU 负责准备、配置、启动和管理 DMA。 - DMA 引擎负责实际搬运。 -
CPU 在 DMA 运行期间可以处理其他任务。 - DMA 完成后，CPU
还要处理结果和资源。

## 8. 为什么不让 DMA 完成所有内存复制？

理论上，某些硬件确实支持主机内存到主机内存的 DMA
复制。但普通内存复制仍常由 CPU 执行，原因包括：

1.  **配置成本**：DMA
    需要准备描述符、映射地址、同步和完成通知。对很小的数据块，开销可能比
    CPU 直接复制更大。
2.  **CPU 复制很快**：现代 CPU 有缓存、预取、SIMD
    和优化过的内存复制实现。
3.  **硬件能力不通用**：网卡 DMA 引擎主要服务于网卡
    I/O，不一定支持任意两块内存之间的通用复制。
4.  **资源与同步成本**：DMA 引擎、IOMMU
    映射、缓存一致性和页面生命周期管理都有成本。

因此不能简单地说"内存到内存一定 CPU"或"DMA
一定更快"。需要根据数据大小、硬件和软件实现判断。

## 11. 面试回答模板

### 11.1 用户态和内核态是什么？

用户态和内核态是 CPU
执行指令时的两种特权级别。普通应用程序通常在用户态执行，不能直接执行特权操作；需要操作系统服务时，通过系统调用进入内核态，由内核完成相应操作，结束后再返回用户态。它们不是进程或线程永久固定的状态。

### 11.2 Java 直接内存为什么能提高 I/O 性能？

DirectByteBuffer 的数据区位于 JVM
堆外的本地内存，仍然属于用户进程地址空间。普通堆内 ByteBuffer 在 OpenJDK
的一些 I/O
实现中需要临时直接缓冲区中转：读取时先读入临时直接缓冲区，再复制到堆内缓冲区；写入时先把堆内数据复制到临时直接缓冲区，再执行本地写操作。使用直接内存可以减少这类堆与临时本地缓冲区之间的额外复制，但普通
read/write 仍然需要系统调用和内核数据处理。

### 11.3 DMA 是什么？还需要 CPU 吗？

DMA 是直接内存访问机制，允许设备或 DMA 引擎在 CPU
不逐字节执行复制指令的情况下完成数据传输。CPU 仍然需要准备缓冲区、映射
DMA 地址、填写描述符、启动传输，并在完成后处理状态。DMA
的价值是把大量数据搬运工作交给硬件，释放 CPU 去执行其他任务。

### 11.4 零拷贝是什么？

以 Linux `sendfile()` 为例，应用通过系统调用请求内核把文件发送到
Socket。内核获取文件数据，常见路径中使用 Page
Cache，并让网络发送结构引用原来的数据页，网卡再通过 DMA
读取主机内存中的数据。这样可以避免文件内容先复制到 JVM
用户缓冲区、再复制回内核网络发送路径，从而减少 CPU
复制和用户空间中转。零拷贝不代表完全没有复制、没有缓冲区或不需要 CPU。

### 11.5 直接内存和零拷贝有什么区别？

直接内存解决的是 JVM 堆内缓冲区与本地 I/O
缓冲区之间可能存在的额外中转复制；零拷贝解决的是数据在内核与用户空间之间不必要的中转，典型场景是文件数据不进入
JVM 用户缓冲区而由内核直接转发。二者优化层次不同，也不是互斥关系。

## 12. 最后记住这 8 句话

1.  用户态 / 内核态描述 CPU 当前执行指令的特权级别。
2.  用户空间 /
    内核空间描述虚拟地址空间与访问权限，不是两种独立的物理内存条。
3.  JVM Heap 和 DirectByteBuffer 都属于用户进程可访问的内存；Page Cache
    和 Socket 网络数据结构由内核管理。
4.  DirectByteBuffer 是堆外内存，不是内核内存。
5.  CPU 可以亲自执行内存复制；DMA 可以在 CPU 配置后独立搬运数据。
6.  磁盘和网卡等设备与主机 RAM 之间的数据传输通常使用
    DMA；普通内存复制通常由 CPU 完成，但不是绝对规则。
7.  `sendfile()` 仍然需要读取文件、执行系统调用、组织网络协议和配置
    DMA，只是避免文件内容经过 JVM 用户缓冲区中转。
8.  **零拷贝优化的是数据复制路径，不是取消内存、缓冲区、CPU 或 DMA。**
