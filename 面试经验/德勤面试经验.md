**1. 如果要把高德替换成其他地图服务，怎么设计？**

你可以这样回答：“如果要支持地图平台切换，我会把路线规划能力抽象成业务接口，业务层只依赖这个接口，高德和其他地图平台分别提供适配实现。切换平台时，通过配置选择对应实现，减少对行程求解和活动保存等业务代码的修改。”

接口可以很简单，例如：

```
public interface RouteProvider {
    RouteResult route(RouteRequest request);
}
```

这里需要进一步解释：**接口统一的是业务含义。** 请求统一表达起终点和出行方式，结果统一表达距离、耗时和失败原因；不同平台的字段、单位、错误码在适配层处理。例如业务统一使用“米、秒”，就不能让一个实现返回秒，另一个返回分钟。坐标约定、经纬度顺序和平台支持的交通方式也需要核对，平台专属的地点 ID 则需要保留来源信息。

如果面试官追问“怎么保证可靠切换”，可以继续说：“我会先用固定地点和典型出行场景做接口契约测试，验证参数、单位、异常处理和结果完整性；再通过小流量验证调用成功率、延迟和配额消耗，保留配置回退能力。路线缓存的 key 也要区分供应商，避免切换后继续命中旧平台结果。”

这道题值得说清的是：**你能把外部依赖的变化限制在适配层，并验证切换后的业务行为。** 不需要承诺两家平台算出的路线完全相同。

**2. 数据库和 Redis 缓存的一致性怎么处理？**

你可以先回答：“项目以数据库为准，采用旁路缓存。查询时先读缓存，未命中再查询数据库并回填；更新时先提交数据库事务，再删除对应缓存，让后续查询重新加载新数据，并设置 TTL 作为过期兜底。”这是常见的 Cache-Aside 做法，但它本身不能保证数据库与缓存始终一致。[Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside?utm_source=chatgpt.com)

**“事务提交后”要讲准确。** 假如数据库事务尚未提交就删除缓存，其他请求可能查到旧数据并重新写入缓存。因此，Spring 中可以通过 `@TransactionalEventListener(phase = AFTER_COMMIT)` 或事务同步回调执行失效操作。仅仅把删除缓存的代码写在 `update()` 后面，不能说明事务已经提交。[docs.spring.io](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html?utm_source=chatgpt.com)

即使提交后再删，也仍可能出现旧值回填：请求 A 缓存未命中，先从数据库读到了旧值，但暂时没有回填；请求 B 更新数据库并删除缓存后，A 才把手里的旧值写入缓存。所以，面试官继续追问时，你可以说：“基础方案提供的是允许短暂不一致的缓存策略。如果要进一步完善，删除失败可以通过持久化任务重试；对于旧值回填，可以结合异步补删、版本控制等措施缩小窗口。要求严格读取最新状态的业务，我会直接查询数据库。”

你之前提过延迟双删，这里需要修正一点：**延迟应参考读请求从查数据库到回填缓存的耗时分布，并留出余量，不能只根据 QPS 决定。** 它能降低旧值残留的概率，但固定延迟不能保证覆盖所有慢请求。

**3. 微服务有什么优势？**

可以这样回答：“微服务按业务能力划分服务边界，主要优势是独立开发、独立部署和按服务独立扩容。比如某个计算服务资源消耗较大，可以只扩容这个服务；某项业务需要频繁更新，也可以单独发布，减少对其他服务发布节奏的影响。不同服务还可以根据需要采用不同技术栈。”这些都是微服务架构可以提供的能力。[Microsoft Learn](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/microservices?utm_source=chatgpt.com)

结合你的实习，可以补一句：“我接触过 Java 业务服务与外部 Python 计算服务的集成，能体会到业务请求和计算任务对资源、部署环境的要求不同。将边界划分清楚，有利于分别管理和扩展。”

你原来的“快速扩容、统一管理配置、回滚迅速”需要讲得更准确：**扩容的重点是按服务独立扩容；配置中心和快速回滚属于相关工程能力，单体应用也可以具备。** 同时补充代价会更完整：“服务拆开后，会增加网络调用、跨服务数据一致性、部署和故障定位的复杂度，所以我会根据业务规模和团队情况决定拆分程度。”故障隔离也需要超时、限流和资源隔离等措施配合。

**4. WITH 的结果是怎么给后面的 SQL 使用的？**

你可以回答：“WITH 用于定义公共表表达式，也就是 CTE。它给一个查询结果命名，后面的主查询或后续 CTE，就可以通过这个名字在 FROM、JOIN 等位置引用它。它的作用域是当前这条 SQL。”[postgresql.org](https://www.postgresql.org/docs/current/queries-with.html?utm_source=chatgpt.com)

例如，下面先定义 `zone_stats`，再通过名称引用它：

```
WITH zone_stats AS (
    SELECT zone_id, SUM(area) AS total_area
    FROM coverage_detail
    GROUP BY zone_id
)
SELECT zone_id, total_area
FROM zone_stats
WHERE total_area > 100;
```

对应你的项目，可以继续说：“公交和轨道覆盖统计需要使用相同的交通小区相交结果，所以我把公共的空间计算提取到 CTE，后面的统计查询引用它。这样能组织公共计算、减少重复 SQL，并便于检查执行计划。”

这里要保留一个边界：**WITH 不保证在所有数据库和查询中都只计算一次，也不保证一定更快。** 优化器可能将 CTE 内联，也可能物化保存中间结果；物化又可能影响条件下推。因此，实际优化要结合所用 KingbaseES 版本的执行计划和耗时验证。PostgreSQL 官方文档也明确说明了 CTE 内联与物化的不同执行行为。[postgresql.org](https://www.postgresql.org/docs/current/queries-with.html?utm_source=chatgpt.com) 你可以报告接口从 **13.6 秒降至 10.2 秒**的结果，但把原因完整地描述为“合并统计 SQL、提取公共计算并验证效果”。

**5. Agent 的工具上下文是怎么治理的？**

你可以这样回答：“工具结果会随着多轮调用反复进入上下文。我在工具结果写入模型消息之前增加投影处理，只保留当前决策需要的字段，对列表条数和长文本设置上限；保留必要的证据、错误信息和提交回执，并通过 `total`、`truncated` 等字段明确告知模型结果是否完整。在 120 个地点的测试场景中，单次工具输出字符量从 19,249 降至 4,931，减少了 74.4%。”

面试官可能会问“字段删掉后，会不会影响模型判断”。可以回答：“所以裁剪规则要按工具语义设计。例如地点描述、成员备注可能是推荐理由的依据，需要保留；几何数据或内部管理字段则可以单独传输或省略。同时用测试检查结果结构、关键证据和截断提示，再通过真实模型评测观察任务完成情况。”这里要明确，**字符量下降是上下文体积指标，任务完成率才反映功能是否受到影响。**

最后再单独解释错误治理：“参数缺失、可调整的业务冲突，会返回结构化错误和修正提示，允许模型在次数限制内修正；外部鉴权错误、超时或限流，则由系统按错误类型决定快速失败或有界重试，避免模型反复修改无关参数。”你原来讲的**工具输出裁剪**与**错误快速失败**是两项机制，分别解释它们解决的问题，面试官会更容易理解你的设计。
